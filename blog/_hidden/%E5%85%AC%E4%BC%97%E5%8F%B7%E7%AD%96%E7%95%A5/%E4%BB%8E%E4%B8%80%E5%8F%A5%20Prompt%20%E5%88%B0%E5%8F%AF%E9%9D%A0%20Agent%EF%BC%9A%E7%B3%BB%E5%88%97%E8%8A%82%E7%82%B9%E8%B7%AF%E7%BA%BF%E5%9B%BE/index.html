从一句 Prompt 到可靠 Agent：写作推进路线图

从一句 Prompt 到可靠 Agent：写作推进路线图

这是内部写作地图，不是对外发布的课程目录。

它要解决的问题很具体：我现在该推哪一篇，写之前要准备什么，一篇写完后又根据什么选下一篇。

先看结论

系列不再预设十五个必须依次完成的节点。

真正需要稳定的只有三件事：

  1. 始终使用同一个「技术简报助手」作为主例子。
  2. 每篇从一个真实失败出发，只引入解决这个失败所需的机制。
  3. 每篇都要独立给出一个有用的判断，不让读者等到系列完结才得到答案。

其他都可以变：文章顺序、是否使用某个框架、代码展示多少，以及这个系列最后有几篇。

系列真正要讲什么

这不是 LangChain、LangGraph 和 Langfuse 的连载教程。

系列的核心判断是：

一个可靠 Agent 不是一次设计出来的。它是在一次次具体失败中，逐渐长出行为边界、状态、恢复能力和验证方法。

所以文章里的主角始终是问题，不是框架。

不是：这一篇该介绍 LangGraph 了

而是：当前流程已经出现回退、暂停和恢复，
      普通函数调用开始难以说清状态，
      这时才值得讨论图。

系列中的固定例子

项目暂定名：tech-brief-agent。

需求保持简单：

输入：一个技术主题 + 5 个资料链接

输出：一篇 500～800 字的中文技术简报
要有事实、来源，以及一个有依据的判断

固定要求：

  • 重要事实有来源。
  • 资料事实与作者判断能够分开。
  • 来源冲突时保留分歧，不擅自选择更顺耳的答案。
  • 证据不足时缩小结论，不用常识补齐。
  • 不使用宣传腔，不为了完整而面面俱到。

需要长期保留的不是一份大而全的应用，而是四组可重复使用的失败样例：

样例 用途
资料充分且一致 检查修复边缘失败时，是否伤害了正常输入
缺少关键证据 检查模型会不会擅自补齐
两个来源互相矛盾 检查模型会不会悄悄合并分歧
营销稿与二手转述混入资料 检查来源判断和引用质量

这些样例会随文章逐渐补齐，不需要在第一篇之前全部建完。

现在就怎么推进

第一步：把 Prompt 失效草稿变成可发布的文章

现有草稿的主线已经成立：

同一句 Prompt，换模型后结果更好看却更不可靠
→ 问题来自「严谨」等未被说明的词
→ 继续堆人格词没有减少解释空间
→ 把默契改成可观察的行为
→ 再把能确定检查的边界交给程序

这篇现在缺的不是更多观点，而是一个能够支撑开场的实验记录。

发布前准备：

  • [ ] 固定一组包含「来源冲突 + 缺少证据 + 营销数字」的资料。
  • [ ] 使用同一句 Prompt、相同参数，至少运行两个模型或两个模型版本。
  • [ ] 保留原始输出，标出哪句话合并了冲突，哪个数字没有足够证据。
  • [ ] 判断这是否真的是模型差异。如果结果无法稳定复现，就把「旧模型稳定、新模型出错」改成边界更窄的表述。
  • [ ] 确定哪些输出截图或对比片段进正文，完整输出可放附录或仓库。
  • [ ] 实验补完后再做一轮 humanizer-zh，不在还没有证据时继续打磨金句。

这篇的完成标准：读者能从对比输出里看见 Prompt 的隐含默契如何被不同模型解释，而不只是接受作者的说法。

第二步：只建一份最小样例集

不需要现在就搭建 Agent 应用。为第二篇准备三到四组固定输入就够了。

每组样例留下：

原始资料
希望保住的关键事实
必须暴露的冲突或缺失
不能出现的错误
可以接受的表达差异

先用 Markdown 或 JSON 记录，不引入评测平台。这份样例集的作用是帮助写文章和比较 Prompt，不是提前完成一套生产系统。

第三步：写 Prompt 版本与回归

暂定标题：

Prompt 改到第八版，为什么反而不知道哪版最好？

核心启发：

没有固定样例和评价标准，Prompt 版本只是存档，不是能够积累的经验。

推荐叙事路径：

每次修改都修好了眼前的问题
→ v3 文风更好，却漏掉引用
→ v5 修好引用，正常样例又变得冗长
→ 固定几组输入和最小评价标准
→ 第一次能说清一次修改改善了什么，又牺牲了什么

动笔前需要的材料：

  • 同一个 Prompt 的至少三个版本。
  • 上一步建立的最小样例集。
  • 一张简单对比表：引用完整、冲突保留、缺失处理、篇幅和信息密度。
  • 至少一个「修好 A，却伤害 B」的真实回归。

这篇不展开 Langfuse、LLM-as-a-Judge 和完整 CI。先用文件、Git、少量脚本和人工判断说清「为什么要比较」。

完成标准：读者看完后能给自己的 Prompt 建一份最小回归表，而不是只学会给文件加版本号。

第四步：再决定是否紧接 Workflow 与 Agent

候选标题：

什么时候只需要 Workflow，什么时候才值得交给 Agent？

核心启发：

Agent 的价值不在于让流程显得更智能，而在于处理那些无法提前确定下一步的局部问题。

推荐叙事路径：

一次模型调用同时负责搜索、判断和写作
→ 修改一项要求，其他能力跟着退化
→ 先把确定步骤拆成 Workflow
→ 只有「证据不足时下一步怎么走」无法写死
→ 把这一小段交给 Agent 动态决定

这篇需要一个真正会分叉的任务。如果当时的简报助手仍然只是固定地读五个链接再写作，先不写这篇，因为它还没有真正需要 Agent。

可用的分叉是：

证据足够 → 进入写作
证据不足 → 修改查询并继续搜索
来源冲突 → 寻找原始资料或保留分歧

动笔前先问自己：我手里有真实运行记录，证明固定流程在这里不够吗？如果没有，这个题继续留在候选池。

后续不排期，只保留认知层次

前三篇之后不再依次填框架。下面这些是不同层次的问题池。哪个问题先在实现中出现，哪一篇就先写。

层次一：行为怎样变得可比较

标题方向 核心启发 什么时候值得写
同一句 Prompt，换个模型为什么像换了一个程序？ Prompt 里没写出来的默契会随模型一起变 已有草稿，正在补证据
Prompt 改到第八版，为什么反而不知道哪版最好？ 版本只记录变化，样例与评价才能积累经验 有了至少一个真实回归案例后
Demo 成功了，为什么改一处就坏另一处？ 评测要说明改善了什么、牺牲了什么 手工对比已经无法覆盖线上失败时

层次二：一次调用怎样长成流程

标题方向 核心启发 什么时候值得写
什么时候只需要 Workflow，什么时候才值得交给 Agent？ 确定的步骤写成流程，无法预定的局部才需要 Agent 实际任务已经出现证据不足、动态回退或工具选择
一个例子读懂 LangChain：它到底封装了什么？ 它收起的是模型、工具和消息之间的胶水，不会让模型更聪明 手写工具循环已经影响理解或维护时
流程什么时候需要「走回头路」？ 图的价值是让状态与转移条件可见 已经出现多个分支、循环、暂停或恢复点时
Agent 最后答错了，究竟是哪一步先坏的？ 最终输出只是结果，Trace 才能还原错误路径 流程越过一次调用，普通日志已经无法定位失败时

LangChain、LangGraph 和 Langfuse 只是候选实现。写作时可以使用它们，也可以用更小的手写版本说清问题。

层次三：Agent 怎样管理信息与长任务

标题方向 核心启发 什么时候值得写
资料越多，Agent 为什么反而越容易答错？ Context Engineering 管的是这一步应该看什么，不是能塞进多少 资料与历史消息已经开始互相污染时
Agent 应该记住什么，又该忘掉什么？ Memory 的难点是决定什么值得在未来继续影响判断 重复说明偏好与旧记忆污染开始同时出现时
任务变长后，Agent 为什么越来越容易跑偏？ Plan 是用来比较变化的基准，Skill 是可复用的做事方法 已经出现漏项、重复搜索或长任务目标漂移时
一个 Agent 忙不过来，就该拆成多个吗？ 多 Agent 只适合能够独立推进、最后重新汇合的支线 子任务真的独立，并行能节省时间且汇总格式已经明确时

层次四：Agent 怎样从能跑变成敢用

标题方向 核心启发 什么时候值得写
Agent 做到一半断了，为什么不能从头再来？ Retry 决定再做一次，Checkpoint 决定从哪里继续 任务时间和成本已经高到不能接受整段重跑时
Agent 能写完文章，为什么还不能让它直接发布？ 能做什么与被允许直接做什么是两个问题 工具开始产生真实副作用，需要沙箱、权限或人工确认时
一个可靠 Agent 最后应该留下哪些复杂度？ 没有对应失败的机制不应因为框架提供了就保留 系列已经积累足够失败案例，可以做一次回顾时

每次怎样决定下一篇

一篇发布后，不按原目录自动进入下一节。先问四个问题：

  1. 我在实现或使用中，真的遇到了哪个失败？
  2. 这个失败能不能用一组具体输入和输出展示？
  3. 解决它需要的是一个新机制，还是只是继续改 Prompt？
  4. 这个问题能不能给读者一个可迁移的判断，而不是只介绍某个库？

四个问题都有答案，再把它提升为下一篇。如果只是某个新框架刚好很热，可以单独写工具文，不必强行放进这个系列。

每篇的写作骨架

不要用一套八步法把所有文章写成同一个模子。只要保住下面这条叙事线：

一个已经能跑的版本
→ 在具体输入上失败
→ 最直觉的修法为什么不够
→ 加入一个新机制
→ 同一个输入重新运行
→ 得到什么，又多付出了什么

小标题不要固定。有的文章可以先展示两份输出，有的可以从一次中断或误发开始。叙事线稳定，表面结构不必整齐。

每篇开写前，只填这五项：

暂定标题：
读者能带走的判断：
用来开场的失败：
需要准备的证据或代码：
这篇明确不展开什么：

代码怎样跟着文章长

代码服务于证明，不是系列本身的建筑项目。

当前只需要：

tech-brief-agent/
├── pyproject.toml
├── uv.lock
├── fixtures/
├── prompts/
├── outputs/
└── experiments/

约定：

  • Python 项目统一用 uv 管理。
  • 一开始不建 app/、数据库、完整 Web 界面和十四份代码快照。
  • 每写一篇，只加当篇需要的最小实验、Prompt 和输出。
  • 文章发布后再打 Tag，不为还没有发生的节点预留版本。
  • 如果后来的框架版本与早期示例差异太大，优先让当篇代码可运行，不为了维持一条虚构的演进线而牺牲清晰度。

发布节奏

工程系列不需要连续发完。可以与「被历史遗忘的未来」交替：一篇解决当下工程问题，一篇拉开历史视角。

对外不宣布「十五篇大型系列」，也不在标题里放 N01、N02。读者点开任意一篇，都应该能单独读懂。

前两篇发布后，先停一次，检查：

  • 读者更在意 Prompt 技巧，还是「经验怎样积累」这条主线？
  • 代码与实验是增加了信息，还是让文章变成了工具说明？
  • 第二篇留下的真问题，是 Workflow 与 Agent，还是 Eval、Context 或别的东西？

第三篇从这些答案里选，不从旧目录里选。

如果这七件事还没有做完，暂时不需要规划 LangGraph、Memory 或多 Agent 的文章细节。
