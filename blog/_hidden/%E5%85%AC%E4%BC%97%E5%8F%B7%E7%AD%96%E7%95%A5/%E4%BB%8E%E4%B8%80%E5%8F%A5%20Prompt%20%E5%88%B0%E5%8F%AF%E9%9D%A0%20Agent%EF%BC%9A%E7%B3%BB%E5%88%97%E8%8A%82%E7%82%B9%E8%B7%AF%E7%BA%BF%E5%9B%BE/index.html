从一句 Prompt 到可靠 Agent：系列节点

从一句 Prompt 到可靠 Agent：系列节点

系列角色：知识主干·Agent 系统。 当前活跃主链，负责解释模型之外的系统如何从可运行走向可检查、可恢复、可授权。整体归属与交叉规则见内容系列总图。

系列判断

这个方向足以形成长期系列。它既不是 Agent 术语课程，也不是只讲工程道理的问题文；它追踪一次模型调用如何在真实失败中，逐步长出流程、工具、状态、记忆、恢复和权限边界，并让每一次失败都带出一个可迁移的核心概念或框架。

固定承诺：

每篇先让一个真实失败出现，再由失败逼出一个核心概念或框架：既讲清它为什么需要，也拆开它怎样运转、解决什么、不解决什么。最后留下的不只是一条从不可控到可检查、可恢复、可授权的工程路径，还有一张可以迁移到其他 Agent 系统的概念地图。

读者收益：

  • 普通读者先跟着具体任务和失败进入，不会觉得文章在抽象说教，也能看见 Agent 是模型与外部系统一层层组合的结果。
  • 技术读者能获得稳定的概念坐标，判断什么时候普通函数就够，什么失败真的需要 Workflow、Graph、Memory、Checkpoint 或 Human in the Loop。

系列边界

  • 模型内部的 Attention、残差、MoE 等结构，交给「模型为什么这样设计」。
  • 某个开源仓库的反常实现与取舍，交给「从源码里看懂 AI 工程」；本系列只解释稳定的问题主线。
  • 自然、小说或组织与 Agent 的共同机制，交给「不是比喻」。
  • 框架安装、API 列表和功能横评不属于本系列。框架只在暴露一个问题时才成为案例。

单篇文章必须同时完成两层任务

这个系列表现好的关键，不只是“前一篇留下问题，后一篇继续解决”，而是每篇都同时有两层：

  • 问题层：一个已经能运行的具体系统遇到新的失败，普通读者能看懂“为什么现在非解决不可”。
  • 知识层：用一个核心概念或框架解释失败从哪里来、机制怎样运转，以及它的适用边界。

标准推进方式是：

具体任务已经能跑
↓
出现一个新的真实失败
↓
旧方法为什么解释不了、解决不了
↓
引出一个核心概念或框架
↓
拆成最小组成、运行过程与可观察证据
↓
说明它解决什么、不解决什么、什么时候不必用
↓
暴露下一阶段的问题

这里的“框架”不只指 LangGraph、LangSmith 这样的软件框架，也包括 ReAct、Context Engineering、状态机、幂等、授权边界等概念框架。不是每篇都必须挂一个产品名，但每篇主线文章都必须给读者留下一个清晰、可复用的认知结构。

判断一篇是否成立，可以看两条：

  • 只有“应该少塞资料”“应该加评估”之类结论，没有解释核心对象、组成和边界，容易退化成说教。
  • 只有框架功能和 API，没有先让失败发生，容易退化成文档复述。

  • 《LangGraph 到底解决了什么问题？》已覆盖 State、Graph、暂停与 Checkpoint 的入口。

这是当前最适合继续串的主链。它的优势不只是概念连续：三篇复用同一个天气 Agent，每篇都从上一篇已经成功的系统里找到一个新失败，不需要读者重新学习场景。

它们之所以成立，也不只是案例连续。每篇都让问题落到一个可以带走的框架上：

文章 先出现的问题 带出的核心概念或框架 同时讲清的边界
ReAct 模型知道天气知识，却拿不到实时天气，也不会自主推进 Agent = LLM + Tool + State + Loop 不是所有工具调用都需要 Agent 循环
LangGraph 循环开始分支、暂停、恢复，普通控制流越来越难维护 State + Node + Edge + Checkpoint 简单线性任务不必为了“像 Agent”而上图
Agent 评估 最终答案看似正确，但不知道中间过程是否可靠 Trace → Dataset → Evaluator → Experiment 评估负责暴露失败，不负责自动让模型变好

工程边界支线：一场读书会怎样长出 Loop 与 Graph

  • 《从 Prompt 到 Loop Engineering》是一篇横切全系列的总览，说明 Prompt、Context、Harness 与 Loop 的工程边界如何向外移。
  • 《从 Loop 到 Graph Engineering》已建立分叉、并行、汇合与局部返工的关系。后续 Multi-Agent 篇必须进入任务独立性、上下文隔离、通信成本或共因失效，不再重复“拆成多条支线”。

回看与前置支线

  • 《Prompt 没变，为什么换个模型，行为就变了？》已建立“隐含默契 → 行为协议 → 确定性检查”的入口。「哪些要求交给代码」已被部分覆盖，只有找到更强的边界冲突时才单独成篇。
  • 《Claude Dreaming vs Hermes Skill：帮你入坑 Agent Memory》已经区分了“把经验留为事实”与“把经验固化成做事方法”。后续 Memory 主链不再重新介绍 Semantic / Procedural Memory，而应先说清 Context、State 与 Memory 的不同生命周期，再进入记忆治理。

「一个例子读懂 LangChain 到底封装了什么」暂不作为核心节点。如果只能说明模型、消息与工具怎样连接，ReAct 与已有框架文章已经足够；只有找到一个“抽象层隐藏了哪种失败或代价”的新问题时，才恢复为独立篇。

当前阶段与下一批文章

第一阶段“让 Agent 跑起来，并知道它有没有做对”已基本完成。现在应顺着天气 Agent 主链，进入第二阶段“让 Agent 在长任务里不被信息淹没、不忘记目标”。

主链第一篇

资料越多，Agent 为什么反而越容易答错？

继续使用天气 Agent：它现在已经会调工具、保存状态、暂停恢复，也能被评估。新失败是，对话、多次天气查询、工具回包、用户偏好和风险规则全部进入上下文后，它开始引用旧城市、旧日期或无关规则。

这篇真正要讲清：

  • Prompt 是要求，Context 是这一步实际看到的全部信息。
  • Context Window 是容量上限，Context Engineering 是信息选择。
  • State 保存任务已经确定的事，不等于把全部聊天历史都塞回模型。
  • 更多信息会同时增加成本、延迟与干扰；关键不是删得越多，而是这一步只看当前需要的东西。

它的核心概念落点是 Context Engineering。文章不能只得到“资料不是越多越好”这个结论，还要给出一张最小框架：Prompt、当前状态、历史消息、工具结果和检索材料分别是什么，它们如何被选择、压缩、隔离和淘汰，以及 Context 与 State、Memory 的边界在哪里。

后续主链

  1. 任务变长后，Agent 为什么越来越容易跑偏？

    从信息选择进入目标保真：长任务不只要减少上下文，还要在对话之外保存目标、当前计划、证据、预算和停止条件。核心概念落点是长任务控制面：Goal → Plan → Evidence → Gate / Stop。

  2. 上下文窗口越来越长，Agent 为什么还需要 Memory？

    区分当前推理的 Context、任务执行的 State 与跨任务保留的 Memory。核心概念落点是 Context / State / Memory / Skill 四类对象及其生命周期；文末接入已有 Dreaming / Skill 文章，不重复讲记忆类型。

  3. 工具已经执行成功，Agent 为什么不能放心重试？

    从一个已经发送成功、但响应丢失的真实动作进入 Retry、Checkpoint 与 Idempotency。核心概念落点是失败恢复框架，以及“重算”和“重复执行副作用”的区别；避免重复 LangGraph 中已经讲过的“从哪里恢复”。

  4. Agent 能写完文章，为什么还不能让它直接发布？

    从真实副作用进入身份、最小权限、可撤销委托、人工确认与审计。核心概念落点是 Capability / Identity / Authorization / Approval / Audit。

穿插篇

Prompt 写得越长，为什么不一定越可靠？ 仍然值得写，但不紧接在当前工程主链后面。它适合在两篇长任务文章之后作为低门槛回看篇，从单条规则推进到规则冲突、优先级和指令边界。

发布节奏

现有反馈说明，读者愿意跟随一个具体 Agent 连续撞上新问题。后续保持以下节奏：

  1. 两至三篇连续主链：复用同一案例，每篇完成“一个新失败 + 一个核心概念或框架”，并在结尾明确暴露下一篇的问题。
  2. 一篇低门槛回看或旁证：用 Prompt、经典软件或开源仓库重新照亮主线，但不另起一套概念目录。
  3. 再回主链：穿插篇不连续超过一篇，避免读者失去“这个 Agent 接下来还会遇到什么”的期待。

发布顺序不追求把概念补齐。一篇只有在上一篇的系统里发生了新失败，并且这个失败值得带出一个可复用的认知结构，才继续占据主链。
