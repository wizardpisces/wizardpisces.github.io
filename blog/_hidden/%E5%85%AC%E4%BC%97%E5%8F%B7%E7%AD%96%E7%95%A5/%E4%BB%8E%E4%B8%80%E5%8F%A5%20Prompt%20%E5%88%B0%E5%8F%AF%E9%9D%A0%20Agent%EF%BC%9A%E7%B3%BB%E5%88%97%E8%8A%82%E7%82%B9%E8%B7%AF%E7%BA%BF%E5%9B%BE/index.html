从一句 Prompt 到可靠 Agent：系列节点

这张表只记录从 Prompt 走向 Agent 时可能遇到的问题。

它有一条大致的认知线，但没有固定顺序。实际先撞上哪个问题，就可以先从哪里写。技术名词只是落点，不代表文章必须使用某个框架。

序号 话题引子（标题方向） 可以碰到的启发 概念落点
1 [Prompt 没变，为什么换个模型，行为就变了？](…/…/tech/ai-好问题/模型一换，Prompt 为什么会失效？从隐含默契到行为协议.md) Prompt 里有大量没有写出来的默契，模型变化会让这些默契失效 行为协议
2 Prompt 写得越长，为什么不一定越可靠？ 增加要求不等于减少歧义，规则之间还可能互相冲突 指令边界
3 哪些要求应该写进 Prompt，哪些应该交给代码？ 能被确定检查的事情，没有必要继续依赖模型自觉 确定性代码
4 Prompt 改到第八版，为什么反而不知道哪版最好？ 只有固定样例和判断标准，版本变化才有积累 Prompt 版本与回归
5 Demo 明明成功了，为什么换个输入就坏了？ 一次成功只能说明样例能跑，不能说明行为稳定 Eval
6 一次模型调用，什么时候应该拆成 Workflow？ 搜索、判断和写作混在一起时，一个修改很容易伤到其他能力 Workflow
7 什么时候只需要 Workflow，什么时候才值得交给 Agent？ 确定的步骤适合写死，无法提前知道下一步的局部问题才需要 Agent Agent 决策循环
8 模型会回答问题，为什么还需要工具？ 会说不等于能查、能算、能执行，工具把语言连接到外部世界 Tool Calling
9 一个例子读懂 LangChain：它到底封装了什么？ 框架处理的是模型、消息和工具之间的连接，不会让模型自动变聪明 Agent 框架
10 流程什么时候需要「走回头路」？ 出现分支、循环和暂停以后，状态怎么变化比步骤列表更重要 Graph / State
11 Agent 最后答错了，究竟是哪一步先坏的？ 最终答案只留下结果，执行轨迹才能还原错误路径 Trace / Observability
12 资料越多，Agent 为什么反而越容易答错？ Context Engineering 关心的是这一步该看什么，不是最多能塞多少 Context Engineering
13 Agent 应该记住什么，又该忘掉什么？ 记忆的难点是决定哪些旧信息应该继续影响未来 Memory
14 任务变长后，Agent 为什么越来越容易跑偏？ 长任务需要一个可以反复对照的目标，也需要可复用的做事方法 Plan / Skill
15 一个 Agent 忙不过来，就应该拆成多个吗？ 多 Agent 适合可以独立推进、最后再合并的任务，不是角色越多越智能 Multi-Agent
16 Agent 做到一半断了，为什么不能从头再来？ 重试解决再做一次，检查点解决从哪里继续 Retry / Checkpoint
17 Agent 能写完文章，为什么还不能让它直接发布？ 能力和授权是两件事，真实副作用需要权限边界和人工确认 Guardrails / Human in the Loop
18 一个可靠 Agent 最后应该留下多少复杂度？ 每一个机制都该对应一个已经发生的失败，框架提供的能力不必全用 可靠性与复杂度

可以把整条线暂时理解成：Prompt 先变成可检查的行为，单次调用再长出流程、工具和状态，最后才面对记忆、恢复、权限这些长期运行问题。它是方向感，不是文章目录。
