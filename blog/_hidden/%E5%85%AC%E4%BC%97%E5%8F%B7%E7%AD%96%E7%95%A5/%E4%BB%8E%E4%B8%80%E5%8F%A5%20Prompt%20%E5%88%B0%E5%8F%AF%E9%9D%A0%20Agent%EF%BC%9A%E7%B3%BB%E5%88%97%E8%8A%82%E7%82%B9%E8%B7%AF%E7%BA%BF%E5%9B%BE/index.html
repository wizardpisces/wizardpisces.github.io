从一句 Prompt 到可靠 Agent：系列节点

系列角色：知识主干·Agent 系统。 当前活跃主链，负责解释模型之外的系统如何从可运行走向可检查、可恢复、可授权。整体归属与交叉规则见内容系列总图。

系列判断

这个方向足以形成长期系列。它既不是 Agent 术语课程，也不是只讲工程道理的问题文；它追踪一次模型调用如何在真实失败中，逐步长出流程、工具、状态、记忆、恢复和权限边界，并让每一次失败都带出一个可迁移的核心概念或框架。

固定承诺：

每篇先让一个真实失败出现，再由失败逼出一个核心概念或框架：既讲清它为什么需要，也拆开它怎样运转、解决什么、不解决什么。最后留下的不只是一条从不可控到可检查、可恢复、可授权的工程路径，还有一张可以迁移到其他 Agent 系统的概念地图。

读者收益：

  • 普通读者先跟着具体任务和失败进入，不会觉得文章在抽象说教，也能看见 Agent 是模型与外部系统一层层组合的结果。
  • 技术读者能获得稳定的概念坐标，判断什么时候普通函数就够，什么失败真的需要 Workflow、Graph、Memory、Checkpoint 或 Human in the Loop。

系列边界

  • 模型内部的 Attention、残差、MoE 等结构，交给「模型为什么这样设计」。
  • 某个开源仓库的反常实现与取舍，交给「从源码里看懂 AI 工程」；本系列只解释稳定的问题主线。
  • 自然、小说或组织与 Agent 的共同机制，交给「不是比喻」。
  • 框架安装、API 列表和功能横评不属于本系列。框架只在暴露一个问题时才成为案例。

单篇文章必须同时完成两层任务

这个系列表现好的关键，不只是“前一篇留下问题，后一篇继续解决”，而是每篇都同时有两层：

  • 问题层：一个已经能运行的具体系统遇到新的失败，普通读者能看懂“为什么现在非解决不可”。
  • 知识层：用一个核心概念或框架解释失败从哪里来、机制怎样运转，以及它的适用边界。

标准推进方式是：

具体任务已经能跑
↓
出现一个新的真实失败
↓
旧方法为什么解释不了、解决不了
↓
引出一个核心概念或框架
↓
拆成最小组成、运行过程与可观察证据
↓
说明它解决什么、不解决什么、什么时候不必用
↓
暴露下一阶段的问题

这里的“框架”不只指 LangGraph、LangSmith 这样的软件框架，也包括 ReAct、Context Engineering、状态机、幂等、授权边界等概念框架。不是每篇都必须挂一个产品名，但每篇主线文章都必须给读者留下一个清晰、可复用的认知结构。

判断一篇是否成立，可以看两条：

  • 只有“应该少塞资料”“应该加评估”之类结论，没有解释核心对象、组成和边界，容易退化成说教。
  • 只有框架功能和 API，没有先让失败发生，容易退化成文档复述。

  • 《LangGraph 到底解决了什么问题？》已覆盖 State、Graph、暂停与 Checkpoint 的入口。

  • 《Agent 为什么会“记错”？问题可能出在它看到的世界》已用北京、上海两份天气同时进入回答上下文的错误，区分 State 与 Context，并建立“每一步只让模型看见当前需要的信息”的 Context Engineering 入口。原计划的《资料越多，Agent 为什么反而越容易答错？》已被这篇覆盖，不再单独成篇。

这是当前最适合继续串的主链。它的优势不只是概念连续：四篇复用同一个天气 Agent，每篇都从上一篇已经成功的系统里找到一个新失败，不需要读者重新学习场景。

它们之所以成立，也不只是案例连续。每篇都让问题落到一个可以带走的框架上：

文章 先出现的问题 带出的核心概念或框架 同时讲清的边界
ReAct 模型知道天气知识，却拿不到实时天气，也不会自主推进 Agent = LLM + Tool + State + Loop 不是所有工具调用都需要 Agent 循环
LangGraph 循环开始分支、暂停、恢复，普通控制流越来越难维护 State + Node + Edge + Checkpoint 简单线性任务不必为了“像 Agent”而上图
Agent 评估 最终答案看似正确，但不知道中间过程是否可靠 Trace → Dataset → Evaluator → Experiment 评估负责暴露失败，不负责自动让模型变好
Context Engineering 工具已经查到上海晴，最终回答却继续引用北京小雨 State → 选择 / 压缩 / 隔离 → Context 保存完整历史不等于每次都把全部历史交给模型

工程边界支线：一场读书会怎样长出 Loop 与 Graph

  • 《从 Prompt 到 Loop Engineering》是一篇横切全系列的总览，说明 Prompt、Context、Harness 与 Loop 的工程边界如何向外移。
  • 《从 Loop 到 Graph Engineering》已建立分叉、并行、汇合与局部返工的关系。后续 Multi-Agent 篇必须进入任务独立性、上下文隔离、通信成本或共因失效，不再重复“拆成多条支线”。

回看与前置支线

  • 《Prompt 没变，为什么换个模型，行为就变了？》已建立“隐含默契 → 行为协议 → 确定性检查”的入口。「哪些要求交给代码」已被部分覆盖，只有找到更强的边界冲突时才单独成篇。
  • 《Claude Dreaming vs Hermes Skill：帮你入坑 Agent Memory》已经区分了“把经验留为事实”与“把经验固化成做事方法”。后续 Memory 主链不再重新介绍 Semantic / Procedural Memory，而应先说清 Context、State 与 Memory 的不同生命周期，再进入记忆治理。

「一个例子读懂 LangChain 到底封装了什么」暂不作为核心节点。如果只能说明模型、消息与工具怎样连接，ReAct 与已有框架文章已经足够；只有找到一个“抽象层隐藏了哪种失败或代价”的新问题时，才恢复为独立篇。

当前阶段与下一批文章

第一阶段“让 Agent 跑起来，并知道它有没有做对”已基本完成。现在应顺着天气 Agent 主链，进入第二阶段“让 Agent 在长任务里不被信息淹没、不忘记目标”。

主链第一篇：已完成

Agent 为什么会“记错”？问题可能出在它看到的世界

继续使用天气 Agent：它现在已经会调工具、保存状态、暂停恢复，也能被评估。新失败是，对话、多次天气查询、工具回包、用户偏好和风险规则全部进入上下文后，它开始引用旧城市、旧日期或无关规则。

这篇已经讲清：

  • Prompt 是要求，Context 是这一步实际看到的全部信息。
  • Context Window 是容量上限，Context Engineering 是信息选择。
  • State 保存任务已经确定的事，不等于把全部聊天历史都塞回模型。
  • 更多信息会同时增加成本、延迟与干扰；关键不是删得越多，而是这一步只看当前需要的东西。

它的核心概念落点是 Context Engineering。文章已经用 State、Context 与 Memory 的数据流说明：系统可以保存完整事实，但每次模型调用只装入当前任务所需的视图。

后续主链

  1. Agent 为什么会走对每一步，却到达错误的终点？

    从信息选择进入目标保真：长任务不只要减少上下文，还要在对话之外保存目标、当前计划、证据、预算和停止条件。核心概念落点是长任务控制面：Goal → Plan → Evidence → Gate / Stop。

  2. 任务结束后，Agent 应该忘掉什么，又带走什么？（暂缓）

    生命周期边界成立，但当前草稿主要靠概念递进，读者问题和现实收益还不够强。保留素材，不进入近期候选。只有找到一个独立成立的真实失败，例如旧任务状态污染新任务并造成明确代价，再恢复为主链文章。

  3. 工具已经执行成功，Agent 为什么不能放心重试？

    从一个已经发送成功、但响应丢失的真实动作进入 Retry、Checkpoint 与 Idempotency。核心概念落点是失败恢复框架，以及“重算”和“重复执行副作用”的区别；避免重复 LangGraph 中已经讲过的“从哪里恢复”。

  4. Agent 能写完文章，为什么还不能让它直接发布？

    从真实副作用进入身份、最小权限、可撤销委托、人工确认与审计。核心概念落点是 Capability / Identity / Authorization / Approval / Audit。

决策策略短季：Agent 为什么要换一种做决定的方式

这组文章属于可靠 Agent 系列，不建立新的顶级栏目。它不按算法名称介绍 ReAct、MCTS、World Model 或 Reflexion，而是连续追问：

当前 Agent 遇到了什么失败？为了修复它，决策过程必须增加哪一种状态、反馈或搜索结构？它又带来了什么成本？

已有《什么是 ReAct？》负责建立“观察、行动、反馈、再行动”的单路径循环，《Agent 为什么会走对每一步，却到达错误的终点？》负责把 Goal 与 Plan 分开。短季从这两个基础继续向下：

Agent 已经能边做边调整
        ↓
早期方向押错后，后续步骤仍沿错误路径推进
        ↓
MCTS：保留分叉，并用后续结果更新前面的路线价值
        ↓
多条路径怎样评分？
        ├─ 真实工具反馈 / 在线 Evaluator
        └─ 无法真实试错时，用 World Model 预测结果
        ↓
一次搜索结束后，失败经验怎样影响下一次任务？
        ↓
Reflexion + Episodic Memory

首批节点：

文章 先出现的失败 增加的设计 主要代价
Agent 修 Bug 时，为什么不能想到一个原因就一路查下去？ 第一个解释被过早当成唯一方向 分支状态、探索与利用、价值回传 Token、工具调用和状态隔离成本
Agent 同时找到三条路，凭什么知道哪条更值得继续？ 路径变多以后，模型自评无法稳定排序 在线 Value、规则检查与外部反馈 评价偏差可能把搜索带向错误分支
Agent 不可能把每条路都真的走一遍，怎么提前判断后果？ 真实环境无法承受每条路径都执行一遍 动作条件预测与模型预测控制 模型误差会随推演距离累积
Agent 已经失败过一次，为什么下次还会犯同样的错？ 失败只留下一段文字，没有进入下一次决策 反馈、反思与情景记忆 错误经验可能被反复放大

其中 Value / Evaluator 与已有 LangSmith 文章不重复：LangSmith 篇讨论离线比较一次 Agent 运行是否可靠，这里讨论搜索进行中怎样给当前节点估值。Reflexion 也不重新介绍 Memory 分类，只解释失败反馈怎样进入下一次尝试。

这个短季的边界是决策方式。Workflow、权限、重试、幂等和多 Agent 仍留在可靠 Agent 的其他节点；模型内部怎样实现预测，交给模型架构系列。

后续还有几类高级策略，但暂不塞进首批：

标题方向 解决的失败 策略落点 暂不进入首批的原因
计划写得越完整，Agent 为什么越容易做到一半就作废？ 长任务开始前生成的完整计划，无法吸收中途出现的新信息 分层规划、Plan-and-Execute、动态重规划 需避开《走对每一步却到达错误终点》中已经讲过的 Goal / Plan 边界
任务越简单，为什么 Agent 反而不该想太久？ 所有任务都使用搜索、反思和强模型，成本迅速失控 Router、Adaptive Compute、按不确定性分配预算 需要真实成本数据或对照实验，不能只讲“简单任务用小模型”
三个 Agent 都同意，答案为什么还是可能错？ 多个角色共享模型、上下文和错误前提，投票形成虚假共识 Multi-Agent Debate、异质性与共因失效 主归属仍是 Multi-Agent 节点，不与决策短季连续发布
Prompt 和工作流都调不动了，Agent 还能怎么继续变好？ 手工规则无法覆盖大量细粒度决策 轨迹反馈、Agent RL、策略训练 需要找到普通读者能观察到的训练前后差异
让 Agent 自己改工作流，为什么可能越改越差？ 自动生成的新流程在少量样例上变好，却破坏其他任务 Automated Agent Design、搜索与回归评估 只有拿到可复现案例后才成篇

这些策略不是同一层的算法替代关系。分层规划改变任务怎样拆，MCTS 改变路径怎样搜索，Evaluator 决定怎样评分，World Model 提供环境预测，Reflexion 与 RL 决定经验怎样改变未来行为，多 Agent 改变任务由谁完成。文章仍按失败归类，不做“高级 Agent 算法大全”。

决策模型短季：把“生成答案”和“做判断”拆开

这组文章属于本系列的工程支线，不建立新的顶级栏目。它承接 ReAct、评估和工具调用，但不重复 Agent 的路径搜索。固定追问是：

当一个模型已经能生成答案时，为什么系统还要另外训练或部署模型，专门负责分类、排序、评分、验证、安全判断和路由？

每篇都要从一个可观察的失败进入，区分“提出候选”和“判断候选”，并说明判断结果进入训练、评估还是运行时控制。读者最后应能判断：什么时候该用生成模型，什么时候应该把决定交给更小、更专门的模型或确定性代码。

问题递进：

AI 会写答案
    ↓
但不知道哪个答案更好
    ↓
Reward / Preference / Judge：给候选结果评分
    ↓
生成结果看似合理
    ↓
Verifier / Safety Classifier：决定能否继续传播或执行
    ↓
候选结果太多
    ↓
Reranker：重新判断哪个最适合当前任务
    ↓
用户意图不明确
    ↓
Intent Classifier / Router：决定由谁、用什么能力处理
    ↓
系统开始直接消费判断结果
    ↓
Decision Model：不再把“决定”伪装成一段聊天

首批节点：

标题方向 进入现象 认知落点 与相邻内容的边界
一种 AI 负责生成，另一种负责决定：Jev 想验证什么？ 生成结果很多，但系统仍要筛选、拒绝或转交 生成模型与判断模型的职责边界 不重复“模型为什么需要工具”
Jev 为什么比通用大模型快？它到底砍掉了什么？ Jev 不再把每个判断翻译成长文本 从 Prefill、Decode、Hidden States 和有限候选解释 Jev 的速度来源与能力取舍 不把“零幻觉”写成“永远正确”；区分格式约束、语义判断和 Calibration
同样是“打分”，Reward Model 和 Judge Model 到底差在哪？ 一个分数既能训练模型，也能评估模型 训练信号、离线评估、运行时控制的区别 不重复 LangSmith 的运行追踪
AI 说自己做对了，为什么还要 Verifier 再检查一遍？ 模型给出完整答案，却无法证明满足约束 生成是提案，验证是放行条件 不把 Verifier 泛化成“更聪明的模型”
搜索找到了很多资料，为什么还要 Reranker？ 召回结果相关，却不一定能回答当前问题 语义相似与任务相关不是同一个排序标准 不重复 RAG 的检索流程
用户只说了一句话，AI 怎么决定该交给谁？ 同一句话可能进入不同工具、模型或人工流程 意图分类与路由是系统入口，不是回答本身 不重复 Tool Routing 的 Agent 运行时决策
为什么安全判断不能只交给回答问题的那个模型？ 执行者同时充当自己的监管者 独立判断、拒绝和权限边界 不替代 Harness 沙箱与授权篇
AI 为什么开始不再生成文字，只返回一个决定？ 决策结果需要被程序直接消费 Decision Model 把选择、评分和路由结构化 作为 Jev 等近期案例的新闻入口

这些名词不能互相替代：它们的输入、输出、训练目标和介入时机不同。只有当某个名词能带出独立的失败现场和新的系统边界时，才单独成篇；否则合并到共同问题中。

多 Agent 协作短季：当一个 Agent 变成一个组织

这组文章属于可靠 Agent 系列，不新增顶级栏目。它不按 CrewAI、OpenAI Agents SDK、Google ADK、Microsoft Agent Framework 或 A2A 逐个介绍，而是追问：

为什么要把一个 Agent 拆成多个，什么时候值得拆；拆开以后，怎样组织、通信和裁决，才能让收益超过协调成本？

它与已发布的《从 Loop 到 Graph：一个例子看懂多 Agent 怎么协作》连续，但不重复。Graph 篇已经解释任务如何分叉、并行、汇合和局部返工；这个短季负责做选择：哪些节点值得升级为独立 Agent，应该采用哪种组织和通信方式，何时普通工作流反而更好。

每篇都必须落到同一组判断：

它解决什么失败？
什么条件下值得使用？
收益来自哪里？
新增了什么成本和风险？
更简单的方案什么时候已经够用？

首季按“代价出现 → 决策边界 → 组织方式 → 结果契约 → 集体决策”推进：

Agent 增加后，任务为什么没有按比例变快？
        ↓
工作流节点什么时候才拥有独立决策边界？
        ↓
多个 Agent 由谁分工和调度？
        ↓
它们之间应该交付什么结果、共享什么状态？
        ↓
出现分歧时，投票、验证和裁决分别解决什么？

首季保留五个节点：

顺序 文章入口 本篇新增的认知结构 不进入本篇的内容
1 为什么 Agent 变多了，事情反而更慢？ 比较并行、专业化和隔离收益，以及共享前提、合并、返工带来的协调税；回答为什么需要、什么时候不该拆 不展开具体怎样分工
2 同样是五个步骤，为什么有时叫工作流，有时叫五个 Agent？ 拆的不是任务，而是独立决策边界；用目标、上下文、工具、状态、成功标准和任务生命周期区分 Tool、Node 与 Agent 不做框架术语横评，也不讨论谁来指挥
3 五个 Agent 一起干活，谁来决定下一步？ 对比固定编排、主—子 Agent、平级交接与动态分派；按任务是否已知、决策权是否集中选择组织方式 不深入消息格式；可用多个子 Agent 重复搜索作为分工失败案例
4 Agent 之间说得越多，为什么反而越容易把事情说乱？ Agent 通信的最小单位不是对话，而是可消费的结果契约；再比较直接消息、共享状态、事件与持久交付物 不讨论多数投票；“接手后失忆”并入本篇作为交接失败入口
5 三个 Agent 都同意，答案为什么还是可能错？ 判断独立性、共因失效、投票、外部验证与最终裁决 不把更多角色默认当成更多独立证据

五篇的递进关系不能退化成概念目录：第一篇先完成“要不要拆”的判断；第二篇决定“拆的是不是独立决策边界”；第三篇选择组织和调度方式；第四篇把通信从“聊天”推进到“结果契约”；第五篇处理通信后仍存在的意见冲突。

“两个 Agent 跨系统协作时为什么需要协议？”退出首季。A2A 涉及能力发现、异步任务、身份与授权，当前案例无法用一条足够简洁的因果链自然承载。只有找到新的真实现场时再恢复，不为了把关系推到系统边界之外强行收束。

现有第一篇草稿保留，但要删去已经进入具体分工方法的段落，让它只回答“是否该拆”。原“重复搜索”草稿已经移除；第三篇可以重新使用多个子 Agent 搜到相同结果的失败现场，解释拆开后怎样组织。

第二季再进入分布式系统式的问题：故障归因、共享状态、并发冲突、异步任务与失败恢复。比如“两个 Agent 同时改同一件事，谁说了算？”只有当 Agent 已拥有独立生命周期和可相互影响的状态时才成立，不提前塞进首季。TraceElephant 等研究资料先作为证据储备，等出现足够低门槛的失败现场再成篇。

这个短季不写三类内容：框架功能横评、角色模板合集、默认宣称多 Agent 优于单 Agent。产品和协议只在它们能够证明某个组织边界时进入正文。

Skill 小专题：Agent 为什么没有用上你写的能力

这是一组隶属于可靠 Agent 系列的三篇小专题，不建立新的顶级系列。固定承诺是：不写 Skill Creator 操作手册，而是从一次可复现的失败进入，解释 Skill 怎样被发现、加载和验证。

  1. 写 Skill 的 Skill，怎么知道自己写对了？

    从一个递归对象进入：用官方 skill-creator 创建 interview Skill。quick_validate.py 返回有效，只能证明这份能力包可以被系统接受。接着让同一个 Skill 面对典型请求、相邻请求、证据不足和敏感信息，依次暴露“会不会触发”“有没有改善”“代价是否值得”三层问题。OpenAI 与 Anthropic 的官方 creator 分别解释设计完整性与行为验证。核心落点是 可装载 → 可路由 → 有增量 → 可维护。

  2. 为什么你的 Skill 写得很完整，Agent 却根本不会用？

    用两个正文相近、description 不同的 Skill 做对照实验。Agent 在读取完整 SKILL.md 之前，先依据名称与 description 判断是否需要加载；因此 description 不是简介，而是能力路由接口。核心落点是 发现 → 选择 → 加载。

  3. Skill 不是更长的 Prompt：为什么说明、资料和脚本必须分开？

    从一个不断膨胀的 Skill 入手，解释渐进式披露：入口只保留稳定规则，条件知识进入 references，确定性操作进入 scripts。核心落点是“何时加载什么”，而不是文件夹规范。

AI 怎么接手我们的软件？Computer Use 机制篇

已成稿：AI 操作电脑时，它看到的真是我们看到的界面吗？。

原来的四篇接口拆分取消。第一篇已经用同一次订单导出贯穿无障碍语义、截图操作与 CLI/GUI 的层次关系，完整回答“Agent 实际看见什么、通过哪一层接口行动”。API、CLI、无障碍树和像素不再分别成篇。

独立增量：无障碍信息把部分视觉识别变成结构读取；Agent 看到的不是唯一的“软件界面”，而是系统选择暴露给它的那层表示；GUI 的长期价值是为没有机器接口的软件提供兼容入口。

证据以 Microsoft Playwright MCP/CLI 与 Apple AXUIElement 官方说明为主，不从无障碍权限弹窗推断具体产品读取了控件树，也不声称 Computer Use 都依赖无障碍接口。

这篇暴露了一个尚未回答的新问题：界面显示动作已经执行，不等于业务目标已经完成。因此该方向可以继续，但只作为「从一句 Prompt 到可靠 Agent」下的短专题，不建立新的顶级系列。

候选节点：

  1. AI 明明点了“提交”，为什么任务还不算完成？

    用订单导出、表单提交或邮件发送中的“按钮已点击，业务却未完成”进入。区分动作被执行、系统接受请求、后台状态改变和目标得到验证。核心判断是：可靠 Agent 的终点不是最后一次点击，而是外部世界出现了可验证的新状态。这个问题由第一篇自然暴露，又能让陌生读者独立进入，作为首选下一篇。

  2. Codex 明明能运行终端，为什么还要内置改文件、搜索和看图工具？

    从“一个万能 Shell 理论上什么都能做”与“成熟 Agent 反而拥有许多窄工具”的反差进入。窄工具的价值不只是方便，而是缩小动作空间、约束输入输出、减少无关信息，并让授权与审计落到具体动作。读者带走的判断是：给 Agent 工具，不只是增加能力，也是在设计它能怎样犯错。

  3. AI 能操作整台电脑，为什么反而不该给它一只万能鼠标？

    从能力最通用、权限却最难收紧的冲突进入，解释对象级授权、危险动作确认和最小权限。只有找到区别于 Harness 沙箱漏洞篇的真实产品现场与证据时才成篇；否则并入第二篇，不为凑数量单独发布。

短专题的递进是：看见哪一层 → 动作是否真的完成 → 能力怎样被限制。这不是接口名词课程；此前的“按钮为何找不到”“CLI 是否过时”“与录制脚本有何不同”都已被第一篇覆盖，不再成篇。每完成一篇都重新判断下一问题是否仍有独立增量，不承诺连续发布三篇。

Agent 的工具箱：其余候选储备

这是一组隶属于可靠 Agent 系列的产品入口篇，不建立 WorkBuddy 或 Codex 产品系列。固定承诺是：从普通用户看得见的“AI 会装能力、会调用工具”进入，解释模型、Tool、Skill、MCP 与运行环境分别补上了什么。WorkBuddy 提供大众入口，Codex 提供可以观察和验证的工程现场；不使用 WorkBuddy 标题把正文偷换成 Codex 功能介绍。

首批节点：

  1. WorkBuddy 都能自己装 Skill 了，AI 是真的学会新本事了吗？

    从安装前后模型没有重新训练这个反差进入。Skill 增加的是可发现的方法、资料与脚本，不直接改变模型参数；能力是否真正出现，还取决于触发、工具权限、运行环境与结果验证。与“写 Skill 的 Skill”不重复：旧篇检查作者怎样写对 Skill，本篇回答用户安装 Skill 后，系统究竟多了什么。

  2. 同样是让 AI 做事，Tool、Skill 和 MCP 为什么不能合成一个？

    从“安装一个 Skill 后，AI 到底多了什么”继续追问：Tool 是一次可执行动作，Skill 是选择与组合动作的方法，MCP 负责跨系统发现和调用工具。只讲三者在一次任务中的接力，不做术语百科。

  3. 装了几十个 Skill，AI 为什么偏偏想不起该用哪个？

    从能力已经安装却没有触发进入发现与路由：名称和 description 先参与选择，完整说明通常后加载；能力越多也会增加相似候选、上下文和误选成本。接续已有 Skill 路由篇，但将单个 Skill 的写法推进到整个能力市场的选择问题。

  4. AI 能自己创建 Skill，为什么不能让它想装什么就装什么？

    从 WorkBuddy 的查找、创建与安装能力进入供应链、脚本权限、第三方数据流向和错误经验固化。核心落点是 Agent 扩展自己的动作空间时，创建、审核、授权、试运行和正式启用必须分开。

这组内容按问题成熟度发布，不要求连续。WorkBuddy 适合周二的产品现象入口，Codex 的工具机制与接口取舍适合周四；同一篇只能选择一个主现场，另一产品只在确实能验证共同机制时出现。

穿插篇

Prompt 写得越长，为什么不一定越可靠？ 仍然值得写，但不紧接在当前工程主链后面。它适合在两篇长任务文章之后作为低门槛回看篇，从单条规则推进到规则冲突、优先级和指令边界。

发布节奏

发布不再按周二、周四划分文章类型，也不为系列预留固定槽位。每次从已有稿件和候选中选择当前最值得发的一篇。

  1. 问题足够强才继续：复用同一案例时，每篇仍需完成“一个新失败 + 一个核心概念或框架”；下一问题不能独立成立，就暂停系列。
  2. 连续两篇后重新比较：第三篇与 Skill、模型架构、源码和其他强选题重新比较读者收益，不因系列尚未讲完自动获得优先级。
  3. 逻辑顺序不等于发布时间：路线图只负责检查认知依赖。出现更成熟、更有读者关系的文章时，可以随时穿插。

发布顺序不追求把概念补齐。一篇只有在已有系统里发生了新的失败，并且这个失败值得带出可复用的认知结构，才继续推进主链。
