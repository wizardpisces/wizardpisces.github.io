为什么需要这张图

系列不是互斥的文件夹，而是对读者的连续承诺。一篇文章可能同时涉及模型、Agent、源码和历史，但必须有一个主问题；否则既无法判断它应接在哪条线上，也容易用多个角度重复同一个结论。

当前内容体系采用“三条知识主干 + 两种横向视角”：

模型内部怎样计算
        ↓
模型怎样被组织成可靠 Agent
        ↓
软件基础设施怎样托住模型与 Agent

时间视角：这些技术为什么在当时形成、今天还留下什么
外部视角：自然、小说与组织中的关系怎样照亮同一机制

三条主干负责连续建立知识；两种视角负责从时间和其他系统重新检查这些知识。它们可以交叉，但不平铺成五个互相争抢文章的分类。

三条知识主干

系列 反复打开的对象 固定追问 不可替代的认知落点
模型为什么这样设计 模型内部的结构与计算路径 这个结构当初在修复什么失败，又把代价移到哪里？ 最小机制模型
从一句 Prompt 到可靠 Agent 模型之外的 Agent 系统 系统遇到什么真实失败，才需要增加这一层机制？ 从可运行到可检查、可恢复、可授权的工程地图
从源码里看懂 AI 工程 AI 软件框架与工程实现 这层看似多余的设计为什么不能删？ 可由源码证据支持的工程决策模型

三条主干不是同时开课。任何阶段只选择一条作为主要储备方向。可靠 Agent 主线在 2026 年 8 月 27 日的 Goal / Plan 篇后暂停连续推进；2026 年 9 月 3 日用一篇 Skill 小专题完成过渡，9 月 10 日起将“模型为什么这样设计”切换为周四活跃主线。主链表示问题之间存在关系，不等于按课程目录连续发布；下一节点缺少独立读者问题时仍然暂缓。

两种横向视角

系列 观察方式 何时值得独立成篇 认知落点
技术为什么会变成今天这样 沿时间还原能力、成本、生态、习惯与制度 历史条件会改变我们对当下技术的判断 条件、约束与路径依赖框架
不是比喻 对齐两套系统的角色、资源、协调、约束与失效方式 外部结构能推出 AI 系统里原来看不见的新判断 关系诊断框架及映射断点

横向视角不负责补齐一门课，适合低频精品。若历史或类比只是帮助表达，不改变核心判断，就不改变文章的主归属。

四个内容维度不是系列

“黑箱、对齐、工程、变局”回答一篇文章主要让读者看见什么，属于内容维度或标签；五个系列回答文章如何连续生长，属于读者合同。两者不能互相替代。

一篇文章可以是：

主系列：从源码里看懂 AI 工程
主维度：工程
交叉关系：模型架构

但不能同时拥有两个主系列。

关键名词怎样进入系列

系列可以专门解释 OpenTelemetry、OTLP、Trace Endpoint 这类关键名词，但不单独维护术语表，也不从“这个词很常见”倒推一篇文章。

每个名词必须由一个具体问题逼出来：

先出现一个看得见的反常结果
        ↓
让同一个对象完整运行一次
        ↓
缺少这个名词就无法解释下一步
        ↓
说明它在流程中的职责、边界与替代关系

一篇通常只带出 3—5 个互相组成机制的名词。标题优先写读者能看懂的现象，不把多个缩写并列在标题里。读完后，读者应能用这些名词解释另一个系统，而不只是复述定义。

关键名词密度较高、依赖开发背景或前置上下文的文章，默认进入博客的 ai-工程拆解 目录，不进入公众号发布计划。只有能够在不依赖旧文的情况下，从一个普通读者可理解的现象进入，并把必要概念压缩到少量角色时，才重新改写为公众号稿。博客负责保存完整技术链，公众号负责证明一个更低门槛、可迁移的判断。

单篇归属规则

先写出文章准备证明的最终判断，再问哪一种证据不可替代：

模型内部的信息、梯度或参数路径不可替代
→ 模型架构

同一个 Agent 连续出现的工程失败不可替代
→ 可靠 Agent

源码、测试、Issue、RFC 或提交历史不可替代
→ 源码解剖

同期材料、产品条件和时间变化不可替代
→ 技术历史

两套系统的关系映射及映射断点不可替代
→ 不是比喻

冲突时不按标题里的专有名词归类，而按文章最终留下的认知结构归类：

选题 主归属 可交叉链接 分界理由
残差连接为什么有效？ 模型架构 源码 不读某个仓库也能解释核心机制
PyTorch 怎样实现 Autograd？ 源码 模型架构 重点是框架怎样记录并执行梯度依赖
PyTorch 为什么从 Eager 又走向编译？ 视证据决定源码或历史 另一方 实现机制是主角则归源码；时代条件与生态转向是主角则归历史
Agent 到底应该记住什么？ 可靠 Agent 源码 重点是 Context、State、Memory 与 Skill 的系统边界
某个 Memory 仓库为什么拆出四种资产？ 源码 可靠 Agent 没有该仓库的实现证据，文章就不成立
免疫系统怎样启发 Agent 记忆治理？ 不是比喻 可靠 Agent 只有关系映射能推出新判断时才独立成篇

是否新建系列

新方向先尝试以下归宿：

现有系列中的一个节点
→ 某条主干的一季或支线
→ 两三篇小专题
→ 独立单篇
→ 最后才是新系列

只有现有五个合同都无法容纳，并且同时满足稳定承诺、三个强节点、自然递进和清晰边界，才增加顶级系列。某个新框架、热门项目、叙事手法或证据来源本身，不构成新系列。

发布节奏

  1. 周二负责从热点、广角和日常现象建立读者入口，先回答“这件事为什么与我有关”，再留下一个可迁移的判断。
  2. 周四负责 Agent、技术机制与模型架构，建立稳定的专业深度。同一主链可以连续发布两篇；第三篇只有在脱离前文后仍有强问题、低门槛入口和独立收益时才继续，否则切换到小专题、重要事件机制或其他技术主干。
  3. 同一个热点按最终问题归类：追问外部关系、影响与“为什么是现在”进入周二；必须拆开运行机制、架构边界或工程取舍才能成立，进入周四。
  4. 当另一条知识主干已经出现两至三篇相互承接且反馈明确的文章，再切换周四的活跃主链；不同时维护多条课程进度。

当前周四主线按时间分两段：2026 年 8 月 27 日前完成可靠 Agent 的阶段节点；2026 年 9 月 10 日起连续推进“模型为什么这样设计”。Skill 小专题与源码考古作为穿插储备；可靠 Agent 保留强问题候选，不再为补齐 Context、State、Memory、Skill 等概念强行排课。

一周两更

两个发布槽位对应两种稳定的阅读承诺：

周二：热点、广角与现象，帮助读者判断正在发生什么、为何与自己有关
周四：Agent、技术机制与架构，解释系统为什么这样运行、边界和代价在哪里

「从源码里看懂 AI 工程」不额外占第四个固定日期。遇到证据成熟、时效更强的源码篇，可以替换某个周四的模型篇，但不把周四再拆成两条同时追赶的进度。

周二不提前锁死系列。周一根据一周内出现的问题做一次闸门判断：

普通读者已经遇到这个现象，而且文章能提供新的判断方法
→ 发布现象分析

有时效性，而且暴露了独特机制、工程取舍或更大关系变化
→ 按最终问题归入周二或周四

外部关系能推出新的 AI 判断，且映射与断点都有证据
→ 发布「不是比喻」

只有热度，没有足够问题深度与证据
→ 不追新闻，转入技术历史候选

技术历史是周二的稳定备稿池，不是必须连续发布的栏目。「不是比喻」保持低频精品，不为凑轮换强行成篇。两个槽位是默认节奏，不是必须填满的产量指标；问题、证据或读者收益不成立时可以空缺。
