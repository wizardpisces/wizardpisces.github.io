从串行交接到持续协作：开发工作区的 Agentic 化

一、背景与问题

当前 FE Code Agent 将需求转换为多条阶段链：

需求与上游材料 → TodoList → BFF → Web
                                  ├─ 初始化
                                  ├─ Figma 产物
                                  ├─ 交付计划与拆分
                                  └─ 逐项实现、审核与交付

每个阶段生成材料，下一个阶段再根据材料重新理解任务。中间产物同时承担上下文交接、方案表达与启动门禁：

材料堆积 → 人工难以阅读、审核
逐级转述 → 上下文丢失、假设固化、错误累积
阶段门禁 → UI 等待后端，无实际依赖的工作一起阻塞
上游变化 → 派生材料同步、下游重新执行

阶段可以全部完成，最终代码仍可能不满足目标。出现问题后，又要逆着交接链查找原始要求、判断与修改，归因困难。

需要重新设计的是 Agent 工作的环境与协作方式。

二、Agentic 化的设计对象

将业务目标、工程知识、代码、操作入口和验证方式组织成 Agent 可以自主使用的环境：

                     Agentic 工作区
      目标与约束 / 原始来源 / 工程知识 / 实际代码
                 操作入口 / 验证与反馈
                           ↕
                   Agent 按任务需要使用
                           ↓
              理解、实现、验证与持续修订

Agent 能在环境中找到所需信息，判断当前能做什么，调用工具操作工程，并用实际反馈修正结果。不同执行者围绕同一任务和事实协作，而不是只消费上一角色加工后的交接物。

工作区需要具备四项能力：

能力 环境应当提供什么
信息可发现 任务全貌、原始来源、工程地图、相关知识的入口
边界可判断 业务约束、允许修改范围、真实依赖、未确认事项
工程可操作 可访问的代码、可运行环境、明确的命令与工具接口
结果可验证 验收依据、实际输出、失败反馈和人工判断入口

这些能力可以服务不同 Agent 或执行器。方案重点是环境怎样提供支持，不预设一套新的 Agent 框架、固定角色或阶段状态机。

三、把工作区组织成可使用的环境

任务入口连接信息、工程和操作，目录可以采用：

workspace/
├── AGENTS.md                 环境地图、事实来源、操作范围与更新规则
├── task.md                   本任务目标、验收、当前决定与未决问题
├── sources/                  需求、设计、接口与讨论的原文或引用
├── repos/<repo>/             实际工程及其上下文入口
├── knowledge/                工程约定、组件索引、可用 Skills
├── environment/              运行、预览、测试与检查的入口说明或脚本
├── work/                     按需产生的计划、分析和尝试
├── evidence/                 日志、测试、截图与 Review 依据
└── history/                  输入、代码、决定和结果的变化关联

工程与外部来源可以通过挂载或引用接入。原始文档保持自己的事实责任，任务入口只组织本次范围和当前决定，避免再复制一整套需求。

AGENTS.md 描述怎样使用环境

要理解目标 → 看 task 与相关原始来源
要找实现方式 → 查工程入口、组件索引、已有代码与 Skills
要修改工程 → 检查允许范围、依赖和本地约定
要判断结果 → 使用对应运行、测试与验收入口
遇到变化 → 核对来源与消费者，记录修订和复验

入口给出导航与约束，详细知识按需读取。Skills 描述特定问题的处理策略；组件索引提供工程事实与候选依据；命令和工具承担可确定的操作与检查。

关键约束落实到工具、测试和权限。文档中的说明与实际命令、路径、运行结果保持一致，失效内容随反馈修订。

当前事实与未知条件显式可见

每类事实保留来源和确认责任，区分已确认要求、工程现状、暂定假设和未决问题。Agent 可以直接回查需求、设计和契约，避免将分析稿中的推断当成批准的事实。

任务状态和当前决定有统一维护入口；可读视图可由运行记录生成。多人或多个 Agent 协作时，重要决定与公共契约由对应负责人确认，避免并发改写共享结论。

四、中间产物转为工作材料与审核视图

需求、契约、代码和测试保留其实际用途。技术设计、计划与 TodoList 根据当前需要产生：

原始来源与工程
       ├→ Agent 按需读取 → 直接开展工作
       ├→ 分析与计划 → 辅助判断，执行中持续修订
       └→ 当前成果 + diff + 风险 → 人工审核视图
                                      ↓
                                决定与反馈写回

审核视图聚焦当前需要确认的决定和结果，工作记录保留完整依据。人工可以展开原文、代码和日志，不必逐份批准重复表达相同内容的阶段文档。

真正被下一项工作消费的契约、代码或批准仍有约束作用。是否等待，应由当前动作的实际需要决定。

五、FE Code Agent 怎样使用这种环境

同一需求工作区提供业务目标、Figma、相关仓库、组件知识与验证入口。FE、BFF 和测试工作按需要展开：

                    需求目标与共享工程环境
                    │
                    ├─ 设计 + 组件 → UI 与本地交互 → 运行验证
                    ├─ 业务 + 契约 → BFF / 数据适配 → 接口检查
                    └─ 验收要求 → 测试场景；对象就绪后执行

               相关实现、服务与权限就绪 → 真实集成验收

UI 可以直接读取设计和工程组件，在 Fixture 下实现与预览；契约补齐后再接入真实数据。是否需要单独的技术设计、拆分或专门执行者，由工作复杂度与约束决定。

这需要工程本身提供展示与数据边界、可启动的预览环境，以及必要的测试入口。页面若直接依赖尚未生成的 SDK，工作区就需要补齐隔离能力，而非只在说明里宣称可以提前开发。

契约只提供部分能力时，缺口明确关联到对应目标。UI、本地交互和其他独立工作可以继续，真实业务能力保留待补。代码实现、Fixture 验证和真实集成分别记录结果。

验证是环境能力

代码修改 → 实际运行或检查 → 输出与判定 → 修正或继续

环境应让 Agent 找到并执行构建、测试、接口和 UI 检查，读取完整输出并定位失败。截图、实际操作与人工评价补充自动化检查的覆盖。

缺少运行能力时，结果明确保持未验证。测试通过、报告完成和节点结束都只证明相应事实，最终结果仍对照原始目标与验收要求确认。

六、新信息进入环境，带动相关工作修订

需求、设计、契约和人工评论可以继续关联到已有任务。执行者在检查点采用新的依据，核对代码消费者和原有假设，再判断相关结果是否仍有效。

来源变化 / 人工反馈
        ↓
更新当前事实与决定，保留前后依据
        ↓
定位相关实现、假设与验证结论
        ↓
修改必要部分 → 复验 → 更新结果与审核视图

例如，协议字段改名需要核对生成链和映射；单位含义变化可能影响显示、计算与断言。机械依赖可用程序检查，业务影响需要结合原始要求判断。

每轮记录采用的输入、工程状态、实际操作、diff 与输出。失败时从结果回查依据；变化后复用仍有效的代码和证据，失效或不确定的部分重新检查。

七、怎样开始验证

先建设一个独立的需求工作区，不继承旧系统的阶段图与交接协议。接入真实 FE 工程、相关输入、工程导航和运行验证入口，让现有可用的 Agent 直接在其中工作。

首轮只检查环境是否真正帮助 Agent：

  • 能否自主找到需求、组件、接口、工程约定与验证方法。
  • 能否在后端材料未齐时，推进确实独立的 UI 工作。
  • 能否根据真实失败输出修复，而非等待下一阶段或只修改报告。
  • 新契约与人工反馈到达后，能否继续原工作并正确复验。
  • 能否交付可审核结果，并清楚保留未满足和未验证的目标。

初期人工提供来源关联、确认关键取舍。反复出现的信息缺口补到导航与知识，重复且确定的操作固化为脚本，稳定的使用策略再沉淀为 Skill。

任务页优先展示目标、实际成果、待决问题和验收证据；执行时间线从真实操作生成，供回查使用。

八、取舍与边界

环境更易理解 → 减少重复探索
环境更易操作 → 减少人工代办
反馈更完整   → 更早发现并修正错误

这些收益需要连同知识维护、运行环境和验证成本一起观察。导航与知识应简明且可回查，过期内容及时修订；依赖不确定时扩大检查，保留必要集成验收。

自主工作受明确范围与权限约束。事实可读不代表获得修改授权，普通推断不能覆盖批准的业务要求，外部副作用和发布仍需宿主控制。

衡量 Agentic 化的结果，是 Agent 能否借助这个环境更可靠地完成工作，以及人是否减少了重复解释、交接和排错投入。

关联方案

  • 从“AI+现有流程”到“AI 原生”的范式转变：共享知识与协作方向。
  • Agent 的分治式演进：任务解耦与局部反馈闭环：局部执行与验收的成立条件。
  • Agent 改进工作空间：任务修订与知识演进机制：知识、采集和反馈机制如何逐渐形成。
