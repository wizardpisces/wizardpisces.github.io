从固定流程到任务驱动：Main Agent 的 Feature 编排设计

一、背景

当前 FE 开发将大需求投入固定阶段链：技术设计、接口准备、任务拆分、页面实现、审核与交付。无实际依赖的工作被强制串行，人工到最后才看到结果；Website、RN 共用的 BFF 变化后，下游又容易从入口重跑。

Main 基于Feature 垂直交付拆分和指派任务。首期从 FE 的简单协作开始，例如 BFF 提供协议、Website 与 RN 消费协议；具体通信内容保留在工作区中。

二、核心架构

任务来源 + 工程 + 可用 Agent + 已有经验
                  ↓
           Main → Feature 与子任务
                  ↕ 人工修正与确认
                执行器
                  ↕ 调用与续跑
           Website / RN / BFF
                  ↓
           任务结果与验证依据
                  └→ Main：继续 / 调整 / 请人判断 / 交付

共享任务工作区：原始来源、代码、编排、执行记录、反馈与证据

Main 决定做什么、交给谁和依赖关系；子 Agent 自主调查、实现和验证。工作区提供共享上下文，编排结构只描述任务关系。

三、核心结构

Main 输入

MainInput
├─ goal：本次目标与范围
├─ sources：PRD、Figma、已有协议等来源入口
├─ agents[]：身份、能力说明、工程入口、调用入口
└─ knowledge：已有经验入口〔可缺省〕

Main 查阅工程后规划。子 Agent 从工作区读取当前 Feature 和自己的任务，按需回查 PRD、Figma；全局要求仍有约束作用，写入权限由运行宿主控制。

Main 输出

Plan
└─ features[]
    ├─ id、goal：本片目标与边界
    ├─ acceptance：验收条件
    └─ tasks[]
        ├─ id：本次需求内唯一标识
        ├─ agent：执行者
        ├─ goal：本次需要完成的工作
        ├─ dependsOn[]：前置任务 ID〔可为空〕
        └─ review：结果交给后续任务前，是否需要人工确认

Feature 列表给出建议交付顺序，任务的 dependsOn 表达真实依赖。共享工作只定义一次，多个任务可以引用它；已有结果可直接读取，不为已经满足的输入重复创建任务。

同一个 Agent 可以在不同节点继续工作：

T1：Agent A，完成可独立推进的部分 ─┐
                                 ├→ T3：Agent A，结合两项结果继续
T2：Agent B，提供所需结果 ─────────┘

T1.dependsOn = []
T2.dependsOn = []
T3.dependsOn = [T1, T2]

图由任务引用生成。T1、T2 在资源隔离时可并行，T3 等前置结果就绪后继续；先串行执行也不需要改变图。

切片仍以较早形成可验收行为为准，原始要求均需有归属；详细条件见Feature 划分原则。

子 Agent 返回

Result
├─ taskId、status：完成 / 受阻 / 失败
└─ record：实际成果、验证证据与剩余问题的记录入口

run(workspace, taskId) → Result
resume(workspace, taskId, 反馈或输入变化) → Result

成果可以是代码、协议或其他材料，消费者从记录入口按需读取。宿主保存任务与会话关联；被确认和采用的内容保留依据，后续可以核对变化。

四、执行与人工介入

plan = Main.plan(MainInput)
人工确认或修正：Feature、执行者、顺序与依赖
检查：要求有归属，Agent 入口存在，任务引用有效且无循环依赖

循环：
  从前置结果已就绪的待执行任务中选择 → run 或 resume
  保存 Result；review 为真 → 等待人工确认再供下游使用
  失败、受阻或人工反馈 → Main 决定修订、调整安排或等待补充
  本片满足 acceptance → 人工验收 → 推进下一片
  全部完成 → 必要的组合验收 → 交付

独立且资源隔离的任务可并行，同一工作树保持串行；初版可以并发 1 起步。未改变条件的受阻任务等待补充，不反复启动。人工评审时固定被审内容。

五、局部续跑与经验复利

人工反馈 / 输入或上游结果变化
    → Main 结合依赖与执行记录定位相关工作
    → 对应 Agent 检查实际影响
    → resume(原任务, 差异与反馈)
    → 受影响验收重开并复验，无关成果保留

依赖辅助定位，实际影响由 Agent 结合工程判断。会话不可恢复时，依据现有代码、记录和待办继续；修正切片或指派时更新 Plan。

人工修正记录：原安排 → 新安排 → 原因 → 执行后的实际效果
                                ↓
候选经验 → 后续 Main 参考 → 新任务验证 → 保留 / 修订 / 撤回

复利来自切片和协作安排逐步改善。先保留修正与结果，再按任务修订与知识演进机制提炼适用条件明确的经验。

六、落地顺序

沿用Agentic 工作区，最小持久化入口：

workspace/
├─ task.md、sources/      目标与原始来源
├─ agents/               子 Agent 能力说明与调用入口
├─ plan.json             Feature、任务与依赖
├─ repos/                实际工程
└─ runs/                 执行结果、输入依据、人工修正与历史安排
  1. 适配现有 Agent 的局部执行和续跑入口，实现 MainInput、Plan、Result，先跑通一片与人工反馈。
  2. 选择一个简单的上游提供结果、下游消费结果的任务，改变一次输入，检查局部续跑和成果保留；BFF 与端的协议协作可作为首个实例。
  3. 根据实际缺口演化结构，观察首个可验收成果耗时、返工范围和总成本。
