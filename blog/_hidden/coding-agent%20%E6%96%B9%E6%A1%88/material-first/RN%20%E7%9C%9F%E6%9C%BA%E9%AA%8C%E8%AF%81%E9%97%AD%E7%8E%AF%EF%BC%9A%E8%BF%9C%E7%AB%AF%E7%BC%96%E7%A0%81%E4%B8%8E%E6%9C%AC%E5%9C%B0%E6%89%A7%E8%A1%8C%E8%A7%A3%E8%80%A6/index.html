Coding Agent 的反馈闭环：编码与验证解耦

背景与难点

远端可以集中提供编码算力与任务存储，但 RN 验证依赖 App 安装、签名、设备权限、测试账号和运行网络。把这些环境一并集中部署，会让自动反馈闭环被设备与环境管理拖住。

核心问题不是如何远程点击屏幕，而是：代码在远端生产，运行环境在本地，如何持续交换验证任务与证据，驱动自动修改？

解决思路

解耦代码生产与运行验证：远端 Coding Agent 负责编码与验收，本地执行器负责运行与取证，通过消息队列异步协作。 复用本地已有环境，不要求远端复制整套设备环境；部署与运行成本仍存在，但不再与远端编码绑定。

不仅解耦执行位置，也解耦推进时机：验证检查点就绪即可发布，独立编码继续推进，反馈在合适节点消费。 第一版先以整体任务跑通闭环，再逐步引入检查点，不要求一开始就解决任务拆分粒度。

任务生成、消费与反馈

flowchart LR
    R["远端 Coding Agent<br/>编码、维护清单、审阅"] -->|验证就绪即发布| T["验证任务队列"]
    T -->|消费| L["本地执行器<br/>运行页面、采集证据"]
    L -->|生产| E["验证结果队列"]
    E -->|消费反馈，修正或补验| R

协同状态：验证清单

远端 Coding Agent 维护需要验证的页面、状态和验收条件，据此持续生成验证任务，并根据回传证据更新进度。代码版本、验证任务与审阅结果的关联保存在远端，本地只消费具体请求。当前交付版本的必需验证项全部通过，才结束验收。

发布粒度：验证检查点

编码任务不等于验证任务。 组件、素材、布局等多个编码任务，可以共同组成一个验证检查点；不按每次提交或每个小任务完成机械触发。

后续优先以“页面 + 指定状态”为验证单元，例如默认态、空态、弹窗。发布条件是：能运行、预期可判断、版本与状态可复现。可验证不等于已经通过，不必等页面完美才请求反馈。

协作协议：Agent RPC

把验证理解为“由 Agent 执行的异步远程函数调用”：Agent RPC 描述调用契约，消息队列承载请求与结果。执行器处理操作过程，返回可审阅的产物；具体启动和恢复经验是执行端的辅助能力，不进入主协议。

保留最小 RPC 雏形，具体字段可在落地时调整。

请求：远端生产，本地消费

{
  "id": "capture-001",
  "method": "rn.capturePage",
  "environment": {
    "commitSha": "<目标代码版本>",
    "runtimeProfile": "<本地运行配置引用>"
  },
  "params": {
    "page": "<目标页面>",
    "state": "<目标状态>"
  }
}

响应：本地生产，远端消费

{
  "id": "capture-001",
  "result": {
    "screenshot": "<截图制品引用>"
  }
}

id 关联请求与响应，method 表达能力，environment 指定环境与版本，params/result 承载实际输入输出。失败时用 error 替代 result，说明无法完成的原因。

请求与结果分别扩展，进度与验收结论分离。远端保存任务及会话关联，消费结果后继续决策；

推进方式

  1. 整体任务闭环：先选一个页面需求，整体作为一个编码任务；完成后发布截图验证，消费反馈并修正复验。不拆子任务，不引入自动拆分算法。
  2. 检查点流水推进：从验证清单中识别可独立验证的页面状态，就绪即发布，同时推进其他独立编码。
  3. 按需扩展：再探索交互证据、多设备并行与任务聚合，沿用协议思路扩展执行及调度能力。

第一阶段验证跨端闭环，第二阶段再验证编码与验证的重叠执行；异步机制从一开始保留，但不把细粒度拆分作为首版前提。

横向迁移

迁移到 Web 等场景，只需替换环境适配与执行方法；“发布验证任务 → 消费执行 → 回传证据 → 续跑迭代”的机制不变。
