GEPA 如何优化 Agent 策略

当前先跑通 Skill Creator 生成候选、人工审查、后续使用与修订。GEPA 放在需要反复比较候选、已有可重复评价方式之后接入，自动评估世界萃取可以继续后置。

下面用“从一次类型检查复盘中提炼诊断比较 Skill”串起目录、过程和产物。

1. 已有输出提供什么

现有目录已经保存任务事实：

rn-agent-output/
├── runs/<任务>/
│   ├── records/inputs/          # 原始任务、约束与验收
│   ├── records/attempts/        # 各轮结果、检查与产物
│   ├── logs/                    # 执行轨迹与工具输出
│   └── agent-workspace/         # 工程副本与执行上下文
└── operator/<照看过程>/
    └── journal.jsonl            # 人工评审、介入及理由

本次 smoke 中，诊断比较初验不确定，调整比较方式后复验通过，业务代码树没有随之变化。这可以成为一个具体的复盘问题：

怎样识别本次新增诊断，同时避免把生成文件中旧诊断的行号移动误判为新增？

Creator 读取对应输入、日志、检查脚本与修正记录，再结合已有 Skills 提出指导。原始事实保持不改，按需引用，不复制整个缓存与运行目录。

2. 现在先做的 Skill Creator

建议新增的最小目录

rn-agent-output/
├── runs/、operator/             # 已有事实来源
├── skills/
│   ├── skill-creator/
│   │   └── SKILL.md             # 人工维护的 Creator 指导
│   └── diagnostic-comparison/
│       └── SKILL.md             # 人工审查后保留、准备试用的经验
└── postcoding/diagnostic-comparison/
    ├── brief.md                 # 本次问题、目标、材料入口和边界
    ├── candidate/
    │   └── diagnostic-comparison/
    │       └── SKILL.md         # 本轮候选
    └── review.md                # 变更提案、人工意见、修订与采纳结果

这是建议增加的目录，不是现有输出已具备的能力。Skill 按目录保存，需要时可带脚本、模板和参考材料；当前不另建中间知识库。

怎样跑一轮

人工描述问题与目标，brief.md 引用相关材料
                    ↓
Agent 按 skill-creator 指导读取事实与已有 Skills
                    ↓
生成 candidate/，提出新增、更新、合并或移除建议
                    ↓
人工 Review ↔ 修改候选，理由保留在 review.md
                    ↓
人工采纳到 skills/ → 在后续相关任务中试用

例如，候选 SKILL.md 可以包含：

Compare diagnostic identities, not only total counts.
Normalize generated-file line shifts only when source context matches.
Keep newly introduced diagnostics visible in the comparison.

Creator 同时说明适用条件、证据和例外。若库中已有基线比较 Skill，优先提出更新；若指导重复或冲突，指出具体位置并提出合并或移除建议。候选不直接覆盖正式内容，更新与移除前保留旧内容。

这一阶段的产物就是候选 Skill、变更提案和人工修订记录。 无需 GEPA，也无需先实现 Env Creator。入库与全局启用分开，后续任务记录实际采用的指导、行为和环境结果。

Creator 自身怎样迭代

如果人工反复纠正“把单个 Case 写成通用规则”“重复创建相近 Skill”等问题，就把这些纠正沉淀进 skills/skill-creator/SKILL.md，再观察后续提炼质量。

Creator 的规则与自检可以降低冲突和过度泛化风险。通用性、组合效果和不退化仍需要使用与回归证据；第一版可以先把效果记为“待验证”，不必为此阻塞候选生成。

3. GEPA 以后插在哪里

普通 Creator 可以生成候选并与人工反复修订。GEPA 增加的是：根据执行反馈反思、提出多个候选，并按评价结果选择继续探索的方向，同时管理预算与候选记录。1

这里先优化产出的一份 diagnostic-comparison Skill：

Creator 产出的初始 Skill
          ↓
GEPA 提出候选 → 写入隔离的 Skill 目录
          ↑                 ↓
     分数与具体反馈 ← Agent 使用候选执行 Case
          ↓
选中的候选 → 人工 Review → 决定是否更新 skills/

优化过程会多出什么产物

建议在同一问题目录下保存：

postcoding/diagnostic-comparison/
├── brief.md、candidate/、review.md     # 原有生成与人工审查材料
└── gepa/
    ├── candidates/01/SKILL.md         # 第一个实验候选
    ├── candidates/02/SKILL.md         # 第二个实验候选
    ├── evaluations.jsonl             # 候选、Case、分数、反馈和执行证据入口
    └── best.json                     # 选中的候选引用，等待人工审查

这些文件名表示我们希望保存的工作区产物，由接入层整理。GEPA 提供候选与优化结果，原始执行证据仍由已有执行器保存。2

例如，两个候选分别采用“只比较数量”和“比较诊断身份”。对“旧错误减少一条、新错误增加一条”的 Case，两条示意记录可以是：

{"candidate":"01","case":"same-count-new-error","score":0,"feedback":"错误总数相同，漏掉新增诊断","evidence":"<本次执行记录入口>"}
{"candidate":"02","case":"same-count-new-error","score":1,"feedback":"识别出新增诊断","evidence":"<本次执行记录入口>"}

分数来自固定检查对实际输出的判定，不能由候选自己宣布。单个 Case 通过只提供局部证据，还要检查其他样例和相关 Skills 的组合效果。

这里的“训练产物”是候选指导、实验记录与选择结果，不是新的模型权重。1

实际需要增加哪三个连接点

连接点 我们需要做什么
候选落盘 将 GEPA 给出的内容写入隔离 Skill 目录，让 Agent 实际使用，不覆盖正式库
执行评价 运行 Case，根据固定条件返回分数、诊断反馈和证据入口
优化调用 将初始 Skill、Case 和预算交给 GEPA，保存结果，交人工决定是否采纳

已有任务目录、MCP 采集和执行宿主可以保留。GEPA 不会自动理解输出目录、制定可靠评分，也不会替我们完成 Skill 库的合并与删除决策。

如果初始 Creator 已经给出合适指导，GEPA 也可能没有找到更好的候选。它的具体收益应是：在同样预算下，更快试出有效改动，或减少人工逐个组织实验的工作，而不是保证生成质量提升。

4. 按什么台阶推进

阶段 做什么 留下什么 GEPA
现在 Creator 读取工作区，人工审查与修订 候选 Skill、增删改提案、Review 记录 不需要
后续使用 在相关任务中试用，观察采用、失败和回归，继续改 Creator Skill 内容与实际使用结果的关联 不需要
可重复比较后 先手工准备少量 Case，固定判定，再反复比较候选 候选、评价与选择记录 按收益决定是否接入
需要扩大覆盖时 Env Creator 从任务中萃取、恢复并校验评估场景 可重复使用的环境与判定依据 复用这些场景继续优化

少量手工 Case 与完整的自动评估世界是两件事。 前者可以先支持一个局部实验，后者在后续扩大覆盖、降低环境恢复成本时再建设。

初期先优化产出的 Skill。若以后用 GEPA 优化 Creator，评价会多一层：Creator 指导 → 生成 Skill → 在任务中应用 → 评价结果，需要更充分的样例和更高的预算，暂不一起引入。

当前最小目标是把一次真实复盘变成可审查、可试用、可修订的 Skill。等候选已经需要反复比较，再用 GEPA 接管实验搜索；不为引入优化器提前建设整套评价平台。
