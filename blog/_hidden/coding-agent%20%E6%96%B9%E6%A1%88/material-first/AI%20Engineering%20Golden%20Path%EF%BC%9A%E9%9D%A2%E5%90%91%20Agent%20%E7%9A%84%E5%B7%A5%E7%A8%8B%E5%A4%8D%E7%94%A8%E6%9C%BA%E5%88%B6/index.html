从代码复用到决策复用：面向 Coding Agent 的可验证工程复用机制

Coding Agent 已经能够搜索仓库、理解需求并完成复杂代码修改。新的问题不再只是“它会不会写”，而是：当越来越多代码由 Agent 生成时，团队已有的工程经验能否继续发挥作用。

同一个需求，Agent 可以生成多种都能运行的实现。单次看未必有问题，长期却可能形成越来越多不同的目录、抽象、错误处理和测试方式。

团队并非没有答案。答案通常已经存在于优秀实现、公共能力、Code Review 和工程师的判断里，只是 Agent 很难在正确时机准确使用。

AI Engineering Golden Path 想解决的是：

把团队已经验证过的工程解法，变成 Agent 能发现、能采用、能验证，并能通过真实结果持续修正的默认路径。

本文把这种面向同类工程问题的、经过验证的默认实现路径称为 Golden Path。它不是整套系统的名称，也不是要求 Agent 严格遵循的固定流程，而是工程复用机制中的一种核心产物。

范式变化：从代码复用到决策复用

传统工程复用主要解决“有没有现成代码”：

前端 → Component、Hook、页面模板
后端 → SDK、Service、数据访问模块
测试 → Fixture、Mock、测试工具

但真实开发还包含大量无法由一个组件回答的问题：页面状态如何组织、接口采用什么分层、错误和权限在哪里处理、什么逻辑值得抽象，以及什么证据才能证明结果可以交付。

因此，Agent 时代的工程复用需要继续向前一步：

Code Reuse
复用现成实现

Decision Reuse
复用同类问题中已经验证过的工程选择

复用对象不再局限于某个端或某类代码，而是反复出现的工程问题及其已验证解法。

核心机制

Golden Path 不是一份更长的最佳实践文档，也不是要求所有代码完全一致的固定模板。

它是一条针对特定问题、经过验证的优先路径（on-policy，同策略）：Agent 默认先沿用；当前需求存在真实差异时可以偏离，但需要满足相应的工程约束与验证条件。

这套机制只需要四个抽象概念。

Asset：可以直接复用的实现

Component、Hook、SDK、公共 Service、Fixture 和测试工具都属于 Asset。存在合适 Asset 时，Agent 应优先引用，而不是重新生成相似代码。

Golden Path：优先采用的工程路径

当不存在可直接复用的答案时，Golden Path 告诉 Agent：这类问题通常参考哪些真实实现，优先采用什么组织方式，哪些差异允许调整。

Contract：结果必须满足的边界

Contract 定义类型检查、测试、接口兼容、运行截图或人工验收等条件。它不规定 Agent 必须如何思考，只规定什么结果才算成立。

Case：来自真实任务的反馈

Case 由执行过程、最终代码、验证证据和人工评价组成。它用来检验已有路径是否有效，也为修正或产生新的路径提供依据。

四者形成闭环：

flowchart LR
  Task[工程任务] --> Path[复用 Asset 或参考 Golden Path]
  Path --> Verify[Contract 验证]
  Verify --> Case[形成 Case]
  Case --> Improve[修正工程先验]
  Improve --> Path

为什么它是 Agentic

把文档放进 RAG，并不会自动得到 Agentic Engineering。真正的变化发生在 Agent 的执行闭环里：

Observe：理解需求、仓库和已有实现
Decide：判断复用、参考还是根据差异自主实现
Act：修改代码并调用必要工具
Verify：在真实工程和运行环境中验证
Learn：用结果和人工反馈修正已有路径

Agent 仍然负责搜索、判断和执行。Golden Path 提供经过验证的工程先验，Contract 提供结果边界，Case 负责让先验接受真实结果检验。

它既不是让 Agent 每次自由发挥，也不是由人预先拆出一条固定流水线，而是在 Agent 自主性与工程确定性之间建立反馈闭环。

与 Agent Skill 的关系

Agent Skill 是知识的封装、执行和学习单元，可以通过说明、脚本、模板和工具，让 Agent 完成某类任务，也可以从执行案例中总结经验并持续迭代。

Golden Path 不是 Skill 之外的平行机制，而是面向组织工程复用的一类 Skill 内容与默认选择策略：

Agent Skill
→ 通用的知识封装、执行和学习单元

Engineering Golden Path
→ 面向组织工程问题的一类 Skill 内容与默认选择策略

一个 Skill 可以用于图片处理、文档排版或设备操作；一个 Golden Path Skill 则表达团队对某类工程问题已经验证过的优先解法，包括可复用 Asset、参考实现、允许偏离的边界和验证条件。

Golden Path 额外需要回答的只是：哪些经验值得升级为组织默认路径，以及如何避免把一次偶然成功固化成工程规范。因此，它可以通过 Skill、Tool、索引或 Context 实现，但不应与这些载体混为一谈。

抽象策略

为了避免再次建设一套复杂知识系统，需要坚持三个原则。

按工程问题抽象，而不是按端抽象

Web、RN 和 Backend 的代码不同，但都存在状态组织、错误处理、权限、重试、测试和可观测性问题。可以跨端复用的是问题表达和决策原则，具体实现仍属于各自工程环境。

区分知识与载体

Golden Path 可以存在于代码、Markdown 或团队共识中，也可以通过 Skill、Tool、索引或 Context 提供给 Agent。载体解决“如何交付”，Golden Path 解决“什么值得成为默认路径”。

用反馈修正先验，而不是证明先验

Case 不负责证明预设方案正确，而是检验它是否真的改善结果。失败既可能说明缺少 Asset，也可能说明 Golden Path 不适用、Contract 不完整，甚至说明新增知识产生了副作用。

一个简单例子

假设 RN 页面还原出现四种现象：没有发现通用组件、发现后没有采用、文案违反 i18n 规范、代码数值合理但实际视觉不符。

它们都可以被视为同一条 Golden Path 的失效，只是发生在不同环节：

发现：没有找到已有 Asset
选择：找到后没有优先采用
实现：没有遵循 i18n 等工程约束
验证：没有通过运行态复核发现视觉偏差

Golden Path 描述的是整条优先路径；Asset、约束和验证是这条路径中的组成部分。分析 Case 时，再根据失效环节决定补充 Skill 内容、检索 Tool、参考实现还是验证能力，而不是把所有问题都归结为增加提示词。

结语

模型提供通用编码与推理能力，但不会天然拥有一个团队持续变化的工程经验。团队真正需要积累的，也不只是更多代码和文档，而是对“什么问题应该如何解决”的可验证认识。

AI Engineering Golden Path 将这份认识接入 Agent 的执行过程：

能直接复用 → 使用 Asset
需要新增实现 → 参考 Golden Path
完成代码 → 通过 Contract 验证
真实结果 → 沉淀 Case 并修正路径

它不需要成为 Skill 之外的另一套系统，而是一种面向 Coding Agent 的工程复用范式：可以借助现有 Agent Skill 机制实现，让 Agent 保留自主判断，同时优先站在团队已经验证过的经验之上工作。
