RN Screenshot-to-Page TODO

本文维护六阶段路线下的执行项。阶段目标、成果和评价标准见《RN 页面还原：六阶段推进》。

当前目标

当前只聚焦阶段 1：把 RN Screenshot-to-Page 接入现有流程节点，完成一个真实、可运行、可人工验收的页面。

截图 + 需求 + RN 仓库 + 验收条件
→ 现有流程节点
→ Codex
→ 可运行 RN 页面
→ 人工验收

Page Schema、Task Brief、Material 和 BBox 暂时作为候选增强能力。可以继续准备和移植，但不阻塞基础版本跑通，也不默认全部注入 Codex。

并行计划

  • [ ] Trace 与记录 Tool：完善 Raw Trace、Decision Events 和 Execution Report
  • [ ] RN 验证自动化：从人工验证逐步演进到自动进入页面、截图、断言和视觉 Diff
  • [ ] Material 基础：继续建设 Catalog、Fixture、Candidate Board 和查询 Tool
  • [ ] Schema 与 Context：继续迁移 Page Schema，并探索 Task Brief、BBox 等候选输入
  • [ ] Material Generator Skill：对干净的工程进行 Material 化

并行建设不阻塞阶段 1；只有真实 Case 证明有效的能力才进入默认路径。

跨端工程复用不属于当前 RN TODO，单独见《AI Engineering Golden Path：面向 Agent 的工程复用机制》。

阶段 1：接通基础版本

  • [ ] 选择真实页面：确定一个准备上线的 RN 页面，提供截图、需求、代码仓库、页面入口和验收条件
  • [ ] 接入现有流程节点：让节点能够创建并运行 RN Screenshot-to-Page 任务
  • [ ] 执行页面还原：Codex 在真实 RN 仓库中搜索、实现并接入页面
  • [ ] 完成运行验证：先允许人工启动、进入页面和截图，确认页面能够在 Native 环境运行
  • [ ] 完成人工验收：记录成功、失败和需要人工修正的内容
  • [ ] 留下最小轨迹：保存人工验证步骤、截图、Langfuse Raw Trace、关键 Decision Events 和最终 Execution Report

阶段成果：一个真正跑通的 RN 页面，以及第一份可分析的真实 Case。

阶段 2：固定 Baseline

  • [ ] 固定 Case 输入：保存截图、需求、验收条件和仓库 Commit
  • [ ] 保存 Direct Baseline：记录不额外注入候选增强能力时的运行结果
  • [ ] 记录核心指标：最终验收、首轮通过、人工修正、执行成本和相对增益
  • [ ] 验证可复现性：确认同一 Case 可以重新运行和比较

阶段成果：后续 Schema、Task Brief、Material 和 BBox 实验都使用同一基准。

阶段 3：单变量增强

  • [ ] 验证 Page Schema：只增加 Screenshot → Schema 相关输入，比较结果变化
  • [ ] 验证 Task Brief：只增加整理后的任务表达，比较需求理解是否改善
  • [ ] 验证 Material：只增加组件查询和示例信息，比较组件选择是否改善
  • [ ] 验证 BBox：只增加位置增强信息，比较视觉定位是否改善
  • [ ] 按需验证 Golden Path：仅当页面逻辑或代码组织不稳定时，增加一个同类页面参考并比较结果
  • [ ] 覆盖修改场景：把已有页面修改作为独立 Case，验证增强能力是否仍然有效

实验顺序由真实 Failure Case 决定，不要求按上述列表全部实施。

阶段 4：建立优化闭环

  • [ ] 升级 Run Finalize：让 submit_execution_report 在保存结果后，按 taskId 关联 Decision Events、Langfuse Trace 和验证证据，并标记本次 Run 结束
  • [ ] 接入验收后分析：人工评价完成后再分析完整 Case，避免在缺少最终结果时过早归因
  • [ ] 分析 Case：结合结果、Raw Trace、Decision Events 和 Execution Report 定位问题
  • [ ] 提出单一改进假设：明确应该调整 Skill、Tool 还是 Context
  • [ ] 完成对照验证：在原 Case 和回归 Case 上验证是否真正改善
  • [ ] 版本化更新：只有验证有效并经人工确认后，才更新默认 Skill 或 Tool

公共观测能力先只保留两个 Tool：

record_run_decision_event
submit_execution_report

证据和失败类型属于 Execution Report；最终评分由运行结果和人工验收产生，不继续拆分 Tool。

阶段 5：抽取公共能力

  • [ ] 确认跨场景价值：只选择已在真实 RN Case 中证明有效的 Agent-Agnostic 能力
  • [ ] 泛化数据结构：移除 RN 专用字段，保留任务、阶段、证据、疑虑和结果
  • [ ] 接入其他 Agent：选择一个 BE 或 Test Case 验证复用价值

阶段成果：公共能力可以跨 Agent 使用，而不是复制 RN 页面还原逻辑。

阶段 6：动态策略选择

  • [ ] 积累足够 Case：形成不同任务、增强组合和结果的可比较记录
  • [ ] 总结适用条件：明确 Direct、Schema、Material、BBox 和 Task Brief 各自适合的问题
  • [ ] 按任务选择能力：避免所有任务默认注入相同上下文和工具

阶段 5、6 暂不作为当前交付项。

根据 Failure Case 决定后续投入

  • [ ] 找不到合适组件：补充 Material 信息，再验证组件检索是否改善结果
  • [ ] 看不准元素位置：验证位置增强图或独立视觉感知模型是否改善视觉定位
  • [ ] 遗漏或误解需求：验证 Task Brief 是否比原始需求表达更有效
  • [ ] 页面逻辑组织不稳定：选择一个同类页面 Golden Path，验证是否减少结构偏差和人工调整
  • [ ] 无法完成 Native 验收：补充稳定的 RN 截图采集和视觉对照能力
  • [ ] 执行过程难以复盘：优化 Run Decision Events、Execution Report 和问题记录

没有真实 Failure Case 触发时，不提前扩建对应系统。

后续灵感与研究方向

以下内容不是当前阶段 1 的阻塞项，但作为后续优化 Agent 路径的重要指导保留。

Task Brief

Task Brief：探索如何从完整 PRD 中提取 RN 页面任务，形成 Schema 与 Direct 路径可以共用的轻量输入。

可能的最小形态：

页面目标
页面入口与业务场景
必须展示和交互的内容
不能破坏的业务约束
设计稿或截图
验收条件

可能的推进策略：

  1. 当前继续复用现有 PRD、TD 和 Schema 流程完成页面上线；
  2. 从真实任务中手工整理一份最小 Task Brief，同时提供给 Schema 与 Direct；
  3. 只有它能减少需求误解或人工补充时，才进一步研究自动提取和结构化。

位置增强图辅助 Codex 视觉定位

位置增强图：先标出候选区域并编号，帮助 Codex 把文字描述和截图位置对应起来。

可能的形态：

原始截图
+ 带编号的区域标记图
+ region_id / bbox / 简短描述
→ 一起提供给 Codex

可能的推进策略：

  1. 默认仍让 Codex 直接看原始截图；
  2. 只在元素定位不稳定的真实案例中，用 SAM、OmniParser 或简单人工框选生成位置增强图；
  3. 对比增强前后的定位和实现结果，有增益后再封装成可选 Tool。

理论基础参考《模型能叫出按钮的名字，为什么指不准它在哪里？》。

Agent 执行轨迹优化

执行轨迹：分别记录原始过程、阶段状态、最终结果和外部评分，用于定位 Agent 为什么成功或失败。

可能的形态：

Langfuse Raw Trace
→ Run Decision Events
→ Final Execution Report
→ Result Score

可能的推进策略：

  1. 先保证 Langfuse 能记录真实模型调用和工具调用；
  2. 再用少量 Decision Events 补充关键选择、证据和疑虑；
  3. submit_execution_report 只提交最终状态和证据，由基础设施按 taskId 聚合完整 Run；
  4. 人工验收后再分析成功与失败样本，判断 Task Brief、Material 或 Tool 是否真正产生增益。

Material 演进

Material：先用最少信息帮助 Agent 找组件，遇到真实召回问题后再增加字段。

可能的演进形态：

组件名称、描述、关键词、导入路径
→ Fixture 与 Native 展示
→ 组件截图和视觉特征
→ 更复杂的检索或视觉召回

可能的推进策略：

  1. 先用最小 Metadata 和 Fixture 支持组件查找与正确引用；
  2. 记录找不到、找错和不会使用组件的真实案例；
  3. 根据失败原因分别补充关键词、示例参数、截图或视觉特征；
  4. 只有简单查询无法满足时，才引入更复杂的索引和召回方案。

页面逻辑的 Golden Path

Golden Path：当 Material 能解决组件复用，却无法约束复杂页面逻辑时，为 Agent 提供一个经过验证的同类实现参考。

可能的推进策略：

  1. 只有真实页面出现代码组织不稳定时才触发；
  2. 人工选择一个同领域、同类型的优秀页面作为 Golden Example；
  3. 记录参考源码、必须约束和验证方式，与 Baseline 做单变量比较；
  4. 验证有效后，将结论交给独立的工程复用方案继续沉淀，不在 RN TODO 中建设通用平台。

完整方案见《AI Engineering Golden Path：面向 Agent 的工程复用机制》。
