面向 RSI 的 Coding Agent：从任务反馈到方法迭代

背景

Coding Agent 可以在一次任务中根据测试、运行结果和人工反馈反复修正代码，但任务完成后，这些修正未必改变下一次执行。同类组件选型、验证缺失或环境误判，仍可能需要人工重新纠正。

RSI（Recursive Self-Improvement，递归自改进）关注的是：系统能否根据反馈改进自身，并进一步改进产生这些改进的方法。

在 Coding Agent 中，工程切入点是将任务中经过验证的有效变化沉淀到 Skill / Tool / Context，再用提炼与使用结果改进 Skill Creator 本身。

范式变化：从交付结果到改进执行系统

因此，优化单元从交付代码扩展到 Agent 的执行系统，再扩展到产生改进的方法：

任务修正：改业务代码
└─ 改善当前任务的结果

执行系统改进：改 Skill / Tool / Context（含工程信息）
└─ 改善后续任务的执行方式

递归改进：改 Skill Creator 的取证 / 筛选 / 验证方法
└─ 改善下一轮如何产生改进

进步通过可复用的策略与能力留下来，继续接受后续任务的反馈。

工程经验如何被复用

代码复用 → 使用已有组件、SDK、Service 等实现
决策复用 → 沿用经过验证的选型、组织方式与验证策略

Golden Path 是针对同类工程问题、经过验证的优先路径，说明适用条件、参考实现和允许调整的边界，可以通过 Skill 或 Context 提供给 Agent。

Asset 提供可复用实现，Contract 定义结果要求，Case 保留实际执行与验收反馈。Agent 根据需求采用或调整路径，再通过结果修订指导和适用范围。

总体闭环

Coding 负责完成任务并留下实际交互；Post-coding 对照这些记录与工程约束，提出可复用的改进。候选经过人工 Review 和新任务验证，再进入后续执行。

真实任务
  ↓
执行轨迹 + 环境结果 + 人工反馈
  ↓
对照工程约束与已有经验
  ↓
候选改进 → 人工 Review / 修订
  ↓
新 Case 验证 + 既有能力回归
  ├─ 有收益 → 保留 → 下一轮任务
  ├─ 有退步 → 修订 / 删除 → 重新验证
  └─ 证据不足 → 补证 → 重新判断

这一闭环还要作用于 Creator 自身，才能进入 RSI 的递归层：

任务执行反馈 → 改执行方法 → 后续任务检验
提炼与使用反馈 → 改提炼方法 → 后续提炼检验

反馈驱动的工程机制

真实事件为主线，验收记录作为标注

失败前后的输入、工具返回和实际改动，是定位优化点的依据。真实事件流保留过程事实，验收标注将具体片段与任务目标、判断依据和修正关系连接起来。

真实事件流：操作 / 输入输出 / 产物变化 / 人工交互
  ↑ 关联原始事件与证据
验收标注：
  目标 / 标准 / 判定 / 失败点
  重试关系 / Skill 应用

事件中已有的事实 → 直接复用
需要验收语义的部分 → 补充标注

复盘入口：反复失败、无效重试、人工纠正；对照材料：首次成功、修正后的结果。

环境反馈决定优化方向

测试 / 构建 / API / Mock / Browser / Native 提供环境输出，判定时保留验收标准、执行条件和判定来源。

确认缺口 → 选择优化对象
├─ 已有能力未被发现 → 工程信息 / 检索
├─ 指导不适用 → Skill / 适用范围
├─ 证据缺失或不可见 → Tool / 验证入口
└─ 运行环境故障 → 环境修复 / 重新观察

判断一次调整是否可复用，还要对照需求、工程状态和已有经验。

人工驱动提炼，使用结果持续回流

人工补充业务背景、隐含约束和优先级，并修订候选的归因与适用范围。这些反馈与对应候选版本关联，保留取舍依据，供下一轮分析使用。

人工：提出问题 / 补充约束
  ↓
Agent：取证 / 对照工程与经验 / 提出候选
  ↓
人工 Review：评论与理由 ↔ 对应候选版本
  ↓
新 Case：具体 Skill 指导 → 实际行为 → 验收与返工
  ↓
反馈回流 → 保留 / 修订 / 删除指导

改进机制如何进入递归层

如果 Creator 只是把每次失败转成新规则，经验可能越来越多，误用范围也随之扩大。此时需要调整的是证据筛选、同类 Case 比较和验证方法，再检查调整后的提炼质量。

递归发生在改进机制也成为被改进的对象：

Coding 轨迹
→ 改 Skill / Tool / Context → 下一轮 Coding

Skill Creator 的工作轨迹
→ 改取证 / 筛选 / 验证方法 → 下一轮提炼

例如：

人工反复删除过度泛化的规则
  ↓
候选方法：增加反例核查
  ↓
比较候选适用性 / 遗漏 / 人工修订成本
  ├─ 改善 → 更新 Creator 指导或工具 → 下一轮提炼
  └─ 未改善 → 修订 / 放弃该方法

Creator 的输入、取证操作、候选版本、Review 和使用结果，构成这一层的复盘材料。

改进成立的依据

通过某项检查提供的是局部证据；策略是否值得保留，还要观察它在未参与提炼的任务中的表现、代价和回归。对 Creator 的修改，则需要同时检验其产出的候选质量。

比较条件：保留任务输入 / 验收标准 / 执行条件
验证范围：未参与提炼的新 Case + 既有能力回归

执行层：结果改善 / 返工减少 / 成本变化 / 引入的退步
提炼层：候选适用性 / 遗漏 / 人工修订成本
