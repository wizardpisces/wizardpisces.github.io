工程预提炼：从已有实现生成可验证 Skills

背景与目标

工程中的公共能力、成熟实现、文档和测试，已经包含大量可复用的知识。Agent 进入一个新工程时，需要重新发现这些能力、判断适用条件，并理解工程约束。

工程预提炼在需求任务开始前完成这部分知识准备：从已有工程提取有来源依据的候选 Skills，经过验证后供后续任务按需使用。即使工程尚未积累 Agent 执行案例，也可以建立初始指导。

预提炼机制

负责提炼的 Agent 根据目标工程的实际能力和参考实现，生成指导，再检查指导是否准确、可用：

源码 / 文档 / 测试 / 已有 Skills
  → 识别可复用能力与工程模式
  → 取证、比较适用条件
  → 生成候选 Skill
  → 来源核查、能力验证与人工 Review
  → 后续任务采用 → 环境反馈 → 修订

围绕使用问题取证

从组件选型、接口调用、错误处理、测试构造等具体问题入手，检查能力入口、核心实现、真实使用方式和已有验证。提炼范围由使用问题决定，避免将整个仓库机械地转成文档。

例如，标题栏选型需要比较平台组件与存量组件的能力、消费者和限制；接口接入需要识别已有请求封装、错误处理和测试约定。它们共用取证方法，具体指导来自各自工程。

将证据整理为候选指导

候选围绕四个问题组织：

什么时候用 → 适用场景与前提
怎么使用   → 能力入口、参考实现与操作方式
怎么验证   → 已有测试、检查方法与验收条件
依据是什么 → 来源证据、限制与待确认问题

索引用于帮助发现能力，Skill 用于表达应用与验证方法。经过实际任务验证、适合优先采用的工程路径，可以进一步沉淀为 Golden Path。

验证后进入任务使用

预提炼阶段核查引用、接口和适用条件，并通过已有测试、最小示例或局部运行检查指导是否可执行，保留未验证的部分。人工 Review 补充隐含约束和工程取舍。

后续任务检验指导是否被采用、是否减少错误与返工、是否引入回归。能力检查提供初步可用性证据，任务反馈检验实际收益，两者共同修订候选。

与任务后提炼的关系

机制 起点 生成与验证方式
工程预提炼 已有实现、文档、测试与工程约束 生成候选 → 核查与验证 → 任务应用
任务后提炼 执行结果、环境反馈与人工修正 分析执行经验 → 生成或修订候选 → 新任务验证

预提炼提供任务开始时可用的知识，任务后提炼用真实经验校正这些知识。两者共享取证、抽象、Review 和验证能力，前端、后端与测试工程都可以采用。

提炼方法的迁移与改进

任务复盘中积累的提炼方法，可以迁移到新工程。例如，如何定位平台公共能力、比较成熟实现、识别适用边界，以及选择验证证据，都可以指导后续预提炼。

迁移时重新收集目标工程的实现与约束，并检验生成的指导。源工程的经验帮助决定如何取证，目标工程的证据决定具体结论。

随着应用反馈积累，可以继续检查提炼方法：是否遗漏能力、是否过度泛化、哪些候选反复需要人工纠正。由这些结果修订取证与验证方法，逐步改善下一轮预提炼。
