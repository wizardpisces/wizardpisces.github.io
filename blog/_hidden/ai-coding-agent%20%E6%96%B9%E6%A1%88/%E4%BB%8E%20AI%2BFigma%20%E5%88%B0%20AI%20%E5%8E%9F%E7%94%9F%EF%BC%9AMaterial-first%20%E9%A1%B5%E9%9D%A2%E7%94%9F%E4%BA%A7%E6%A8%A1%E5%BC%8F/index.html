从 AI+Figma 到 AI 原生：Material-first 页面生产模式

现在的 Figma-to-Code 已经能做不少事：识别 Figma 页面结构，映射已有物料，生成楼层 JSON，再由渲染引擎输出页面。

它比 Screenshot-to-Code 稳定得多，也更容易校验。问题是，流程仍然从一张自由设计的 Figma 开始。设计完成后，团队才知道现有物料能不能覆盖；不能覆盖，就得重新识别、拼装、补属性，甚至补组件。返工往往发生在最贵的时候。

所以更值得讨论的问题不是“怎么把 Figma 还原得更准”，而是能否换个起点：先让 AI 用已有生产物料生成可运行原型，产品和设计在原型上继续修改；只有现有物料确实不够时，才进入物料扩展或自由设计。

这里说的“AI 原生”不是取消 Figma，也不是让设计师只能从组件库里挑积木。它只是把 AI 和生产物料提前放进设计阶段，让页面从一开始就尽量处在可实现、可运行、可复用的范围内。

先回答：设计团队为什么要用它

Material-first 首先不是一条新的研发交付链路，而应是一套服务设计团队的工作能力。若只强调“用现有物料生成页面”，它很容易被理解成开发用组件库提前约束设计；设计团队自然会担心创造空间、决策权和工作效率受损。

设计师真正需要的不是被告知哪些组件可以用，而是在真实产品约束中，更快地探索、编辑和判断方案。因而这套能力的价值应当是：让设计判断更早、更低成本地落到可运行的产品上，而不是替设计师决定页面。

设计团队获得的能力 解决的问题 典型输入
可运行的设计起点 不必从空白画布开始；能尽早看到真实内容、状态与交互下的页面骨架 PRD、目标用户、内容结构、参考案例
可实现性即时反馈 修改时立即知道哪些可以复用、哪些只缺 Variant、哪些会带来新增实现成本 原型编辑、Figma 组件或 Frame、自然语言意图
设计探索与对比 能快速比较信息层级、布局和视觉方向，再由设计师选择与继续打磨 设计约束、品牌规范、页面目标
设计资产影响力 反复出现且被验证有效的解法，可以由设计团队推动沉淀为公共能力 复用标记、评审意见、跨页面使用证据

因此，它应被定义为一个设计工作台：设计师可以从需求、视觉参考或已有结构开始，得到可编辑、可运行的候选原型；在编辑过程中看到物料覆盖和缺口；再决定复用、修改、扩展还是自由设计。楼层 JSON / Design Schema 是它面向研发的交付结果之一，而不是设计师唯一或首先面对的产物。

设计侧至少应支持三类输入并存：

  • 意图输入：页面目标、用户任务、内容、操作和状态，例如“为运营提供可筛选、可批量处理的任务列表”。
  • 视觉输入：参考图、Figma 片段、品牌规范，或“更低密度、突出风险状态”这类设计方向。
  • 结构输入：已有 Material Catalog、业务数据模型、可用操作，以及端能力边界。

对应的输出也应同时服务设计和研发：可继续编辑的原型、物料构成与覆盖说明、缺口及处理建议、可回流 Figma 或设计工具的稿件，以及最终可被 Runtime 消费的 Schema。

让设计扩展能力，而不是为实现让步

这套模式能否被采用，取决于权责是否清楚：AI 负责生成候选方案、解释覆盖情况和提示代价；设计师拥有体验与视觉的最终决策权；Design System 团队治理公共物料；研发确认实现与宿主边界；产品确认业务取舍。

AI 不应自动把一个页面特例升级为公共组件，也不应因为现有物料无法实现就否决一个设计。它应当把限制、成本和替代方案及时呈现出来，让人可以有意识地选择“复用现有能力”“补一个合理 Variant”“沉淀新物料”或“保留自由设计”。

这样，现有物料是高质量的默认起点，而不是设计上限；物料库也不再只是研发的约束集合，而是设计团队可以持续塑造的生产资产。

最适合的首个验证范围，是物料覆盖较高的标准业务页。验证的不是生成了多少页面，而是设计到实现的往返是否减少、设计师是否愿意从可运行原型开始、缺口是否更早暴露，以及新增物料是否更少但更准确。

现有流程里，AI 其实在 Figma 之后工作

现有链路大致是：

PRD
  ↓
产品 / UED 输出 Figma
  ↓
AI 映射为楼层 JSON
  ↓
Renderer 渲染页面
  ↓
接入业务逻辑

FE AI Code 真正消费的，通常已经不是原始 Figma，而是识别后的组件楼层 JSON。现有方案已经完成了几件重要的事：页面不再由模型直接拼 React 结构，Figma 节点尽量映射到已注册物料，页面结构由 Schema 描述，并通过真实 Runtime Component 渲染。结果还能继续做视觉和运行验证。

它更像 Figma 到 Material Schema 的转换，而不是传统意义上的 Design-to-Code。

为什么 Figma 还原仍然不算闭环

问题不在于页面能不能生成，而在于设计、物料和实现之间仍然是单向关系。

Figma 可以自由表达视觉效果，生产物料却有明确的 Props、Variant、组合关系和运行时限制。团队通常要等到组件识别时，才会知道设计到底能不能直接复用，还是要补 Variant、新增公共组件，或者为当前页面写一次性实现。

设计一改，识别也要重来。节点层级变化、组件实例替换、页面结构调整，都可能让原来的映射失效。即使最后仍由同一组物料实现，Agent 也得重新判断：这次画的还是不是上次那个组件？

这类识别可以越来越准，但它本质上仍是后验推断。只要设计结构或上下文变了，同一块视觉区域就可能得到不同的解释。

物料建设和页面交付也会缠在一起。Agent 发现缺口时，团队一边要赶当前页面，一边要判断这个结构值不值得沉淀为公共能力。交付压力一上来，组件边界很容易做歪。

先生成物料原型，再进入设计

更合适的默认流程可以是：

业务需求
  ↓
AI 理解页面目标、内容、操作与状态
  ↓
基于 Material Catalog 生成可运行原型
  ↓
产品确认信息结构
  ↓
UED 在原型上调整体验与视觉
  ↓
审计物料缺口
  ↓
基础组合 / 扩展 Variant / 新物料 / 自由设计
  ↓
人工确认楼层 JSON / Design Schema
  ↓
FE Code Agent 接入业务逻辑与宿主能力

表面上只是把物料原型提前了一步，实际改变的是工作关系。

过去是设计先给出最终结果，Agent 再寻找实现方式。现在则是 AI 先用真实生产物料给出一个能跑的起点，产品和设计围绕它修改、验证，必要时再突破它。

最终页面仍然可以进入 Figma，设计师也仍然可以大幅调整。区别只在于，团队能更早看见哪些区域已经被稳定覆盖，哪些区域正在偏离现有能力，以及这种偏离值不值得留下。

为什么应在需求原型阶段发现缺口

需求原型是产品意图第一次被组织成页面结构的时候。此时讨论的是页面表达什么、用户怎么操作，而不是“开发周期内怎么把这个视觉效果做出来”。

这时发现缺口，成本最低。设计还没冻结，产品、UED 和开发可以一起决定是调整页面组合、扩展已有物料，还是保留一个新设计。相比开发阶段再补洞，讨论会从容得多。

它也更容易区分需求和物料能力。一个需求无法被现有组件表达，可能只是基础组件换个组合；可能只缺一个合理属性；也可能真的出现了新的稳定 UI 形态。不是每个特殊区域都该变成公共组件。

用真实物料渲染出的原型还能直接暴露排版、状态、交互和内容容量的问题。内容太长、空状态没设计、操作不可用、容器装不下，这些问题不必等到开发后期才出现。

Material-first 不是让设计师迁就组件库

Material-first 最容易被误解成“开发先规定组件，设计只能从中选择”。真这么做，页面会越来越像，组件库里的缺陷也会被固化。

更合理的边界是：已有物料提供默认起点，不是设计上限。

  • 已有物料满足需求，直接复用；
  • 视觉骨架正确，只缺合理属性时，评审是否扩展 Variant；
  • 多个页面反复出现新的稳定骨架时，作为公共物料候选；
  • 当前页面的特殊排列，保留为页面组合；
  • 现有物料已经影响体验时，允许 UED 自由设计。

设计师仍然负责体验和视觉判断。变化只是，设计偏离生产物料时，这种偏离会被及时记录和评估，而不是拖到开发阶段才被动发现。

缺口可以前移，物料泛化不能自动化

需求阶段适合提前发现缺口，却不适合自动把缺口塞进组件库。

过去：Figma 未覆盖区块 → 识别视觉骨架 → 判断是否新增公共物料
未来：需求无法由现有物料表达 → AI 生成候选页面结构 → 产品 / UED 验证 → 依据复用证据决定是否进入 Catalog

简单结构可以继续用基础组件组合；页面特例留在当前页面；复用证据不足的结构先作为候选物料。只有形态稳定、输入可参数化、且有复用证据的结构，才经人工 Review 进入公共 Catalog。

这样既能减少开发阶段补漏，也不会让 AI 因为每一份 PRD 都往物料库里塞新东西。

Figma 仍然有位置

Figma 不需要退出流程，只是不再是所有页面唯一的起点。

对于标准业务页面，AI 可以先生成真实物料组成的原型，UED 再在 AJR Designer 或 Figma 中继续编辑。到底以哪个工具为主，是后续产品形态要验证的问题，不影响 Material-first 的原则。

对于营销创意页、新交互、复杂动画或现有物料完全覆盖不了的体验，仍然可以采用 Figma-first。设计确定后，再进入组件识别、物料审计和楼层 JSON 生成。

存量 Figma 页面、外部团队设计和非标准组件库稿件，也仍然需要 Figma Parser 和 Recognition。目标不是删掉 Figma-to-Schema，而是少做那些本可避免的全量逆向识别。

如果 Figma 使用官方组件实例，应该优先通过稳定的 Component ID 和 Variant 直接映射；自由 Frame、Detached Instance 和未知结构，才交给 AI Recognition。

两条路径汇聚到同一种 Schema

不需要为新流程重新建设一套 FE AI Code 渲染体系。两条路径最终仍然汇聚到同一种楼层 JSON / Design Schema：

现有路径：Figma → 自动识别与映射 ────────┐
                                         ├→ 楼层 JSON / Design Schema
新增路径：需求 → 物料原型 → 设计确认 ────┘
                                                     ↓
                                             AJR Runtime 渲染
                                                     ↓
                                             FE 业务逻辑接入

一条是逆向路径：Figma → Recognition → Schema。另一条是正向路径：Material Catalog → Prototype → Schema。

后面的 Renderer、Runtime、Code Agent、测试和视觉校验能力都可以复用。这样既不浪费已有 Figma 还原能力，也能按页面类型逐步引入新模式；同一页面甚至可以混用两种来源。

结语

现有 Figma 还原流程本身很有工程价值，真正需要调整的是物料进入流程的时机。

过去，物料在 Figma 完成后等待匹配。现在，物料可以在需求原型阶段参与页面生成。设计师依然可以复用、修改，甚至推翻这个起点；无法覆盖的部分也能更早进入物料补充和设计评审。

从“AI+Figma”走向“AI 原生”，不是不用 Figma，也不是让 AI 直接替人决定页面。它更像是把“设计完成后寻找实现方式”，改成“先用真实生产物料生成可运行原型，再由人决定复用、修改还是创新”。

这件事的成败也不取决于 AI 能否替设计师画得更快，而在于它是否能给设计团队增加能力：在可运行的真实约束中探索，在偏离既有能力时看清代价，并把值得复用的设计选择沉淀为共同资产。
