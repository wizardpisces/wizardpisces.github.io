一种 AI 负责生成，另一种负责决定：Jev 想验证什么？

最近有个叫 Jev 的模型引起了讨论。

它不是用来聊天的，也不是用来写代码的。

它更像一个专门给软件调用的“决策模型”：

这个请求属于哪个团队？
用户是不是想退款？
这条内容要不要转人工？
这个文档和问题到底相关不相关？

很多人第一反应是：

这不就是让 GPT 做分类吗？

Jev 真正想验证的，不是模型能不能选出一个答案，而是：

软件是不是需要一种专门负责“做判断”的模型？

先看一个普通的客服系统

用户发来一句话：

支付接口一直超时，订单提交不了，麻烦赶紧处理。

人一看就知道，这大概应该交给技术团队，而且优先级不低。

但程序真正需要的不是一段解释，而是几个可以直接执行的字段：

{
  "department": "technical",
  "urgent": true
}

接下来业务代码才能继续：

用户输入
   ↓
判断意图
   ↓
结构化结果
   ↓
业务代码
   ↓
分配团队 / 提高优先级 / 转人工

以前可以写规则：

if "退款" in text:
    department = "billing"
elif "接口" in text:
    department = "technical"

但用户不会永远按照你的关键词说话。

“钱没回来”“扣款失败”“订单卡住了”，都可能是在说支付问题。

规则一多，判断逻辑就开始膨胀。

于是我们把这一步交给大模型：

请判断这个工单属于哪个团队。
只返回 billing、technical 或 other。

这已经能工作。

问题是，大模型通常在生成答案，而软件经常只需要一个决定：

要不要转人工？
该走哪条路？
这个结果有多可靠？

假设两个模型都把工单分给 technical：

technical

但它们的把握完全不同：

模型 A：
technical  0.99
其他       0.01

模型 B：
technical  0.36
billing    0.34
other      0.30

答案一样，程序的动作却不该一样。A 可以自动分流，B 更适合转人工。

这里就出现了 Jev 想重点处理的东西：Calibration，校准。

假设模型对 1000 个请求都给出 80% 的信心。校准得好，这批请求里应该大约有 800 个判断正确：

模型说 80% 的样本
          ↓
长期来看约 80% 正确

只有这样，下面的代码才有意义：

if confidence < 0.8:
    human_review()
else:
    route_automatically()

如果模型总是自信满满，但 80% 的判断只对了一半，这个数字就只是包装。

Jev 想把这一步单独做成模型

Jev 的输出可以压缩成三类：

Choice
→ 从有限选项中选一个

Yes / No
→ 判断一件事是否成立

Score
→ 按明确标准给出分数

例如：

Choice：这个工单交给 billing 还是 technical？

Yes / No：用户是否明确要求退款？

Score：这个问题对用户影响有多大？

这些任务本身并不新。分类模型、意图识别和排序模型早就存在。

Jev 想做的，是把这类“软件需要的判断”单独优化成一种模型能力：

请求
  ↓
Decision Model
  ↓
选择路由、判断风险、决定是否继续
  ↓
LLM / Tool / 人工

为什么不让一个大模型全包？

一个通用模型完全能同时完成：

理解请求
判断意图
写回复
调用工具
总结结果

但“全包”会带来几个工程问题。

第一，输出太自由。

你想要三个类别，它可能顺手加一段解释；你想要 true，它可能返回“看起来大概率是”。

第二，成本和延迟更高。

一个只需要判断“要不要转人工”的任务，不一定值得调用最强的生成模型。

第三，判断和执行混在一起。

模型一边判断，一边生成回复，一边决定是否调用工具。出了问题，你很难知道错在理解、路由，还是后面的业务逻辑。

拆开以后，系统更像普通软件：

Decision Model
→ 负责判断

业务代码
→ 负责执行确定规则

LLM
→ 负责生成复杂内容

这不是让系统更“聪明”，而是让每个环节的责任更清楚。

结构化输出也不等于判断正确：

Schema 正确 ≠ 语义正确 ≠ 业务动作正确

所以 Decision Model 最终还是要用真实业务数据看准确率、校准度、延迟和成本。尤其是校准度，如果概率不能指导“自动处理还是转人工”，它和普通分类器的区别就会小很多。

Jev 真正要证明什么？

不是：

我也能分类。

因为 GPT、Claude、Qwen 甚至一个微调后的开源模型都能分类。

它真正要证明的是：

在相同判断质量下
→ 更便宜
→ 更快
→ 概率更可靠
→ 更容易被程序直接调用

这也是“Decision Model”值得单独讨论的原因。

如果未来通用模型已经足够便宜、足够快，而且能稳定输出校准良好的判断，那么独立决策模型的空间会变小。

但如果软件系统里确实有大量：

不需要长篇生成
却需要稳定判断
需要概率
需要低延迟

那么把这类能力单独优化，仍然可能有价值。

回到最开始的问题

一种 AI 负责生成，另一种负责决定：Jev 想验证什么？

因为“写答案”和“决定系统下一步怎么走”，是两种不同的工作。

前者追求表达、组合和完整生成。

后者追求有限选项、稳定概率和可执行结果。

Jev 现在还不能证明 Decision Model 会成为下一代基础模型。

但它提出了一个值得关注的问题：

软件需要的 AI，是否不应该只有一种形态？

有的模型负责生成。

有的模型负责检索。

有的模型负责排序。

也有的模型，只负责告诉程序：

现在该走哪条路。
