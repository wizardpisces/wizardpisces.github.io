写 Skill 的 Skill，怎么知道自己写对了？

最近我给 Codex 增加了一个面试评价 Skill。

它要做的事情不复杂：读取候选人的简历、面试记录和笔试结果，整理出可以录入招聘系统的评价。

帮我完成这件事的，也是一个 Skill，名字就叫 skill-creator。

也就是说，我用一个 Skill，创建了另一个 Skill。

OpenAI 和 Anthropic 都提供了官方 skill-creator。但它们对同一件事有一个很有意思的分歧：一个 Skill 写到什么程度，才算完成？

我给它写了明确的边界：

  • 每个判断必须绑定面试证据；
  • 证据不足时不能强行给录用结论；
  • 不得使用年龄、性别、婚育等与岗位无关的信息；
  • 默认控制在五百字以内；
  • 只负责评价，不负责设计面试题。

文件写完以后，OpenAI 的校验脚本给出结果：

Skill is valid!

看起来已经完成了。

但这个结果只回答了一件事：文件结构没有明显问题。

它没有回答，用户说“帮我看看这个候选人怎么样”时，Agent 能不能想到使用这个 Skill；也没有回答，用户说“帮我设计几道面试题”时，它会不会误用；更没有回答，加载 Skill 以后，评价是否真的比原来更可靠。

一份 Skill 可以完全合法，却没有带来任何新能力。

能被系统接受，只是第一道门

结构校验很有必要。

它可以检查 frontmatter、名称、目录和未完成的模板占位，避免 Agent 连 Skill 都读不进去。就像代码首先要通过语法检查。

问题是，Skill 不是普通程序。

程序被调用以后，通常会从确定的入口开始执行。Skill 在执行之前，还要先经过一次选择：

用户提出请求
      ↓
Agent 判断哪些 Skill 可能相关
      ↓
加载完整 SKILL.md
      ↓
模型理解并执行其中的规则

如果 description 只写“帮助处理面试”，它可能在真正需要评价时没有被选中，也可能在准备题目、安排日程和写招聘文案时频繁误触发。

正文写得再完整，只要第一步没有选中，后面的内容就没有机会生效。

Skill 通过结构校验以后，接下来要检查的不是规则够不够多，而是它能否在正确的任务上出现。

OpenAI 先防止 Skill 被设计坏

OpenAI 官方 skill-creator 花了很大篇幅处理设计问题。

它首先提醒：Codex 本来就具备通用能力。Skill 应该只保留那些会改变判断、提高稳定性，并且值得未来任务重复使用的信息。

这会带来一组很克制的选择：

一次性要求              → 留在当前任务
仓库始终适用的规则       → 放进 AGENTS.md
可复用的判断与工作流     → 做成 Skill
确定且反复执行的操作     → 写成 script

Skill 内部也要继续分层。名称和 description 负责发现，SKILL.md 负责执行，条件知识放进 references，确定性操作交给 scripts，输出需要的模板才放进 assets。

这套设计防的是 Skill inflation：只因为一个任务做过一次，就建立一个新 Skill；只因为某些资料可能有用，就全部塞进上下文；只因为规则越多看起来越专业，就把模型原本会做的事情重新教一遍。

在这套思路里，Skill 很像一个软件模块。职责要窄，接口要清楚，每一层复杂度都要有购买理由。

但模块设计得合理，仍然不代表用户得到了改善。

合适的 Skill，也可能没有增量

假设面试评价 Skill 已经能准确触发。

我们给它一份完整的面试记录，它生成了一段结构清晰、事实充分的评价。这个结果依然不能证明 Skill 有价值。

因为没有 Skill 时，当前模型也许已经能写得一样好。

要判断它有没有用，需要比较：

没有 Skill：原本能做到什么
加载 Skill：哪些结果发生了变化

面试评价至少要检查几种不同情况：

典型请求：材料完整，要求形成评价
证据不足：只有“感觉不错”，却要求直接决定录用
相邻请求：要求设计面试问题，不应该触发评价 Skill
敏感信息：材料包含年龄、婚育或照片评价
矛盾证据：项目表现很好，但基础题回答较弱

如果两种情况下都能绑定事实、避免敏感判断，并在信息不足时保留不确定性，那么这个 Skill 可能只是改变了格式。

如果加载以后反而机械凑齐五个部分，把原本一句话能说清的判断写成五百字，它甚至可能让结果变差。

Skill 的价值不能用“写了多少规则”衡量，只能看它是否修复了一类原本会重复出现的失败。

Anthropic 把草稿当成实验的起点

Anthropic 官方 skill-creator 对这层问题更激进。

Skill 草稿完成后，它会继续构造测试任务，分别运行 with-skill 和 baseline，保存真实输出，再根据结果设计可检查的断言。

例如对面试评价，可以检查：

是否引用了材料中的具体事实
是否在证据不足时避免强结论
是否排除了与岗位无关的敏感信息
是否错误处理了不属于该 Skill 的请求

难以用规则判断的表达质量，则可以交给人工评审或盲评：评审者只看两份结果，不知道哪份来自新版本，避免因为“这是刚优化过的”就下意识认为它更好。

description 也可以单独测试。一组请求应该触发，另一组不应该触发，再观察它的精确率和召回率，而不是由作者读一遍后宣布“已经写清楚了”。

这套方法把 Skill 当成一次对模型行为的干预。既然执行者不是确定性运行时，效果就不能只靠静态阅读判断。

Skill 同时面对两种不确定性

OpenAI 和 Anthropic 看起来走了两条不同的路线，是因为 Skill 同时面对两种不确定性。

第一种发生在加载之前：

Agent 会不会认为当前任务需要这个 Skill？

第二种发生在加载之后：

模型会怎样理解这些规则，它真的会因此做得更好吗？

前一种要求清楚的职责、description 和边界。后一种需要真实任务、baseline 和回归测试。

只有设计，没有实验，容易得到一份看起来很专业却没有增量的 Skill。只有评测，没有设计，也可能在几道测试题上不断调参，最后得到一份更长、更僵硬、只适合测试集的说明。

两套 creator 处理的是前后相接的两层问题。

OpenAI 主要回答：怎样让另一个 Agent 正确理解这份能力。

Anthropic 接着追问：理解以后，怎样证明行为真的发生了改善。

一个 Skill 要过四道门

回到开头的面试评价 Skill。

Skill is valid! 只说明它过了第一道门：

可装载：结构正确，系统能够发现和读取
        ↓
可路由：该用时触发，不该用时保持沉默
        ↓
有增量：结果稳定优于 baseline 或旧版本
        ↓
可维护：提升足以覆盖 token、时间和维护成本

不是每个 Skill 都需要完整 benchmark。

一个低风险、偶尔使用的个人 Skill，跑几个真实任务已经足够。会反复影响团队交付的 Skill，需要典型、相邻和不应触发的测试。涉及财务、招聘、发布和外部副作用时，才值得增加断言、回归测试和盲评。

评测本身也有成本。测试集可能过窄，评分器可能偏爱某种写法，复杂 workspace 还会产生新的文件和上下文负担。为了证明一个几十行的 Skill 有效，搭出一套小型 CI，同样可能是过度设计。

一个 Skill 不能因为文件通过校验，或者某个评测数字变绿，就宣布完成。

它应该在正确的时候出现，修复一类明确的失败，并且带来的改善值得长期维护。
