DeepSeek Harness 明明有沙箱，Agent 为什么还能给自己开门？

把 Coding Agent 交给一个陌生项目之前，很多人会先确认一件事：

它是不是运行在沙箱里？

有沙箱，Agent 就算被仓库里的恶意文字骗去执行命令，也只能在允许的目录里活动。它看得到项目，可以改代码、跑测试，却碰不到项目外的文件。

至少我们希望如此。

最近披露的 DeepSeek Harness 漏洞却出现了一个很奇怪的结果：Agent 明明还在沙箱里，却能通过一次本地请求，把自己的权限改成 danger-full-access，同时关掉审批提示。

之后的命令，便不再受原来的沙箱约束。

这里的 Agent 不会凭空发现漏洞并主动越狱。攻击成立的前提，是它把仓库或网页里的恶意内容当成任务指令，执行了攻击者诱导的命令。可这恰好是沙箱要兜住的错误。

这次出问题的不是沙箱被打穿了。

沙箱工作得好好的，只是被关在里面的 Agent，找到了控制门锁的按钮。

沙箱其实拦住了它

DeepSeek Harness 是一套运行 Coding Agent 的开源系统。Agent 可以读取代码、调用模型，也可以使用 Bash 执行测试和修改文件。

有了这些能力，Agent 才能真的干活。风险也跟着进来了。

代码仓库里的 README、Issue、网页内容，甚至某个不起眼的注释，都可能混入针对 Agent 的恶意指令。模型一旦把它当成任务的一部分，就可能执行原本不该执行的命令。

因此，Harness 会把命令放进操作系统沙箱，限制它能访问和修改哪些文件。

发现漏洞的 OX Research 做了一个对照实验：让两个会话执行同一条写文件命令，目标位于工作区之外。

没有利用漏洞的会话失败了。

利用漏洞后的会话成功了。

原来的沙箱不是摆设。它确实拦住了越界写入。

问题发生在文件隔离之外。

文件出不去，网络还通着

一个程序被限制写文件，不等于它与宿主机完全断开。

DeepSeek Harness 当时的沙箱配置主要收紧了文件访问，却没有隔离网络。沙箱里的命令仍然可以访问宿主机的回环地址，也就是通常所说的 localhost。

而 Harness 恰好在本机运行着一个 HTTP API。

这个 API 能修改 Agent 的权限，也能关闭危险操作前的人工确认。

原本看起来没有关系的两件事，就这样接上了：

沙箱里的 Agent
   ↓
可以访问 localhost
   ↓
调用 Harness 控制 API
   ↓
修改自己所在会话的权限
   ↓
后续命令不再受限

Agent 怎么走进了用户入口

Harness 里有两种角色：Agent 在沙箱里干活，用户通过浏览器管理它。修改权限的 API，原本是留给用户界面的。

问题是，沙箱里的 Agent 也能访问这个 API。当时的接口没有用身份凭证确认调用者，只检查请求里的 Host 是否像本机地址。Agent 运行的命令行程序同样可以满足这个条件。

于是，Agent 发出的请求走进了用户入口，权限变更也被记录成了用户操作。

Harness 知道自己正在修改 Agent 的权限，却不知道按下按钮的就是 Agent。

为什么“加了沙箱”还是不够

我们通常把权限控制想成一堵墙：

Agent 能访问什么？
Agent 能修改什么？

这个漏洞多问了一层：

Agent 能不能接触修改这些规则的入口？

如果答案是能，那么第一层限制再严，也可能被第二层重新配置。

这和服务器把普通用户关进受限账户，却又允许他调用一个无需认证的管理员接口没有本质区别。普通用户不必攻破操作系统，只要请管理员接口替自己完成提权。

沙箱负责限制 Agent 的行动范围，控制面负责定义这个范围。两者放在同一套系统里很正常，但信任方向必须是单向的：

控制面可以收紧或放宽沙箱

沙箱中的进程不能反过来控制控制面

问题就出在这条反向通路上。

我们之前常说，Agent 不只是模型加工具，还需要 Runtime 管理 Session、权限、审批和沙箱。Runtime 的确能让 Agent 更可靠，但当这些能力集中到一起，它也会成为一个权限很高的控制中心。

Agent 能碰到哪些文件固然重要。Agent 能不能修改“自己可以碰哪些文件”，更重要。

修复为什么不在沙箱里

DeepSeek 已在 0.1.2-alpha.1 中修复这个问题。新的设计为浏览器访问增加了身份凭证，不再把 Host 和 Origin 当成用户身份；官方也收紧了非本机监听方式。

这次修复没有继续收紧文件隔离，因为失败的位置不在那里。

真正需要补上的是控制面的认证，以及受限进程与控制面之间的边界。

对正在使用旧版本 DeepSeek Harness 的人，最直接的处理是升级到 0.1.2-alpha.1 或更新版本。若要让 Agent 处理不可信仓库和网页，仅依赖应用自带的沙箱仍不稳妥。DeepSeek 的安全说明也明确建议使用低权限账户，并优先放进一次性虚拟机、容器或专用环境。

比那条利用命令更值得留下来的，是一个容易被忽略的边界：

真正需要隔离的，不只是 Agent 的行动，还包括它修改行动边界的能力。

沙箱可以把 Agent 关在房间里。

但控制门锁的按钮，不能也留在房间里。
