AI 只会输出文字，怎么就能自己操作电脑？

你让 AI 帮你买一样东西。

它打开网页，找到“立即购买”，点了下去。对你来说这是两秒的事。

可模型没有手。它接受的输入是文字，吐出来的也是文字，甚至不知道鼠标长什么样。

那最后，屏幕上那个按钮为什么真的被点中了？

答案不是“AI 有了自己的电脑”。是有一整套东西，把模型输出的文字翻译成屏幕上的动作，再把屏幕的变化翻译回文字交给它看。这套东西通常被称作 Computer Use。

这一篇，就从这一次点击开始，把它一层一层拆开。

一、模型没有手，只能把动作说出来

模型处理的是 token。要让它操作电脑，第一步就绕不开：怎么把屏幕变成它能读的东西。

答案朴素得有点意外——截图。

一张截图就是一张图片，而现在的多模态模型恰好能直接看图。屏幕上的按钮、输入框、弹窗，于是全都变成模型输入里的一块像素。

这里有个容易被忽略的限制：模型看到的是一帧，不是一段视频。它没有实时的眼睛，只有一张张独立的画面。所以每做一步，都得重新截一张图递过去，让它知道现在屏幕上是什么样子。

截图也只是它能看到的表示之一，并不等于“它看到了我们看到的界面”。这一点在《AI 操作电脑时，它看到的真是我们看到的界面吗？》里单独展开过。

输出这一侧同样受限。模型不能说“我点了”，只能输出“请点击某个位置”。换句话说，它把动作“说”出来，交给外面的程序去执行。

于是有了一套约定俗成的动作协议。常见的不外乎这几个：

点击    输入    按键    滚动
拖拽    等待    截图    ……

不同平台的清单和命名不完全一样，但都在做同一件事：把一次操作描述成一条可以执行的数据。

以 OpenAI 的接口为例，一次调用大概是这个形状：

{
  "type": "computer_call",
  "action": { "type": "click", "x": 523, "y": 318 }
}

注意，这条消息里没有任何东西被执行。模型只是产生了一份“我希望点这里”的说明。真正按下鼠标的，是它之外的程序。

二、坐标不是随便写的两个数字

模型说 (523, 318)，程序要把它变成一个真实的屏幕坐标，中间还有一步换算。

不同平台的做法不一样。有的直接给截图上的像素坐标；有的先归一化成相对坐标——例如把宽和高都映射到 0 到 1000 的整数，再由执行器按真实分辨率换算回去。OpenAI 的文档就专门提醒：如果你把截图缩小过，执行动作前要把模型给出的坐标映射回环境本身的坐标系。

真正难的不是这套换算，而是模型要指得准。

模型认出：
“最下面是登录按钮。”            ← 容易

模型指出：
“按钮的左边界在第 90 列，
  上边界在第 500 行……”           ← 容易偏

认出“这是什么”，允许位置、大小和样式变化；指出“它在哪里”，却必须保留精确边界。小图标、密集列表、长得几乎一样的按钮，都会让这一步漂移。这个缺口在《模型能叫出按钮的名字，为什么指不准它在哪里？》里展开过。

一种常见的补法是：把“报坐标”换成“选编号”。系统先用检测器把可操作区域框出来，画上编号，模型只需要回答点哪个编号，再由程序查表得到坐标。精确位置来自前面的检测器，模型只负责在有限候选里做选择。这套做法见《给按钮画上框和编号，模型为什么突然指得更准了？》。

定位问题没有被消灭，只是被挪到了更适合的部件上。

三、一次动作不算任务，要把它变成循环

到这里，模型有了眼睛（一张截图），也能产出一条可执行的动作。但这只是一个回合。

真正让它变成“能干活”的，是把这个回合放进一个循环：

截取当前屏幕
      ↓
模型看懂界面、决定下一步
      ↓
环境执行动作
      ↓
重新截图  ←──────────┐
      ↓               │
  回到第一步 ─────────┘

为什么非要闭环？因为模型看不到自己动作的后果。它点了按钮，页面会不会跳转、会不会弹窗、内容加载完了没有——这些只有下一张截图才能回答。

这也是它和“一次问答”最本质的区别：问答说完就结束，循环会一直转，直到任务完成，或者步数耗尽。各家平台的文档几乎都会写同一句提醒：把 computer use 放在一个循环里运行。

四、从一步到几十步，它凭什么不迷路

一个真实任务很少只有一步。订一张票、填一份表，动辄几十步。

每一步都要重新截图、重新推理，所以模型必须记住三件事：原本要做什么、已经走到了哪一步、之前哪条路走不通。

这份记忆，说到底就是它的上下文窗口。任务目标、已完成步骤、失败的尝试，都塞在里面。

于是长任务最怕两件事：一是越走越偏却浑然不觉，二是反复踩进同一个坑。工程上的对策也很朴素——把大任务拆成可确认的子目标，设置最大步数及时止损，失败时退回上一个稳定状态重来。

OSWorld 这类基准衡量的正是这一段：在 Ubuntu、Windows、macOS 的真实网页与桌面应用里完成开放式任务，而不是回答一个问题。

五、模型之外还有一层：谁来真正动手

再说清楚一次：模型自己碰不到你的电脑。

它全程只输出“点这里”“输入这些字”这样的文字。真正动手的是另一层，一个跑着浏览器和桌面的虚拟机或容器，也就是它的手。

模型  →  动作  →  环境执行  →  新截图  →  回到模型
        （一次网络往返）

这条链路是串行的，每转一圈都要一次网络往返。这也解释了它为什么慢：人点一下是一瞬间，Agent 点一下是一次推理加一次往返。

把这层单独隔离出来，首要目的是安全。哪怕模型真的乱点，破坏也被关在一个与真实设备隔开的沙箱里。

六、不是所有 Agent 都靠“看”

“截图加坐标”只是其中一条路。

另一条路绕开画面，直接读网页的 DOM 树或无障碍树，拿到一份元素清单，然后说，点第 12 个元素。它更准、更快，但只在有结构可读的场景里成立——主要是网页。

这也不是万能的。无障碍树和 DOM 只暴露了系统愿意暴露的那一层；很多桌面软件和画布应用根本没有这样一层结构。所以现实中更常见的是混合：截图负责看清样子，结构信息负责精确定位。

Agent 看见的，始终是系统暴露给它的那层表示，而不是我们眼里那块屏幕。

七、所以它今天还是很难

原理讲完，难点全在细节里。

定位   小图标、密集布局、低清截图，误差都会被放大
延迟   每一步一次推理加一次往返，几十步叠起来是分钟级
幻觉   模型可能“以为”自己点了，其实什么也没发生
安全   网页里的诱导性文字可能骗它做危险操作；
       涉及登录、支付的动作，通常必须停下来等人确认

Anthropic 的文档也在显眼位置提醒：当前 computer use 的延迟，和人类直接操作相比仍然偏慢。这四条里，任何一条没处理好，用户看到的结果都一样——它又卡住了。

最后，回到那个按钮

把这一次点击拆开，能看到四个角色：

模型      看懂界面、决定下一步
动作协议  把决定变成可执行的数据
循环      执行、再观察、再纠正
执行环境  真正动手，并把破坏关起来

模型只做它擅长的那部分：理解用户想干什么，然后在有限选项里做选择。精确位置、状态记录、权限控制，都被交给了更合适的部件。

所以“AI 会操作电脑”不是模型突然长出了一只手。是有人替它搭了一套手眼，再让它在一个循环里一点点逼近目标。

原理可以压成一句话：会看图的模型，加一套动作协议，放进观察、行动、再观察的循环，跑在一层隔离的执行环境里。循环本身并不复杂，难的是让循环里的每一步都足够准、足够快、足够安全。
