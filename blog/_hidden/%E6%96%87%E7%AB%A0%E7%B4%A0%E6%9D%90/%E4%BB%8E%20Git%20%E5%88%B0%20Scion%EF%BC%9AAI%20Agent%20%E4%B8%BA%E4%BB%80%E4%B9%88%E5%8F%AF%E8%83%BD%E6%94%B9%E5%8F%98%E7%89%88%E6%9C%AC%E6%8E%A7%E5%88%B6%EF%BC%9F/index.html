从 Git 到 Scion：AI Agent 为什么可能改变版本控制？

当数百个 AI Agent 同时参与一个代码仓库的开发，每个 Agent 真的还需要一套完整的本地仓库吗？

这既是资源优化问题，也涉及版本控制系统的基本架构：代码应该存在哪里？版本状态由谁维护？多个 Agent 如何共享数据、提交变更和完成合并？

Git 的设计非常成功，但它诞生时主要面对的是人类开发者。开发者拥有自己的本地仓库，独立工作，再通过 Push 和 Pull 与其他人协作。

AI Agent 带来了不同的工作模式：大量任务并发执行，工作区使用时间短，创建和销毁都很频繁，每个任务可能只修改几个文件。

Anthropic 推出的 Scion，正是在探索这种新工作模式下，版本控制系统是否需要重新设计。

它最值得关注的地方，不是发明了一种比 Git Diff 更先进的差异记录方式，而是重新组织了客户端、服务端和共享数据之间的关系。

1. Git 的设计假设，遇到了新的工作负载

Git 是分布式版本控制系统。每个开发者通常拥有一份本地仓库，可以在本地创建分支、提交代码、查看历史，最后再与远端同步。

             Git Server
            /     |     \
       Agent A  Agent B  Agent C
          |        |        |
       Local     Local     Local
       Repo      Repo      Repo
          |        |        |
       Commit    Commit    Commit
          \        |       /
                 Push

这种设计很适合人类开发者。

一个开发者通常长期使用同一个工作区，仓库数据可以反复利用。即使断网，也能继续提交和查看历史。

但 Agent 的工作方式不同：

  • 一个任务可能启动多个 Agent 并行处理；
  • 每个 Agent 可能只修改少量文件；
  • Agent 生命周期短，任务结束后工作区可能被销毁；
  • 大量任务需要频繁创建、检出和合并工作区。

假设一个 Monorepo 有 100 GB 数据，一个 Agent 只需要修改支付模块的三个文件。

如果同时启动数百个 Agent，除了修改这三个文件，还要高效地创建、管理和回收大量工作区，避免重复维护和处理相同的仓库数据。

Git 已经有浅克隆、Sparse Checkout、Partial Clone 等优化手段。但这些优化并没有改变它围绕客户端本地仓库组织工作的基本模式。

问题由此变成：

当大量 Agent 只需要仓库的一小部分，却要频繁创建和销毁工作环境时，让每个 Agent 都独立维护一套仓库，还是最合适的方案吗？

2. Scion：从客户端自治到服务端协调

Scion 重新设计了版本控制系统的架构，变化不止是给 Git 增加一个远程服务器。

在 Git 中，客户端持有仓库数据，并在本地执行大量版本控制操作。

在 Scion 中，服务端承担权威版本状态和核心版本控制操作。客户端不必像传统 Git 客户端一样持有完整历史，工作区也不必各自维护一套完整的仓库数据。

                  Scion Server
          版本状态 / 历史 / 版本控制操作
                       |
          +------------+------------+
          |            |            |
       Content       Cache        Index
       Storage       Layer     派生数据
          |            |            |
          +------------+------------+
                       |
             共享数据与服务能力
                 /     |     \
             Agent A Agent B Agent C
                |      |      |
             Working Files / Workspace

这里需要区分两个概念：

  • Workspace：Agent 实际执行代码任务的工作区，仍然需要读取和修改文件。
  • Repository：版本控制系统管理的版本数据、历史和对象等。

Scion 试图减少的是每个客户端独立维护完整仓库数据的成本，而不是让 Agent 不再需要工作目录。

这种架构的目标，是让多个 Agent 尽可能共享底层数据和服务端能力，减少各自重复维护和处理相同仓库信息的成本。

系统优化的重点也随之改变：

从优化单个开发者的本地操作，转向优化大量并发任务的工作区创建、数据访问和版本控制操作。

3. Changeset：它和 Git Diff 到底有什么区别？

这是理解 Scion 时最容易产生误解的地方。

一种常见说法是：Git 保存快照，Scion 保存 Diff。

但这并不准确。

Git 并不是每次提交都复制全部文件。一个 Git Commit 指向一个 Tree，Tree 描述当前版本的目录和文件状态。文件内容存储在 Blob 对象中，通过内容寻址和对象复用，未修改的文件可以继续引用原来的 Blob。

例如：

Git Commit A
├── payment.go -> P1
├── order.go   -> O1
└── user.go    -> U1

Git Commit B
├── payment.go -> P2
├── order.go   -> O1
└── user.go    -> U1

B 只修改了 payment.go，其他文件不需要重新存储。

所以，Git 本身已经具备很强的增量复用能力。

Scion 的 Changeset 则是版本模型中的一等概念。可以把它理解为：一个版本通过父版本和本次变化来表达。

例如：

Version A
├── payment.go -> P1
├── order.go   -> O1
└── user.go    -> U1
       |
       | Changeset B
       | payment.go: P1 -> P2
       v
Version B
├── payment.go -> P2
├── order.go   -> O1
└── user.go    -> U1
       |
       | Changeset C
       | order.go: O1 -> O2
       v
Version C
├── payment.go -> P2
├── order.go   -> O2
└── user.go    -> U1

每个 Changeset 关联父版本，并记录相对于父版本发生的变化。

沿着版本关系，可以确定某个版本对应的文件状态。实际系统还会使用索引和派生数据加速查询，不需要每次从最早版本开始重放所有变化。

两者的区别可以这样理解：

对比维度 Git Scion
版本表达 Commit 指向描述当前状态的 Tree Changeset 表达相对父版本的变化
内容存储 Blob 对象，支持内容复用 内容寻址的内容存储
版本关系 Commit 通过父提交关联 Changeset 通过父版本关联
核心工作模式 客户端持有仓库并执行大量操作 服务端承担权威状态和核心操作

Scion 把 Changeset、内容存储、共享缓存、服务端计算和历史索引放在一起设计，组成一套共享的版本服务。

4. 它和 Google Docs 的协同编辑有点像

可以做一个有限的类比：多个参与者不再各自维护一份完全独立的数据，而是围绕共享状态提交变化，由系统负责协调。

但两者解决的问题并不相同。

Google Docs 面对的是实时协同编辑。多个用户可能同时修改同一段文字，系统需要协调细粒度的编辑操作，常见技术包括 OT 和 CRDT。

Scion 面对的是代码版本管理。它协调的是文件级版本变化，以及这些变化之间的父子关系、分支和合并。

可以简单对比：

Google Docs
用户输入字符
      |
字符级操作协调
      |
共享文档状态

Scion
Agent 修改文件
      |
文件级版本变化
      |
版本关系与合并

两者相似的地方在于：都需要面对多个参与者同时修改共享数据时的协调问题。

5. 服务端协调也有代价

把更多操作放到服务端，可以减少客户端重复维护和计算，但也会把压力集中到基础设施。

例如，多个 Agent 同时提交变更，服务端就需要处理：

  • 大量并发读写和版本状态更新；
  • 合并计算带来的 CPU 和内存压力；
  • 并发调度、资源竞争和请求排队；
  • 服务端故障对多个 Agent 的同时影响。

而且，服务端合并并不意味着冲突消失。

如果两个 Agent 修改了同一段代码，系统仍然需要判断能否自动合并。无法自动解决时，仍然需要人工或 Agent 介入。

一部分原本分散在客户端的复杂性，就这样转移到了统一的服务端基础设施，并没有消失。

这种设计是否划算，取决于并发规模、任务特征和基础设施能力。

6. 软件基础设施都要为 Agent 重做吗？

不必。

Git 的分布式设计有明确价值：离线可用、客户端自治、生态成熟，也适合绝大多数团队的开发方式。

Scion 解决的是另一类问题：当大量短生命周期 Agent 并发操作同一个大型代码仓库时，传统客户端仓库模式可能产生过高的资源和协调成本。

判断一个基础设施是否值得为 Agent 重构，可以先看三个问题：

  1. Agent 是否大量并发运行，而不是少量、长期运行？
  2. 是否存在大量重复的数据维护、检出和计算？
  3. 这些重复成本是否已经成为系统的主要瓶颈？

如果答案都是肯定的，重新设计基础设施就有意义。

反过来，如果团队只有几个 Agent，仓库规模也不大，Git 的现有能力可能已经足够。

不必因为有了 AI Agent 就推倒所有基础设施，但那些按人类开发者的工作习惯定下的假设，需要重新检查是否还适用。

Scion 探索的是：当软件开发从少量人类开发者转向大量并发 Agent 时，版本控制系统应该如何演进。这并不能证明 Git 已经过时。
