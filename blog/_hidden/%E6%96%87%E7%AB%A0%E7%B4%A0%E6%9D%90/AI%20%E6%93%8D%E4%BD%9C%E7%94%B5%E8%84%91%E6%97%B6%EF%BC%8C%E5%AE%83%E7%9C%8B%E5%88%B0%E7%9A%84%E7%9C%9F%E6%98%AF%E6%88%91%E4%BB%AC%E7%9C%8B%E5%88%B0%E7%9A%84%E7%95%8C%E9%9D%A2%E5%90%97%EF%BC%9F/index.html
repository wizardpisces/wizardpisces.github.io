AI 操作电脑时，它看到的真是我们看到的界面吗？

第一次看到 Computer Use 之类的 Agent 操作电脑，很容易产生一种直觉：

AI 终于学会像人一样使用电脑了。

它打开浏览器、移动鼠标、点击按钮、输入文字，然后完成一个任务。

但再往下问一句，事情就有意思了：

AI 操作电脑时，看到的真是我们看到的那个界面吗？

未必。

一个人看到的是窗口、按钮、文字、颜色和图标；而一个 Agent 面对的，可能是一套完全不同的世界。

一次“点击导出”，其实有很多种实现方式

假设我们正在使用一个订单管理系统，任务是：

“把 9 月 13 日的订单导出。”

对人来说，最自然的操作是打开页面，找到“导出订单”，然后点击。

但对 Agent 来说，“导出订单”至少存在几种完全不同的实现路径。

第一种，直接调用 API：

exportOrders(date="2026-09-13")

第二种，执行 CLI：

orders export --date 2026-09-13

第三种，通过网页 DOM 或其他结构化界面信息找到按钮：

找到 role=button、name=导出订单
→ 执行 press

第四种，也是最接近传统 Computer Use 的方式：

查看屏幕截图
→ 判断“导出订单”按钮在哪里
→ 移动鼠标
→ 点击坐标 (1260, 740)

对于用户来说，这四种方式最后都表现为同一件事情：

“AI 把订单导出来了。”

但对于模型来说，它们代表的是完全不同的信息空间。

这也是理解 Computer Use 的第一个关键点：

Computer Use 并不等于让 AI 学会“看屏幕、移动鼠标”。它更像是一层统一的操作接口，底层可以连接到完全不同的自动化技术。

Computer Use 本质上是一层“统一外观”

从 Agent 的上层看，流程可能非常简单：

模型提出动作
      ↓
Computer Use Tool
      ↓
底层自动化程序
      ↓
浏览器 / 操作系统
      ↓
新的界面状态
      ↓
模型继续判断

模型本身并不会亲自发出鼠标信号。

它调用的是一个 Tool，而 Tool 的底层实现可以负责截图、点击、输入、滚动，甚至调用更结构化的软件接口。

因此，“Computer Use”更像是一种能力抽象，而不是某一种固定技术。底层走的是 API、CLI、界面结构还是截图，要看软件留下了哪条路。

所以，看到 Agent “点击了一个按钮”，并不能说明它真的像人一样理解了那个按钮。

它可能是在看像素。

也可能根本没有“看”。

AI 为什么会使用无障碍 API？

这里有一个尤其有意思的技术细节。

以 macOS 为例，系统的无障碍能力可以把一个图形界面描述成结构化的信息。

一个简单的界面可能类似：

窗口
├── 文本框
│   ├── 名称：搜索
│   └── 当前值：Agent
│
├── 按钮
│   ├── 名称：导出
│   ├── 位置：(1260, 740)
│   └── 可执行动作：按下
│
└── 表格
    └── 订单列表

这套机制最初并不是为 AI 设计的。

它是为了辅助技术，例如 VoiceOver，让无法正常通过视觉使用电脑的人也能够理解屏幕上的内容。

但对于 Agent 来说，这恰好是一份非常有价值的机器可读界面描述。

系统不是要求 Agent 看着一个蓝色矩形，然后猜：

“这个东西可能是按钮。”

它可以直接告诉 Agent：

这是一个按钮。
名字是“导出”。
它支持“按下”这个动作。

Apple 的 AXUIElement 等接口就提供了读取 UI 元素属性、获取动作以及请求执行动作的能力。

于是，一个有意思的现象出现了：

无障碍树原本是帮助人绕过视觉界面的技术，却意外地成为了 Agent 绕过视觉识别的一种“影子 API”。

这并不意味着所有 Computer Use 都依赖无障碍 API。

对于自绘控件、Canvas、游戏画面、远程桌面，或者那些没有提供可靠结构化信息的软件，Agent 可能依然只能退回到最原始的方法：

截图
→ 理解像素
→ 判断位置
→ 移动鼠标
→ 点击
→ 再截图确认

这也是 Computer Use 最有价值、同时又最笨拙的地方。

Agent 操作软件，其实存在一条“接口光谱”

如果把这些技术放到一起，就能看到一条很有意思的光谱：

结构化 API / MCP
        ↓
   语义最明确

CLI / 专用 Tool
        ↓
   参数和结果清晰

DOM / 无障碍树
        ↓
   借用界面的结构化信息

截图 + 鼠标坐标
        ↓
   最通用，但也最不确定

这并不是严格意义上的技术排名，而是体现了一种很稳定的取舍：

越结构化，Agent 越容易理解和验证，但软件必须提前提供这种接口。

反过来：

越接近像素，Agent 越容易覆盖那些没有专门接口的软件，但操作的不确定性也越高。

这其实很好理解。

假设让 Agent 删除一个文件。

如果存在 CLI，可能只需要：

rm example.txt

而如果只能使用 GUI，就可能变成：

打开文件管理器
→ 找到文件
→ 右键
→ 找到删除
→ 点击
→ 处理确认弹窗
→ 检查文件是否消失

后者更像人类操作电脑，但也意味着更多潜在的不确定性：

  • 窗口可能被遮挡；
  • 按钮位置可能变化；
  • 同名文件可能导致误操作；
  • 弹窗可能突然出现；
  • 点击成功不代表业务操作成功；
  • 每一步都可能需要重新观察和确认。

从 Agent 的角度看，GUI 很多时候不是最优解，只是没有更好接口时的最后一公里。

所以，Computer Use 并没有杀死 CLI

恰恰相反。

Computer Use 越成熟，API、CLI 和专用 Tool 的价值可能越明显。

因为一个优秀的 Agent 并不会为了“像人一样”而坚持用鼠标。

如果有一个稳定的结构化接口：

createInvoice(...)
sendEmail(...)
exportOrders(...)
deleteUser(...)

它当然应该优先使用。

GUI 的价值在于另一件事：

现实世界中存在大量根本没有 API、没有 CLI、也没有专门 Agent 接口的软件。

但是这些软件几乎都有 GUI。

于是 GUI 成了一层通用的兼容层。

它不是在宣布：

“GUI 赢了，CLI 过时了。”

而是在说：

只要这个软件还有一个人类可以操作的界面，Agent 就有可能找到某种方式与它交互。

这才是 Computer Use 真正解决的问题：不是教 AI 点鼠标，而是让它有机会接入那些从未为 Agent 准备过接口的旧软件。

但这里还有一个更大的问题

如果 Agent 真的开始大量使用软件，我们可能会发现：

“让 AI 看懂人类界面”并不是最理想的终局。

因为今天的 GUI 主要解决的是：

人应该在哪里点击？

而 Agent 真正需要知道的问题其实是：

这个动作到底意味着什么？

比如，一个按钮叫：

删除

无障碍树可以告诉 Agent：

这是一个按钮
名称：删除
可以执行：press

但 Agent 真正想知道的可能是：

这个删除操作会影响哪些数据？

是否可以撤销？

需要什么权限？

会不会触发其他业务流程？

删除成功以后，系统会返回什么结果？

怎样证明这次操作确实成功？

这已经超出了传统 UI 自动化的范围。

它实际上是在要求软件提供一种新的东西：

机器可理解的行动语义。

下一代软件可能有两套界面

未来的软件可能同时拥有两种界面。

一套给人看：

布局
颜色
图标
动画
按钮
弹窗
交互反馈

另一套给 Agent 使用：

对象是什么
可以执行什么动作
动作需要什么参数
需要什么权限
会产生什么影响
操作是否可撤销
结果是什么
如何验证成功

今天的无障碍树已经有一点类似这种思想。

它告诉机器：

这里有一个按钮
按钮叫“导出”
它可以被按下

但未来的 Agent Interface 可能需要进一步告诉机器：

这里存在一个“订单导出”动作

输入：
- 日期范围
- 订单状态
- 文件格式

权限：
- 需要订单读取权限

副作用：
- 无

结果：
- 返回导出文件 ID

验证：
- 文件状态必须变为 completed

这已经不是传统意义上的 GUI，而是一种 Action Interface——行动接口。

真正的变化，不是 AI 学会了点鼠标

所以，如果只把 Computer Use 理解成：

“AI 终于会操作鼠标了。”

其实低估了它。

真正值得关注的变化是：

Agent 正在迫使软件重新思考“界面”到底是什么。

过去的软件主要面对两类调用者：

人
→ GUI

程序
→ API / CLI

现在多了一类：

Agent
→ Action Interface

在这种新接口成熟之前，Agent 只能利用软件已经留下的路。能调用 API 就调用 API；没有接口，就从 DOM、无障碍树甚至屏幕像素里找入口。

所以，Computer Use 看起来像 GUI 自动化，实际上更像一个过渡阶段。

它的长期意义不是：

“让机器更像人一样操作电脑。”

而可能恰恰相反：

让软件最终不再要求机器必须假装成人，才能使用它。

这也是为什么，今天我们看到的“AI 点按钮”，可能只是一个很早期的信号。

GUI、CLI 和 API 都不会消失。变化的是，软件可能多出一层专门描述“能做什么、需要什么、做完如何确认”的行动界面。

到那时，Computer Use 最值得关注的，就不再是 AI 会不会点鼠标，而是一个更大的问题：

当软件开始拥有 Agent 之后，我们是不是正在从“人机界面”走向“人机共用的行动界面”？
