数据库为什么不直接修改旧数据？从 LSM Tree 到 Agent 的 Git 服务

更新一条数据，最自然的想法是：找到旧记录，把它改掉。

但在一些数据库里，新值写进去了，旧值却还留在磁盘上。过一阵子，后台才把它们整理掉。

为什么要绕这一步？

从一个保存用户积分的数据库开始，就能逐步推导出 LSM Tree。

一、先从“直接修改”开始

假设有一亿个用户，数据放不进内存，主要保存在磁盘上：

用户编号 → 积分
1001 → 80
1002 → 60
1003 → 90
……

现在不断收到更新：

把 1002 的积分设为 65
把 8000 的积分设为 120
把 1002 的积分设为 70

每次找到原位置修改，就要访问这些用户所在的数据页。它们可能分布在磁盘的不同位置，持续的零散更新会带来大量分散的磁盘读写。

能不能先收下更新，攒成一批，再集中写出去？

二、先记下来，暂时不改旧数据

每来一条更新，先追加到磁盘日志末尾：

1002 → 65
8000 → 120
1002 → 70

这样不用每次去找旧位置。

但查询时怎么办？为了知道 1002 的最新积分，总不能每次都读完整份日志。

可以同时在内存里维护一张能按编号查找的有序表。先忽略历史快照，只看当前值：

1002 → 70
8000 → 120

磁盘日志记录发生过的更新，内存表方便快速查询。（典型实现中，前者叫 WAL，也就是预写日志；后者叫 MemTable。）

三、内存写满怎么办？

假设内存只能容纳三个用户的数据。

接着收到 1001 → 80，内存表写满了。把表里的数据按编号顺序写成一个磁盘文件：

文件 A：
1001 → 80
1002 → 70
8000 → 120

这种按 key 排序的文件，通常叫 SST 文件。

接下来，换一张空内存表接收更新。后续更新不回头修改 A。

又收到三条数据：

1002 → 75
3000 → 50
8000 → 130

内存再次写满，生成较新的文件 B：

文件 B：
1002 → 75
3000 → 50
8000 → 130

现在 1002 有两个版本：A 里是 70，B 里是 75。

写入容易了，查询时却得判断哪一份才是最新值。

四、查询时，从较新的数据找起

在这个简化例子里，查询 1002：

先查当前内存：没有
再查较新的 B：找到 75
返回 75

查询 1001：

先查当前内存：没有
再查 B：没有
再查 A：找到 80

真实系统会利用文件的编号范围、索引等信息跳过不相关的数据，不会每次逐个扫描所有文件。但文件越来越多，查找和处理版本的负担仍会增加。

写入时不用找旧记录，读取时就得在多个文件里找最新值。

所以不能只生成新文件，还得有人整理它们。

五、后台把有序文件合起来

把 A、B 合并，重复用户保留较新的积分：

输入 A：
1001 → 80
1002 → 70
8000 → 120

输入 B：
1002 → 75
3000 → 50
8000 → 130

合并生成 C：
1001 → 80
1002 → 75
3000 → 50
8000 → 130

这里不需要保留历史快照。新文件生效、旧文件不再被读取使用后，A、B 就可以回收。

这个后台合并整理过程，叫 Compaction。

那为啥单个文件最好整理排序？看第一步：

A 当前编号：1001
B 当前编号：1002

先输出较小的 1001，再把 A 的读取位置向后移动：

A 当前记录：1002 → 70
B 当前记录：1002 → 75

编号相同，输出较新的 75，两边一起向后移动。

继续这样比较，输入只需向前读，输出不断向后写，像归并排序一样完成批量整理。

文件有了顺序，就能通过批量读写来整理原本零散的更新。

如果要删除用户，也不急着修改旧文件，而是先写一条删除标记，挡住旧积分。等合并时能够安全清理，再回收相关记录。

六、这就是 LSM Tree 的核心

我们一步步得到了这样的结构：

更新到来
    ↓
追加日志，更新内存有序表
    ↓ 内存表写满
生成磁盘有序文件
    ↓ 文件逐渐积累
后台合并，清理失效版本

这就是典型 LSM Tree 的工作方式。全称是 Log-Structured Merge-Tree，通常译为“日志结构合并树”。

实际系统还会把磁盘文件分层组织，限制每层的规模，逐步向下合并。不同合并策略会在读取、写入和空间成本之间做不同取舍。

它没有消除维护数据的成本。回头看这个例子：

  • 查 1001 可能检查多个文件，这叫读放大。
  • 1002 的旧积分暂时留在 A 中，增加空间占用。
  • 1001 没有更新，合并时却又写进 C，这叫写放大。

合并还会与前台读写争抢资源。如果新文件产生得比后台整理更快，文件就会积压，系统甚至需要降低写入速度。

写入快了，数据会暂时分散在多个文件里，后台得持续整理。

七、同一个思路，为什么会出现在 Git 服务里？

OpenAI 为了应对 Agent 的大量提交，扩展的 Git 服务后端 Pando，也遇到了“小文件越攒越多”的问题。

它复用 Push 上传的 packfile，也就是装着 Git 对象的数据包，来服务后续 Fetch。但主干不断更新，落后一天的客户端可能要下载数万个小包。

Pando 于是借鉴 LSM Tree：先接收小包，后台再按层组织、重打包成覆盖更多版本的大包，减少下载文件数，也改善压缩。

假设主干从 v0 连续更新到 v16，每次 Push 收到一个小包。用每四个包合成一个更大的包来示意：

L0：P1～P16，共 16 个小包
    ↓ 每 4 个合成一个包
L1：Q1～Q4，共 4 个中包
    ↓ 再合成一个包
L2：R1，覆盖 v0 → v16

生成大包以后，小包仍然保留。为什么？

客户端 A：已有 v0，想更新到 v16
    → 可以下载大包 R1

客户端 B：已有 v15，想更新到 v16
    → 只需小包 P16

如果只留下 R1，B 为了一点新增内容，也得下载覆盖整段历史的大包。

**大包照顾落后很多的客户端，小包照顾只差少量更新的客户端。**Pando 整理的是历史的包装方式，不会像积分例子那样，因有了新值就淘汰旧提交。

从数据库到 Git 服务，共同的问题都是：每次新数据到来时，要不要立刻把所有东西整理好？

LSM Tree 给出的办法是先记录，再批量维护。Pando 借用了这部分思路，但它如何让大量 Agent 并行 Push、又让许多客户端复用已有包，还需要另外的设计。

下一篇，我们再看 Pando 如何把这些设计组合起来。
