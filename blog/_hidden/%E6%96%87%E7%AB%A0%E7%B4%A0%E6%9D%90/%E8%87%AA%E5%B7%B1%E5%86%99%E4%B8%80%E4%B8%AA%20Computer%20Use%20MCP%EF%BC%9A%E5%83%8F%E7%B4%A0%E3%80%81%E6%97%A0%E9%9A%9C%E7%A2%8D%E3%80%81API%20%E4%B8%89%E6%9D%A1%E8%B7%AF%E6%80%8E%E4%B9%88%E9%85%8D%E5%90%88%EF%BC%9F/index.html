自己写一个 Computer Use MCP：像素、无障碍、API 三条路怎么配合？

很多人对 Computer Use 的印象是"截图 + 让模型点坐标"。

这只说对了一条路。真实的 Computer Use 是一个综合体，至少有三条通道：

像素通道      截图 + 点击坐标
无障碍通道    系统暴露的元素树 + 按名称触发
API / 脚本    应用自己暴露的语义动作

三者不是三个不同的世界，而是同一份状态暴露给模型的三层不同表示：像素最通用，无障碍最精确，API 最有语义。

这篇文章直接从零把这套东西写出来。读完你会有一个能跑的 Computer Use MCP，也会知道三条路各自在哪、什么时候不该用。

一、先定契约：MCP 只规定怎么说话

MCP 解决的是传输与描述：工具名、参数 schema、返回结构。它不关心"点哪里"。

所以契约得我们自己定。把三个通道都摆出来，工具清单是这样的：

screenshot                像素通道：把屏幕编码成图片
click(x, y)               像素通道：坐标 → 点击事件

ax_tree()                 无障碍通道：读出元素树
press_element(name)       无障碍通道：名称 → 触发元素

api_increment(n)          API 通道：语义动作，没有坐标、没有按钮
compare_channels()        自查：列出三条通道在本场景下的可用性

宽度也重要。三条通道同时暴露给模型，它才有得选——这是"能组合"的前提。

还有一条容易漏的：观察工具必须把坐标系一起返回。(167, 328) 离开坐标系就不是动作，只是两个数。

二、假桌面：让三种粒度可以被直接看见

真机截图需要权限，写文章时我试了一下：

$ screencapture -x -t png /private/tmp/probe.png
could not create image from display

没有屏幕录制授权，连"看一眼"都不行。这会干扰学习，所以先做一个确定性的假桌面，但必须保住真实世界的三个结构特征：

状态只在服务端   模型看不到，只能通过工具拿
动作改状态       改完必须重新观察才知道结果
坐标与图同源     算出来的坐标要能落到真实像素

画一个 800x480 的计数器，目标 3、当前 0。关键设计是：同一个状态，用三种方式都能读、都能改。

// 通道一：像素。坐标进，状态出
clickPixel(x, y) { ... }

// 通道二：无障碍。系统给出角色、名称、frame 和可执行动作
accessibilityTree() {
  return { role: 'window', name: 'Counter', children: [
    { role: 'staticText', name: 'current', value: String(state.value) },
    { role: 'button', name: '+1', frame: {...}, actions: ['press'] },
  ]};
}

// 通道三：API。没有坐标，没有按钮，只有领域动作
apiIncrement(n) { state.value += n; ... }

注意无障碍树里的 frame。它和像素通道的坐标数值可以一样，来源却完全不同：那里是系统给的事实，这里是模型猜的估计。 这个区别就是第二条通道存在的全部理由。

三、服务端：三个观察者，三种动作

像素通道

截图工具的关键在返回结构——图片必须作为 MCP 的 image content 回去：

server.registerTool('screenshot', {
  description: '截取当前屏幕。返回 width/height，之后的 click 坐标必须落在这个范围内。',
  annotations: { readOnlyHint: true },
}, async () => {
  const buf = desk.render();
  return {
    content: [
      { type: 'text', text: `截图：${W}x${H}。` },
      // 这一行是分水岭：内容一旦以 content 进入本轮上下文，模型才算真的"看见"。
      { type: 'image', data: buf.toString('base64'), mimeType: 'image/png' },
    ],
    structuredContent: { width: W, height: H, ...desk.snapshot() },
  };
});

动作侧，坐标校验是闸门：

if (x < 0 || y < 0 || x >= W || y >= H) {
  return { content: [{ type: 'text', text: `坐标 (${x}, ${y}) 超出画面，动作被拒绝。` }], isError: true };
}

无障碍通道

无障碍树返回的是结构，不是图片。模型按名字找元素，不用算坐标：

server.registerTool('ax_tree', {
  description: '读取无障碍树：带角色、名称、当前值和可执行动作。比截图精确，但自绘控件可能是空的。',
  annotations: { readOnlyHint: true },
}, async () => {
  const nodes = flatten(desk.accessibilityTree());
  return { content: [{ type: 'text', text: renderAsLines(nodes) }], structuredContent: { nodes } };
});

触发也不需要坐标：

server.registerTool('press_element', {
  inputSchema: { name: z.string().describe('无障碍元素名称，如 +1') },
}, async ({ name }) => {
  const res = desk.pressElement(name);
  // 名字不存在时明确失败，而不是"点了个空的"
  return { isError: !res.ok, content: [{ type: 'text', text: res.ok ? `已触发 "${name}"` : `失败：${res.reason}。没有发出任何动作。` }] };
});

API 通道

这条最有意思：模型完全不接触界面。

server.registerTool('api_increment', {
  description: '应用暴露的领域动作：把计数器加 n。没有坐标、没有按钮，只有一个业务操作。',
  inputSchema: { n: z.number().int().positive() },
}, async ({ n }) => {
  const res = desk.apiIncrement(n);
  ...
});

n 必须是正整数这件事，由 schema 在模型之外强制。这就是窄参数的价值：能被校验的意图，才是可执行的意图。

四、三条通道各走一遍

客户端把"模型该做的判断"写成固定策略，只为了证明闭环成立：

await client.callTool({ name: 'screenshot', arguments: {} });
await client.callTool({ name: 'click', arguments: { x: 167, y: 328 } });   // 像素
await client.callTool({ name: 'press_element', arguments: { name: '+1' } }); // 无障碍
await client.callTool({ name: 'api_increment', arguments: { n: 1 } });     // API

实测输出，可以看到同一个计数器被三条不同的路推到了 3：

[1] 截图 1：800x480
   像素通道 click → 点击落在 inc 上，当前值 1/3。
   无障碍树 → window "Counter" | staticText "current" 值=1 | button "+1" 动作=[press]
   无障碍通道 → 已通过无障碍通道触发 "+1"，当前值 2/3。
   API 通道 → +1 已生效，当前值 3/3。
[4] 截图 4：800x480

四条通道都可用时，这张自查表可以交给模型自己判断：

pixel  可用=true  单位=坐标 (x, y)        依赖=从图中估算位置        失败=图看不清 / 点空 / 算错坐标
ax     可用=true  单位=元素名称 + 动作     依赖=系统暴露无障碍信息     失败=自绘控件查不到元素
api    可用=true  单位=业务动作 + 参数     依赖=应用主动暴露接口       失败=接口不覆盖该操作

五、三条通道的失败，都不能静默

每条通道的失败模式都不一样，但有一条共同要求：失败必须说清是哪种失败。

无障碍找不到元素 → 无障碍通道失败：没有名为 "不存在" 的可操作元素。没有发出任何动作。
API 参数非法     → MCP error -32602: Too small: expected number to be >0 at n
点空白           → 点击落在空白处 (600, 430)，没有命中任何控件，当前值 3/3。
坐标越界         → 坐标 (9999, 10) 超出画面 800x480，动作被拒绝。坐标没有发出。

四条里有三条 isError=true，一条不是——点空白时点击确实发出了，只是没命中。

把这个区分讲透，就是闭环的验收标准：每一次动作之后，模型都要能分清"做到了"“没做到”“根本没发出去”。 三种状态混在一起，它就会开始瞎猜。

六、切到真机：两条权限，两种沉默

假桌面跑通之后，换真机后端。截图用系统 screencapture，无障碍用 AXUIElement，点击用 CoreGraphics 事件。然后立刻撞墙，而且是两种不同的墙。

第一种墙：截图失败，但失败得很诚实。

[1] 截图失败（exit=1）。这是观察通道断了，不是屏幕为空。
stderr: could not create image from display
这类失败通常是系统权限未授予：终端或宿主进程需要在"屏幕录制"里被勾选。

第二种墙：无障碍通道整体被关掉。

AXIsProcessTrusted = False
读取返回 -25204（ax_api_disabled — 进程未获得辅助功能授权，整棵无障碍树都读不到）
这不是界面为空，是这条通道整体被关掉了。

注意 -25204 和"界面没有元素"是完全不同的两件事。如果把"通道被关"和"这里没东西"混为一谈，模型会得出一个错误结论：我看到了一个空界面。

第三种墙最阴险：点击成功，但什么都没发生。

这一条我没有预料到。CGEventPost 提交事件后返回成功，可是光标纹丝不动：

{
  "ok": true,
  "posted": true,
  "cursorAfter": { "x": 0, "y": 0 },
  "landed": false,
  "note": "事件提交成功，但光标没有移动——通常是辅助功能未授权，事件被系统丢弃。"
}

没有异常，没有错误码，只有一个 posted: true。

如果工具在这里返回"已点击"，模型就会基于一个假事实继续往下走——它以为点了，其实什么都没点。这和我们平时说的"模型幻觉"是两回事：幻觉是模型编的，这一条是我们给的。

所以真机后端里加了唯一能做的一步自查：提交后回读光标位置，比对目标坐标，把 landed 一起返回。修好之后，工具在没权限时明确报错，而不是撒谎。

三条墙合起来就是 Computer Use 的第一原理：它的能力上限由操作系统给不给权限决定，不由模型多聪明决定。 而两条通道是两套独立权限——屏幕录制和辅助功能，经常只给了一半，于是"能看不能动"或"能读不能点"。

七、回头看：为什么一定是这三条

写到这儿可以收口了。三条通道不是设计出来的巧合，是三种不同信息源的必然结果。

像素通道    信息单位是坐标        最通用的兼容层：只要有屏幕就能用
无障碍通道  信息单位是元素和动作   系统替你回答"这是什么、能做什么"
API 通道    信息单位是业务动作     应用直接回答"这意味着什么"

越往下，信息越接近语义，也越稳：坐标会算错，元素可能查不到，但 +1 这个动作不会理解错。

代价同样清楚：越语义化，覆盖面越窄。 API 通道只在应用愿意暴露时存在；无障碍通道只在界面有结构时存在；只有像素通道什么都能点，也什么都可能点错。

所以真实实现从不是三选一。工程判断就在于选路：

有 API        优先 API，最稳、最省 token
有结构界面     用无障碍，按名称操作，避免坐标误差
都没有         退到像素，接受它的不确定，靠截图回环纠正

对照三家官方实现，主干完全一致，差别只在坐标表示、工具集数量和记忆放在哪：

OpenAI CUA        截图观察，动作走 computer_call，坐标先归一化再映射回真实分辨率
Anthropic         一个 client 工具集（screenshot / left_click / type / zoom…），宿主机执行每次调用
Gemini            应用带截图请求，模型返回动作，应用执行后再截图

至于"应用主动暴露动作"这条路，你其实已经很熟了——MCP 工具本身就是 API 通道的标准化形态。WebMCP 那一类探索，则是在把浏览器页面也变成可以注册动作的地方。

最后，一张图记住

像素     截图 + 坐标      最通用，最不确定，靠回环纠错
无障碍   元素 + 动作      最精确，依赖系统暴露，自绘控件会失效
API      动作 + 参数      最有语义，只在应用愿意暴露时存在

三者共同点：
  观察要带坐标系
  动作要窄到可校验
  失败要说清是哪一种失败

一个 Computer Use MCP 的代码量比想象中小。真正花时间的从来不是写完这些工具，而是后面这些不性感的部分：三条通道各自失败时的报错语义、截图缩放后的坐标映射、长任务里的状态压缩，以及一开始就撞上的那两道权限边界。

可运行代码在仓库 sub-project/computer-use-mcp/：src/server.mjs 是服务端（三条通道都在里面），src/simulator.mjs 是假桌面，src/smoke.mjs 是一次跑通三条通道的自测，src/screen.mjs、src/actions.mjs 是真机驱动。npm run smoke 直接复现上面那段输出，CU_TARGET=real 复现权限那三段。
