同样一句吩咐，为什么一个 Agent 很快做完，另一个一直在绕？

给两个 Coding Agent 同一个任务：

给这个旧项目加一个 CSV 导出功能，但不能破坏现有接口。

它们的输出速度看起来差不多。

一个 Agent 很快找到导出入口，补了一个边界测试，改完两个文件，跑完测试就结束了。

另一个 Agent 先读项目目录，再读数据模型、接口、前端调用和配置文件。它改了序列化逻辑，又改了接口返回，测试失败后重新读了一遍上下文，最后才发现真正需要改的只有一个导出函数。

同样一句吩咐，为什么差这么多？

慢的，不一定是模型

很多人比较 Agent，第一眼会看模型每秒能吐多少 Token。

但一项任务的时间还包括：

模型调用
+ 工具执行
+ 读取和处理上下文
+ 重复操作
+ 失败重试

第一个 Agent 可能只调用了几次工具：

定位导出入口
    ↓
查看相关测试
    ↓
修改最小范围
    ↓
运行测试

第二个 Agent 的问题不一定是代码写错，而是每一步都把范围弄得更大：

读取整个项目
    ↓
猜测数据模型也要改
    ↓
顺手改接口和前端
    ↓
测试失败
    ↓
重新理解一遍上下文

它并没有一直停着不动。它只是花了很多时间，却没有让问题明显变小。

这才是两者真正的差距：

一次动作之后，
任务的不确定性减少了多少？

“改完代码”不等于“事情做完”

假设 Agent 找到了一个看起来合理的导出实现。

它还需要确认：

旧接口的返回格式有没有变化？
空数据会不会报错？
中文字段会不会乱码？
大文件会不会一次性读进内存？

如果它只看到“代码能运行”，就会很快宣布完成。

如果它先把这些风险变成测试，再修改代码，前几步可能慢一点，但后面少了返工。

所以，真正快的 Agent 往往不是最快写出第一版代码的那个，而是更早知道“什么证据才算完成”的那个。

Agent 的第一步，决定了后面要付多少钱

面对一个陌生项目，Agent 可以先打开整个仓库，也可以先找入口文件和现有测试。

两步都能开始工作，但价值完全不同：

读取整个仓库
成本高，得到的信息杂，下一步仍然不确定

查看导出入口和相关测试
成本低，能马上确定修改范围

这可以压缩成一个很实用的判断：

检查价值
≈ 能改变多少判断
  ÷ 需要付出的成本

Agent 不需要一开始就猜中最终答案。它只需要优先选择那些能快速排除大块可能性的动作。

很多“越做越慢”，其实在第一步就已经埋下了：它选了一个看起来很努力、却不能改变判断的动作。

Harness 会把差距放大

同一个模型，放进不同的 Harness，也可能跑出完全不同的轨迹。

如果每一轮都把整个项目重新塞给模型，它会反复读取已经看过的文件。

如果系统没有记录哪些假设已经被证伪，Agent 可能再次执行同一条失败路线。

如果工具没有调用预算和停止条件，它就会继续“再确认一下”，直到把时间耗在重复检查上。

一个有基本状态管理的 Harness，至少应该让 Agent 看见：

已经检查过什么
哪些路线已经失败
最近一次测试留下了什么证据
当前还缺哪一个判断

模型负责选择动作，Harness 负责让动作有记录、有边界，失败后还能回来。

所以，Agent 的速度不是一个模型参数就能解释的结果。模型的行动倾向、工具的设计方式和运行时状态，都会改变最后那条路径。

真正应该比较什么？

下次比较两个 Agent，不要只看它们谁先吐完答案，可以看：

谁更早找到相关文件？
谁更早跑出能区分问题的测试？
谁重复读取和重复调用更少？
谁第一次有效修改出现得更早？
谁能在证据足够后停下来？

如果一个 Agent 的文字输出速度并不慢，却总在扩大搜索范围、重复读取上下文、沿失败路线继续尝试，那么它慢的不是“说话速度”，而是“缩小问题空间的速度”。

Agent 真正的速度，不是每秒生成多少字，而是每一步有没有让问题变小。

这条判断不只适用于 Coding Agent。查资料、做实验、处理工单，凡是需要连续行动的任务，都可以用同一个标准检查：

这一步完成后，
我比刚才更接近答案了吗？
