AI 进了公司，为什么常常只剩一个 API？

很多 AI 项目，开始时想得很大。

要做 Agent。

要让 AI 自己理解任务、调用工具、检查结果，遇到意外还能调整做法。

可一进公司，方案就开始一点点变形：

Agent
  ↓
固定 Workflow
  ↓
一个模型节点
  ↓
一次 API 调用

最后项目按时上线了。

AI 也确实用上了。

只是最初想改变的工作方式，几乎没变。旧流程、旧系统、责任边界都还在。中间多了一次模型调用。

这件事看起来像一个技术选择，背后却有个组织问题：

公司愿意接入 AI，为什么又会把它能自己决定的部分一点点拿掉？

API 很容易进公司，Agent 没那么容易

假设团队要做一个客户工单 Agent。

客户说：

“我的包裹怎么还没到？”

理想情况下，Agent 会先找订单，再查物流。客户有几笔订单，它得分清是哪一笔。信息不够时追问，查询失败时重试或转人工。风险太高，就停下来。

听起来很合理。但只要它能决定下一步，公司就得回答几个问题：

它为什么选择这一步？
什么时候可以继续，什么时候必须停？
它可以调用哪些工具？
工具失败后会怎么做？
做错了，谁能发现，谁来负责？

于是评审会开始问：

能不能先做成一个 API？

这里为什么不能写规则？

能不能先固定这一步？

先上线一个简单版本行不行？

这些问题本身没有错。有时固定流程加一次模型调用，的确就是最合适的方案。

但讨论可能在不知不觉中换了题目。原本要验证的是：

AI 能不能自己处理这类工单？

最后变成：

模型 API 怎么接进现有系统？

新问题就这样被换成了旧问题。

新技术进来，先被翻译成旧问题

数据库进公司，大家会讨论表结构、事务和故障恢复。缓存有命中率、失效策略和监控。团队大致知道该验收什么，出了问题由谁处理。

Agent 不一样。

团队可能知道 Agent 会读取上下文、调用工具、检查结果。可大家未必一起经历过这些环节在真实业务里怎样出错。知道名词，不等于知道什么时候需要它们。

所以一个陌生的 Agent 进入评审时，组织会先用熟悉的问题理解它：

输入是什么？
输出是什么？
成本多少？
什么时候交付？
出了问题怎么回滚？

一次 API 调用比较好管理。输入、输出清楚，成本也好估。Agent 会自己选下一步，公司还得决定谁来约束它、检查结果。

组织会先用已有经验，管理自己还不会评估的风险。

做过的人，看到的不是同一张图

还是那张工单。

没真正跑过的人，看到的可能是：

工单
  ↓
大模型
  ↓
处理建议

做过的人脑子里却是另一段过程。比如客户有七笔订单，只说“包裹没到”。Agent 选了最近的一笔。物流工具返回“已送达”，模型也回复得很合理。

每一步都成功了。

只是客户等的，是另一笔订单。

订单有七笔
  ↓
客户没说是哪一笔
  ↓
Agent 选错订单
  ↓
查询成功，回复也很流畅
  ↓
真正的问题还在

最麻烦的是：工具没报错，模型也完成了回复，答案却对应错了订单。

于是工程师开始要求状态管理、权限边界、失败重试、结果检查和人工接管。旁边的人听到的却是：

“一个查快递的功能，为什么要加这么多模块？”

工程师见过系统会在哪些输入下出错。其他人只看过它顺利跑通。一个人在担心失败，另一个人在算成本。多讲几遍架构图，也补不上这段经验差距。

架构图解释不了，证据可以

技术团队遇到质疑，常见的反应是继续解释：

为什么需要状态管理。

为什么要有 Evaluation。

为什么 Agent 不能把每一步都写死。

可架构图只能说明“我们打算怎么做”，不能证明“这个问题值得这样做”。

假设团队复盘一百张工单。

其中十二张里，查询和修改都成功了，处理的却是错误订单。现有检查只确认“操作成功”，没确认“订单是不是客户问的那一笔”。

这时，检查模块的工作就很具体：

它能拦住多少错单？会不会把正确订单也拦下？多花的成本值不值得？

让固定流程和 Agent 分别处理这批工单。样本里要有简单单，也要有订单不明、信息缺失和查询失败的情况。看任务有没有解决、有没有转人工、错单是否减少，再算成本变化。

团队终于有了共同材料。讨论也从“架构是不是太复杂”变成：

固定流程已经能处理好哪些工单？
Agent 额外解决了哪些情况？
这点改善，值不值得增加成本和风险？

实验也可以证明 Agent 不值得用

如果固定流程能解决大多数简单工单，而 Agent 提升不明显，就先别急着上。多出来的成本和故障点，也可能不值得。可以缩小它的权限，甚至暂时不用。

也可能有少数例外，固定流程总卡住，Agent 却能稳定处理。那团队就能说清它多解决了什么。还要划清边界：哪些情况仍交给人。

测试结果、失败案例和验收标准都保存下来。下次评审时，团队可以一起看 Agent 哪一步选错，哪些检查能拦住问题。工程师踩过的坑，也就不再只留在一个人脑子里。

为什么最后只剩一个 API

API 的输入、输出、负责人和回滚方式，组织大多知道怎么管理。

Agent 多带来一个决定：什么时候让机器自己选下一步？ 如果团队没有共同经验回答这个问题，方案就容易退回熟悉的 API。

这可能是合理选择。前面的测试如果显示，固定流程已经够用，API 就是更简单的方案。

但如果团队还没让 Agent 跑过真实任务，就先删掉它自主决定的部分，再用这个简化后的版本证明 Agent 没价值，结论就站不住。

关键是看同一批任务的测试结果：不让机器决定下一步，究竟会失去什么？

如果没有明显损失，用 API。

如果 Agent 确实能处理固定流程总卡住的情况，再把这部分决定交给它，并说清权限、检查方式和停止条件。

所以，项目最后只剩一个 API，不足以说明公司排斥 AI。更该看的是：团队有没有验证过，哪些工作值得交给机器自己决定。

如果没有这一步，接口、模型和 Prompt 都可能留下，原先想改变的工作方式却没机会发生。
