AI 十分钟干完的活，为什么在公司还要走两周？

AI 已经能写代码、做 PPT、画图、分析数据。

再往前一步，Agent 还能自己查资料、调用工具、执行任务。

演示里，它像个能接活的员工。进了公司，却常常变成：

Agent → Workflow → 按钮 → API

东西上线了，工作方式却没怎么变。

AI 只负责生成一次内容，后面的事仍要人一步步安排。

为什么总会退回这一步？得从公司为什么需要流程说起。

做事情很贵，所以要先安排好

过去，一个方案要做几天，一段代码也要花上几个小时。做错了，返工还得再花一遍时间。

公司于是把工作安排得很细：

接到任务 → 按流程执行 → 交付 → 他人检查 → 通过

谁做、先做什么、交给谁、谁审批，都要提前定好。这样做是为了少返工。

AI 让“先做出来”变便宜了

现在可以先让 AI 做三个版本，跑起来，看结果，再决定哪个值得继续。

以前得尽量想清楚再动手。现在，有些事可以先试，再根据结果调整：

想清楚 → 做 → 检查 → 交付
             ↓
先做 → 看结果 → 获得反馈 → 再做

可公司的流程没有跟着变。

假设 AI 十分钟生成了一个活动报名页。页面做好了，还得等评审、排测试、走审批。两周后，它终于上线。

AI 加速的是生产，公司的时间却花在排队、交接和等待上。

以前做需要几天，等一天不显眼。现在做只要十分钟，等两周就格外刺眼。

而 Agent 把问题又往前推了一步。

Agent 接手的是“下一步”

还是这个活动页面。如果只让 AI 生成代码，它把代码交出来，任务就结束了。

现在换个任务：“很多人填到一半就走了，找出原因，改好这个报名页。”

Agent 就得先查用户卡在哪儿。查到原因，再修改页面、运行测试。页面改完，还要看报名的人有没有变多。

这时候，它接手的就不只是写代码，还有决定下一步做什么。

问题也来了。假设这是线下活动，Agent 嫌表单太长，把联系电话删了。报名可能更容易了，工作人员却没法通知报名者。

代码能运行，测试能通过，甚至指标变好了，事情仍然可能办错。

所以公司很自然地加上确认：改表单先找产品，上线前再让业务检查。

每一步都有理由。加到最后，Agent 做完一步就得停下来等人。原本交给它的完整任务，又被拆回了一次次指令。

开头那个“生成页面”的按钮，就是这样留下来的。公司买下了执行能力，却还没找到放心交出判断权的办法。

Agent 能走多远，组织早就画过边界

那给 Agent 换个更聪明的模型呢？

它也许能更快发现问题，可有些地方，聪明也没用。

想看用户在哪一步离开，得向数据团队申请。想知道哪些信息不能删，得问业务。改完要发布，还得找有权限的人。

这些地方没接通，Agent 就只能提交建议，然后等。

你给它的目标是完整的，交给它的条件却是分段的。

这就是康威定律讲的关系：组织怎么沟通协作，往往会反映在系统结构里。

团队各管一段，系统也沿着这些边界拆开。过去要靠人跨部门协调的地方，换成 Agent，交接的步骤也没消失。

所以，一个 Agent 即使能连着想完十步，也可能被卡在第一步的工单里。模型的行动循环，撞上了组织的交接流程。

先给一件事找负责人，再让 Agent 跑起来

先别急着重组公司。就拿这个报名页试一次。

找一个人对报名效果负责。由他协调相关团队，把 Agent 需要的数据和权限接好。过去是每做一步就找一次人，现在先把这件事能怎么做商量好。

比如，联系电话必须保留，但填写提示可以改。Agent 可以读取脱敏后的填表错误记录，不需要拿到用户的电话号码。

再约定：改动先过测试，只向一小部分用户开放。出了问题就恢复旧版，想改必填项则必须找负责人确认。

这就是“逆康威”的思路。先想清楚系统应该怎样完成任务，再调整人的分工和协作，让这条路走得通。

现在让 Agent 再跑一遍。

它发现，很多用户把联系电话的格式填错了。于是补上一条格式提示，跑完测试，再让一小部分用户试用。

接下来，它查看填错的次数有没有减少、报名是否更顺畅。有效就保留这个改动，出了问题就撤回。整个过程都在事先约定的范围内，不用每改一句提示，就重新排一次队。

人依然负责，但把精力放在定规则、看结果和处理例外上。

这时才有必要问：报名有没有变顺畅？从发现问题到验证改动，到底省了多少时间？

这也是 AI Native 的具体落点：有了 AI，连做事的方法也跟着调整。页面能快速修改，团队就可以更快试出哪种改法有效。

生成页面只要十分钟，改好一个问题却还要等两周——那 AI 加速的仍然只是写代码，组织本身没有变快。
