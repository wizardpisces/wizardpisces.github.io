Git 为什么难用，却成了程序员离不开的工具？

设想一个你愿意真正托付工作的 AI Agent。

它刚刚修复了一个线上问题，改动了二十多个文件。你没有全程盯着它，也没有因为它动得快而心慌。因为你能看到它从哪些日志得出了判断，能在部署前检查每一处差异；如果测试没有通过，它会停在隔离环境里，不会把半成品带到生产。即使发布后出现异常，也能找回上一个已知状态，知道这次变化究竟从哪里开始。

注意，让你放心的不是“它保证百分之百正确”。而是它的错误能被接住。

这正是 Git 在软件开发里早就解决过的问题。也解释了一个看似矛盾的现象：Git 难学、难记、偶尔让人抓狂，却没有被一个“更简单的保存按钮”替代。

Git 最反直觉的地方：它不急着替你做决定

普通软件倾向于把历史藏起来。你改一段文字，点保存，系统默认当前版本就是答案。Git 却在修改和共享之间塞进了一层暂存区，还允许你开分支、改写本地历史、比较差异、合并冲突。

初学者会觉得这很绕。为什么改了文件还不算提交？为什么同样是撤销，restore、revert、reset 却不是一回事？为什么合并冲突不能自动解决？

因为它们对应的不是命令设计的任性，而是开发中几种不同的“还没想好”。

工作区里的修改，是一个尚在尝试的想法。暂存区是在说：“这部分我准备当作一个完整的变化交出去。”提交是把这个判断变成可追溯的快照。分支让互相竞争的方案先并存。冲突则是在说：“这两个人的意图不能由机器替他们选。”

Git 的官方文档把暂存区描述为下一次提交的提案，也强调本地历史可以在分享前尽可能晚地整理。这正是它真正的发明：把“现在就必须做对”的压力，拆成一连串可以检查、可以回退、可以延后决定的动作。Git 官方文档：三种状态与暂存区 Git 官方文档：重写本地历史

Git 因此并没有减少复杂性。它只是拒绝掩盖复杂性，并给复杂性配上了操作方式。

程序员真正依赖的，是“可被比较的意图”

把 Git 看成版本备份工具，仍然低估了它。

备份只能回答：“旧文件还在吗？”Git 还能回答：“你这次到底主张改什么？它和上一个判断差在哪？这个判断是谁在什么上下文下做的？”

这是一种很特别的能力：把模糊的意图变成可比较的对象。

一段正在编辑的代码，谁也不必立刻认可。进入暂存区后，它开始有边界。形成 commit 后，它有了身份和父节点。发起 review 后，团队可以围绕一份明确的差异讨论，而不必围绕“我大概改了一些东西”互相猜测。

于是，开发者敢于更早地尝试，也更容易推翻自己的尝试。分支不是为了把代码藏起来，而是给一个尚未证实的判断留出空间。提交也不是表演式地写一句 message，而是让以后的人有机会理解当时的选择。

连 Git 的恢复能力都建立在这层可追溯性上。reflog 会记录本地引用何时移动，因而常能找回看似丢失的提交；但记录会过期，已经泄露到外部的密钥也不会因为回退而失去风险。它从不承诺“任何错误都没事”，只尽量让状态和线索还在。Git 官方文档：reflog

这个区别很重要。优秀系统不是消灭错误，而是让错误在扩散之前有边界，让人有材料去判断该不该继续。

Agent 的问题，恰恰不是“会不会写代码”

今天的 Agent 已经能读仓库、跑测试、修改文件、创建工单，甚至执行部署。模型能力越强，越容易把注意力都放在“这次判断准不准”上。

但实际风险往往发生在判断之后。

一个推理大体正确的 Agent，可能选错环境；一段补丁本身没有问题，可能和另一个未完成改动互相覆盖；一封内容正确的邮件，发给了错误的客户列表。Agent 的速度和权限让这类失误的影响更快、更广。

因此，可靠 Agent 的核心能力应当有两层。

第一层是做对事：理解任务、找到证据、选择工具、给出合理方案。

第二层是让这件事即使做错，也能被看见、暂停、追查和补救。

第一层通常由模型和知识决定。第二层主要是系统设计。很多产品只投资前者，于是 Agent 看上去越来越聪明，团队却迟迟不敢放开权限。

给 Agent 一个“提交协议”，而不是一句“请谨慎执行”

把 Git 的思想借给 Agent，重点不是让它每操作一步都执行 git commit，而是给行动设置类似提交的边界。

一次足以影响外部世界的操作，至少应该回答五个问题：

  • 它基于什么证据和前提？
  • 它准备改变什么，影响范围多大？
  • 哪些结果已经自动验证，哪些仍是猜测？
  • 谁或什么策略有权批准这一步？
  • 如果结果不对，回滚、补偿或人工接管的路径是什么？

这五个问题组成一个“提交协议”。它把 Agent 的长链路任务切成可检查的状态，而不是让用户在最后面对一句“已经完成”。

以修 Bug 为例，Agent 不应从报错直接跳到部署。更合理的路径是：先在隔离工作区复现，再产生 diff 和测试结果；当影响范围清楚后，由策略或人决定是否合并；上线后把版本、观测数据和告警关联起来。每一步都能被检查，但只有跨过高风险边界时才需要打断人。

这和 Git 的思路很接近：先允许本地尝试，再把值得共享的变化打磨成清晰的对象。人类复核不必变成每一步点“同意”，而应当放在权限扩大、不可逆或证据不足的时刻。Agent 设计中的停止条件和人工复核，也是在保护这种边界。Anthropic：Building Effective AI Agents

有些世界无法像 Git 一样回退

这是类比最容易被滥用的地方。

代码仓库里的某次修改可以恢复到旧版本，业务世界不一定可以。已经发送的邮件无法收回，已经完成的支付不能假装没发生，已经通知客户的错误信息也会继续影响信任。

所以，Agent 的“回滚”不能只借用 Git 的名字。它需要根据动作类型选择机制：写入前先 dry run；重复请求带上幂等键；高风险操作要求显式授权；真正发生错误时执行补偿动作，并把事件交给人处理。能恢复的状态就恢复，不能恢复的影响就诚实地处理。

这不是给自主性泼冷水。恰好相反，只有把不可逆的边界看清楚，才知道哪些地方可以放心让 Agent 自动做得更快。

回到开头：我们想托付的到底是什么

一个值得信赖的 Agent，不一定是最少停下来问人的那个。它应该知道什么时候继续，什么时候停下；知道怎样把自己的行动变成可检查的证据，也知道哪些后果不能靠一句“撤销”解决。

Git 之所以留了下来，并不是它让程序员更少犯错。它让人可以在还不确定时先行动，在真正共享前再整理判断，在分歧出现时拿出差异来讨论，在出错后仍有机会知道发生过什么。

这是一种比“永远正确”更实际的安全感。

AI Agent 终究也要学会这一点。模型能把任务做得更快，但只有当系统能把错误接住、把意图保存下来、把外部后果控制住，人们才会真的把更多工作交给它。
