Git 为什么这么难用，却始终没有被替代？

想象一下，你准备重写项目的登录流程。

几个小时后，新方案没跑通，旧方案也被改得面目全非。你隐约记得哪些文件动过，却已经说不清每一步改了什么。

如果没有 Git，你大概会寻找昨天的备份，或者对着一堆“最终版”文件重新拼一次。

Git 改变的正是这件事：

它没有阻止人走错路，却让一次走错不必毁掉已经走过的路。

这也是它看起来麻烦，却一直没有被更简单工具取代的原因。

保存副本，只能回到过去

大多数人最初理解的版本管理，是不断复制文件：

方案.doc
方案-最终版.doc
方案-最终版2.doc
方案-真的最终版.doc

它确实保留了过去，却没有记录这些版本为什么出现、彼此是什么关系。

Git 保存的是另一种东西。

A ← B ← C ← D

每次提交都指向来时的路。于是你看到的不只是一份旧代码，还能知道它从哪里分开、经过哪些变化，又怎样走到今天。

普通保存回答“当时的文件是什么样”。

Git 还要回答“我们是怎样走到这里的”。

Commit 不是存档，而是 checkpoint

这也解释了新手最困惑的一件事：文件已经保存了，为什么还要 git add 和 commit？

因为保存只说明磁盘上的内容变了，commit 则是在历史中划出一个可以辨认、可以返回的边界。

假设你刚才修了一个 Bug，顺手改了格式，还写了一半重构。它们同时躺在工作区里，却不该挤进同一个 checkpoint。

暂存区让你挑出真正属于这一步的变化，commit 再把它们连同原因一起放进历史。

所以好的提交不只是“下午三点的代码”。它会告诉后来的人：这里完成了什么，从这里重新出发是否安全。

保存得再频繁，也不一定容易恢复。

真正有用的是在事情说得清的位置留下 checkpoint。

分支让一次尝试不必押上现在

有了 checkpoint，另一件事才变得可能：从同一个位置出发，尝试几种不同的未来。

A---B---E       main
     \
      C---D     feature

分支并不是复制一整套项目。它只是记住：这条尝试从 B 开始。

于是，重写登录流程的人可以继续向前，修补旧流程的人也不必停下来。两边不需要立刻争出谁对，失败的方案也不会污染已经稳定的代码。

等证据足够，再决定合并哪一条路。

Git 保存的因此不只是过去。

它还让几个尚未被选中的未来，可以同时存在一阵子。

已经影响别人的事，不能假装没发生

Git 那几种容易混淆的撤销命令，也在处理同一个问题：错误发生在什么阶段？

还没有提交的修改，可以像草稿一样丢掉。

只存在于本地的提交，可以重新整理边界。

但一段代码已经进入共同历史，甚至被别人接着开发，再把它偷偷抹掉，所有人的来路都会混乱。

这时 revert 不会修改过去，而是增加一次反向变化：那件事确实发生过，现在我们又把它改了回来。

这很像现实世界。没有寄出的邮件可以重写，已经寄出的邮件只能再发一封更正；数据库里没有执行的更新可以取消，已经发生的扣款则需要退款。

后悔看起来只有一句话，处理方式却取决于它有没有越过外部边界。

Git 难，因为它给试错留下了形状

Git 的命令确实可以更好记，报错也可以更友好。

可它背后的这些区别很难真正删掉：正在修改、准备记录、已经记录、已经影响别人，本来就不是同一个状态。

软件开发也不是沿着一条直线写出正确答案。人会尝试，会并行探索，也会在错误发生后改变主意。

简单工具把这些过程藏起来，直到出错时一起爆出来。

Git 把它们提前摆在了桌面上。

它的复杂，不全是设计得差。还有一部分，是试错本身终于有了位置、有了边界，也有了回去的路。

Agent 的重试，不能只是再来一遍

现在让一个 Agent 完成发布任务。

它先修改配置，运行测试，然后执行数据库迁移，最后发送上线通知。

如果最后一步超时，Agent 应该怎么办？

最直觉的答案是：重试。

可从头再跑一次，可能重复执行迁移；直接重发通知，又可能让所有人收到两封邮件。超时只说明 Agent 没拿到结果，不代表外部世界什么都没发生。

这时，单纯记住对话没有多大用。Agent 需要知道上一个可以安全恢复的位置在哪里，哪些步骤已经成功，哪些工具调用产生了外部事实，以及下一次执行怎样避免重复。

这才是 checkpoint 的意义。

它保存的不是“Agent 刚才说过什么”，而是“任务已经走到哪里，哪些路不用再走”。

retry 负责再试一次，checkpoint 决定从哪里再试。

Agent 也需要可以分叉和补偿的历史

Git 的其他设计也跟着回来了。

Agent 可以从同一个 checkpoint 分出两条路线，分别尝试两种修复，再选择测试通过的一条。这更像 branch，而不是让两次尝试在同一份状态上互相覆盖。

如果错误只存在于沙箱，它可以回到 checkpoint 重来；如果动作已经越过边界，写进数据库、发出邮件或者完成支付，就不能靠回滚上下文假装一切没发生。

这时需要的可能是去重标识、状态核对，或者一笔明确的补偿操作。

一个没有 checkpoint 的 Agent，就像一个开着自动保存、却从来不用 Git 的程序员：它可以工作很久，也可以在最后一步出错时，让你不知道该从哪里收拾。

所以，当 Agent 说“我会重试”时，真正值得追问的不是它会不会再想一次。

而是它准备从哪里重新开始，哪些事情不会重复，哪一步之后已经没有真正的撤销键。
