Rust 的“无 GC”到底是什么意思

“Rust 没有 GC”很容易被听成另一句话：它不需要在运行时管理内存。这并不准确。

更准确地说，Rust 没有由语言 runtime 统一追踪对象可达性、再批量回收不可达对象的 tracing GC。它把最常见的资源释放时机绑定到所有权结束，并把所有权与借用是否合法放进编译期检查。

{
    let message = String::from("hello");
    println!("{message}");
} // message 的 owner 离开作用域，Rust 调用 Drop

message 所持有的堆内存不是“编译时已经被释放”。程序执行到这里时，Drop 才真正运行；编译器提前保证的是：不会还有一个合法引用需要它。

单一所有者时，释放可以很直接

一个堆对象有一个所有者。所有权可以移动，但同一时刻只有一个 owner；借用者可以临时使用对象，却不能活得比 owner 更久。

let message = String::from("hello");
let size = message.len();
drop(message);            // 此后不能再使用 message
println!("{size}");

这组规则避免了两种危险：太早释放导致悬垂引用，以及多个所有者都释放同一块内存导致 double free。它不保证“所有值都在栈上”；String 的内容仍可在堆上。它保证的是资源责任清楚。

共享时，Rust 也会使用运行时机制

多个长期持有者需要同一个对象时，单一所有者模型不够用。Rc<T>（单线程）和 Arc<T>（可跨线程）用引用计数记录拥有者数量：clone 增加计数，离开作用域减少计数，归零时才析构。

use std::rc::Rc;

let shared = Rc::new(String::from("hello"));
let consumer = Rc::clone(&shared);
// shared 和 consumer 都离开作用域后，计数才归零

这仍是运行时的内存管理，只是不是 tracing GC。它也有不同的限制：引用计数需要维护计数；强引用环不会自动回收，通常要通过 Weak<T> 或调整对象关系来处理。

RefCell<T> 也说明了同一条边界：它把“同一时刻能否可变借用”的检查从编译期移到运行时，违反规则时会 panic。Rust 不承诺所有安全规则都能静态证明；它要求开发者明确选择静态证明或动态检查。

与 Go 的差别不只是有没有 GC

Go 允许更多动态、隐式的对象共享，runtime 通过 GC 根据对象是否仍可达来决定回收。Rust 则要求大多数关系通过所有权与借用在编译时说清楚，只有 Rc、Arc、RefCell 等明确选择的场景才把判断留到运行时。

所以更值得问的问题不是“Rust 有没有回收”，而是：这个对象的存活关系，能否由类型和代码结构证明？

能证明时，Rust 让 owner 结束时精确执行 Drop；不能证明但需要共享时，就选用相应的运行时机制。这就是 Rust “无 GC”背后的取舍。
