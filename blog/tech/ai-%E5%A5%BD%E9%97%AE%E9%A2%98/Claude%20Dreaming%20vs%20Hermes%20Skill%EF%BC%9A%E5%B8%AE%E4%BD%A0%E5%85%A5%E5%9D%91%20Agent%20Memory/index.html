Claude Dreaming vs Hermes Skill：帮你入坑 Agent Memory

Claude Dreaming vs Hermes Skill：帮你入坑 Agent Memory

Claude 有 Dreaming，Hermes 有 Skill。

看着都在做同一件事：

让 AI 从经验中学习。

从 Agent Architecture 来看，它们其实属于两个完全不同的层级：

  • Dreaming 关心的是：哪些经验值得长期记住？
  • Skill 关心的是：哪些经验值得固化成能力？

换句话说，一个优化的是 Memory，另一个优化的是 Capability。

更准确一点说：

  • Claude Dreaming 更接近 Semantic Memory，也就是“知道什么”。
  • Hermes Skill 更接近 Procedural Memory，也就是“知道怎么做”。

这篇文章真正想讨论的不是 Claude 和 Hermes 哪个更好，而是：

一个长期运行的 Agent，为什么不能只靠一种 Memory？

为什么 Dreaming 和 Skill 容易被混在一起？

因为它们的起点看起来非常像。

两者都从历史经验出发：

Experience
     │
     ▼
Reflection
     │
     ▼
Something reusable

也就是说，它们都不是只处理当前对话，而是试图从过去的 Session、任务和失败里提炼出未来可复用的东西。

这也是它们容易被归到同一类功能里的原因。

但真正关键的问题是：

Reflection 之后，到底抽取什么？

Claude Dreaming 抽取的是事实、偏好、项目背景、长期规律。

Hermes Skill 抽取的是步骤、流程、操作顺序、工具使用经验。

如果画成更具体的结构：

Claude Dreaming：

Experience
     │
     ▼
Extract Facts
     │
     ▼
Better Memory

Hermes Skill：

Experience
     │
     ▼
Extract Procedure
     │
     ▼
Reusable Skill

两者都在做 Reflection，但 Reflection 的对象完全不同。

Memory vs Capability

很多 Agent 文章会把长期记忆统一叫 Memory。

但这个说法其实太粗了。

“用户喜欢中文”是一种 Memory。

“如何按这个团队的流程发布一个版本”也是一种 Memory。

可它们显然不是同一种东西。

前者描述的是事实：

用户偏好中文回答。
这个项目使用 Vite。
这个团队不喜欢引入重型依赖。

后者描述的是做法：

先跑 lint。
再跑 type-check。
再更新 changelog。
最后创建 release tag。

如果都塞进同一个 Memory Store，系统很快就会变得混乱。

因为事实和流程有不同的生命周期：

类型 关心的问题 变化速度 失败方式
Semantic Memory 什么是真的？ 相对慢 记错、冲突、过时
Procedural Memory 应该怎么做？ 相对快 流程失效、过度固化

这也是为什么 Dreaming 和 Skill 看起来都像“长期记忆”，但其实应该分层管理。

Dreaming 更像是在维护一个更干净的世界模型。

Skill 更像是在沉淀一组可复用的行为模板。

一个帮助 Agent 更好地理解上下文。

一个帮助 Agent 更快地完成任务。

Dreaming：把经验压缩成更好的事实

Claude Dreaming 的重点不是训练模型，也不是把一次成功任务变成固定流程。

它更像一个后台的 Memory Consolidation 过程。

大致流程是：

历史 Session
     +
当前 Memory Store
     │
     ▼
Dream Job
     │
     ▼
新的 Memory Store

它会重新审视已有记忆和历史上下文，做几类事情：

  • 删除重复内容；
  • 合并相似事实；
  • 处理冲突信息；
  • 更新已经过时的描述；
  • 抽取更高层的长期规律。

比如原来的 Memory 里可能有这些碎片：

John 喜欢 Python。
John 最近开始写 Rust。
John 不喜欢 Java。
John 现在主要写 Rust。

Dreaming 后，更合理的表达可能是：

用户目前主要使用 Rust。
用户熟悉 Python。
Java 不是首选语言。

这里发生的不是 workflow learning，而是 knowledge consolidation。

也就是说，Dreaming 关心的是：

关于这个用户、这个项目、这个长期上下文，到底哪些事实值得留下？

所以它的价值不是让 Agent 立刻执行得更快，而是让 Agent 不再被低质量记忆拖累。

Memory 越干净，后续推理越稳定。

这也是 Dreaming 很适合处理偏好、背景、约束、项目状态的原因。

例如：

用户经常要求中文回答。
用户在 Python 项目里偏好 uv。
这个项目不希望随便引入新框架。
用户更在意工程可维护性，而不是炫技实现。

这些东西不一定会直接变成某个固定动作。

但它们会影响 Agent 每一次判断。

Skill：把经验固化成可复用能力

Hermes Skill 解决的是另一个问题。

Agent 最大的浪费之一，不是“不知道”，而是“每次都重新探索”。

比如第一次部署 Kubernetes 服务时，Agent 可能经历了这样的过程：

kubectl apply
     │
     ▼
发现配置缺失
     │
     ▼
修复 values
     │
     ▼
helm install
     │
     ▼
等待 rollout
     │
     ▼
health check

如果第二次部署类似服务时还从头探索一遍，就很低效。

Skill 的思路是把成功路径提炼出来：

Experience
     │
     ▼
Workflow Extraction
     │
     ▼
Skill Library
     │
     ▼
Retrieval
     │
     ▼
Reuse

也就是说，它沉淀的不是“用户部署过 Kubernetes”这个事实，而是“遇到类似部署任务时应该怎么做”。

这就是 Procedural Memory。

它更像一个可加载的操作手册：

Deploy Kubernetes Service

1. 检查 values 配置
2. 执行 helm install / upgrade
3. 等待 rollout
4. 运行 health check
5. 根据错误日志修复常见问题

以后遇到类似任务，Agent 可以通过语义检索找到这个 Skill，再按需加载到上下文里。

这类机制的收益非常直接：

  • 少走弯路；
  • 减少重复规划；
  • 复用已经验证过的步骤；
  • 把个人或团队的隐性流程显性化。

对于复杂 Agent 来说，这非常重要。

因为很多任务的难点并不是单步推理，而是知道一套稳定流程：

如何发布版本？
如何排查线上告警？
如何迁移数据库？
如何审查一类 PR？
如何配置某个内部工具？

这些知识如果只以“事实”的形式存着，Agent 仍然要每次重新组织动作。

而 Skill 的价值，就是把这些反复出现的动作组织成能力。

为什么 Claude 不直接做 Skill？

Anthropic 的设计哲学：相信模型能力越来越强，Workflow 不应该固化。

它默认模型本身有较强的 planning 能力，因此长期系统最需要维护的是：

干净、准确、不过度干预推理的 Memory。

所以 Dreaming 固化的是事实，而不是流程。

这有一个明显好处：

不容易把旧方法写死。

Workflow 的变化速度通常比事实更快。

今天一个团队的发布流程可能是：

lint
type-check
build
tag
deploy

过一段时间可能加入：

security scan
canary
approval

如果 Agent 过早把旧流程固化成 Skill，就可能在未来持续调用一套已经不合适的方法。

Dreaming 避开了这个风险。

它只记住更稳定的部分：

这个团队发布前重视检查。
这个项目使用某套 CI。
用户倾向于先验证再部署。

然后让模型在每次任务里重新规划具体步骤。

这也是 Dreaming 更稳的地方。

为什么 Hermes 要强调 Skill？

因为如果 Agent 只靠每次重新规划，长期效率会很差。

尤其是工具调用型任务。

模型可以理解“部署服务”是什么意思，但真正完成任务时，往往需要掌握很多具体细节：

命令顺序
配置位置
失败重试
日志入口
验证标准
团队约定

这些东西只靠 Semantic Memory 不够。

比如 Memory 里写着：

这个团队使用 Kubernetes。

这当然有用，但不足以指导一次高质量部署。

真正能提高效率的是：

这个团队部署 Kubernetes 服务时，通常要按以下流程执行。

这就是 Skill 要解决的问题。

所以 Hermes 的 Skill 层更激进地把一部分经验转成能力。

它相信：

如果一个流程已经多次成功，就不应该每次都让 Agent 从零开始摸索。

这类 Skill 对高频任务尤其有价值。

第一次也许花 20 分钟。

第二次可能只要 2 分钟。

两种 Memory 的风险也不一样

Dreaming 的主要风险，是记忆质量问题。

比如：

  • 把临时偏好当成长期偏好；
  • 把偶然事实总结成稳定规律；
  • 在冲突信息中选错版本；
  • 压缩后丢掉重要上下文。

这些问题会影响 Agent 的判断，但通常不会直接把某个操作流程写死。

Skill 的风险更像工程资产的风险。

它一旦被调用，影响的是实际行为。

典型问题包括：

  • API 变了，Skill 还在调用旧接口；
  • 团队流程变了，Skill 还按旧步骤执行；
  • Skill 写得太大，加载后挤占上下文；
  • Skill 过于武断，让模型不再重新评估更好的方案。

比如一个旧 Skill 写着：

Always use pandas.

但在新的数据任务里，polars 可能更合适。

这时 Skill 就不再是经验，而是惯性。

所以 Skill 的收益更直接，维护成本也更高。

Dreaming 更容易保持系统稳定。

Skill 更容易带来效率提升。

它们不是竞争关系

更合理的方向不是二选一，而是分层协作。

Experience
     │
     ▼
Reflection
     │
 ┌───┴───────────┐
 │               │
 ▼               ▼
Facts        Procedures
 │               │
 ▼               ▼
Memory Store  Skill Library
 │               │
 └───────┬───────┘
         ▼
 Retrieval + Planning

Dreaming 负责回答：

这个用户、项目、团队、环境里，什么长期为真？

Skill 负责回答：

遇到某类任务时，哪些步骤已经被验证过，可以复用？

推理阶段再结合检索和规划，决定什么时候引用事实，什么时候加载 Skill。

比如同样是“发布一个版本”：

Semantic Memory 可能提供：

用户偏好中文总结。
这个项目用 pnpm。
这个团队发布前必须跑 type-check。

Procedural Memory 可能提供：

Release Skill:
1. 检查工作区状态
2. 跑 lint 和 type-check
3. 更新 changelog
4. 创建 tag
5. 生成发布说明

结论

Dreaming 和 Skill 共同指向 Agent 的一个核心问题：

经验应该被记住，还是被固化？

有些经验只应该被记住。

比如偏好、背景、约束、项目状态。

它们应该留在 Semantic Memory 里，帮助 Agent 更准确地理解世界。

但有些经验不适合只停留在“记住”这一层。

当一个流程被反复验证、稳定复用，并且有清晰的成功标准时，它可以被做成 Skill。

这是一种工程权衡。

Skill 的收益是复用，代价是固化。

这才是长期学习真正困难的地方：

不是保存更多经验，而是判断经验应该以什么形态留下。

Dreaming 代表的是一种保守选择：

先把 Memory 变干净。

Skill 代表的是一种激进选择：

把稳定流程变成能力。

真正成熟的 Agent，不是把所有过去都记下来，也不是把所有经验都固化成流程。

它要学会区分：

什么只是事实；

什么才值得变成行动规则。
