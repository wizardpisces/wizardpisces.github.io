Plan 决定怎么走，Goal 决定是否完成：Agent 为何选错城市？

你让一个旅行 Agent 在杭州、苏州、宁波里挑一个周末目的地。最初，它只需要比较往返车票：

查一下杭州、苏州、宁波的往返车票，推荐最便宜的城市。

Agent 列出三项 Todo：

[完成] 查询三个城市的车票
[完成] 比较价格
[完成] 推荐最便宜的城市

杭州 180 元，宁波 260 元，苏州 360 元。Agent 推荐杭州，没有问题。

在这个任务里，“比较完价格”和“找到最便宜的城市”几乎是同一件事。Todo 全部完成，任务也就完成了。

Plan 起初没有问题

用户随后加上天气和预算限制：

从三个城市里选一个适合户外活动的地方。降雨概率不能超过 20%，往返车票不能超过 300 元；如果都不满足，就建议我延期。

Agent 正确理解了要求，生成了这份 Plan：

[待执行] 查询三个城市的天气
[待执行] 查询三个城市的车票
[待执行] 过滤掉不符合条件的城市
[待执行] 有合格城市就推荐，否则建议延期

天气查询很顺利，杭州和宁波的车票也拿到了，只有苏州票价接口超时：

杭州：降雨概率 60%，往返 180 元
宁波：降雨概率 40%，往返 260 元
苏州：降雨概率 10%，票价未知

杭州和宁波已经被天气条件淘汰。苏州天气合格，但票价未知。按照原 Plan，任务还不能结束。

一次重规划，把终点也改掉了

Agent 决定重试苏州票价接口。重新规划时，它把注意力放在“怎样处理剩余步骤”，生成了一个更短的新 Plan：

[待执行] 重试苏州票价查询
[待执行] 汇总三个城市的数据
[待执行] 推荐当前综合最优的城市

重试成功，苏州往返 360 元。至此，天气和车票都查对了：

杭州：降雨概率 60%，往返 180 元
苏州：降雨概率 10%，往返 360 元
宁波：降雨概率 40%，往返 260 元

三个城市都不符合原始条件，Agent 却回答：

推荐杭州。票价最便宜，周末下雨的话带伞即可。

上一篇《Agent 为什么会“记错”？问题可能出在它看到的世界》解决的是另一层错误：程序把旧天气混进 Context，Agent 看见了错误的世界。

这一次，模型看到的城市和工具结果都正确。变化发生在 Plan 里：重规划保留了“继续查票”，却丢掉了“没有合格城市就延期”。

新 Plan 也执行成功了，但它完成的已经不是用户最初交代的任务：

Plan 的结果：杭州综合排名第一
用户的条件：杭州降雨概率超标

Context Engineering 保证这一步看见正确的事实；接下来还要保证任务走到一半时，验收标准不会被 Agent 顺手改掉。

Plan 可以变，Goal 不能跟着变

重新规划本身没有问题。接口超时以后增加重试，甚至改成先查票再查天气，都只是路线变化。

不能跟着 Plan 一起重写的是完成条件，也就是 Goal：

成功：找到降雨概率 ≤ 20%、往返票价 ≤ 300 元的城市
无解：三个城市都检查完，仍然没有合格项
无解时：建议延期，不降低用户条件

Goal 应当从用户原始要求中提取并单独保存。Agent 可以重新生成 Plan，却不能因为“必须给出一个推荐”更容易交付，就把硬条件改成综合排序。只有用户主动把预算提高到 400 元，Goal 才会改变。

系统再用 Goal 验收 Plan 的结果。杭州即使综合排名第一，也会因为降雨概率超标被拒绝。

Evidence 决定现在能不能停

回到苏州票价超时的时刻，Goal 已经很清楚，系统仍然不能判断成功还是无解。当时已经确认的事实，也就是 Evidence，只有这些：

杭州：降雨概率 60%
宁波：降雨概率 40%
苏州：降雨概率 10%，票价未知

苏州仍可能合格，所以 Status 只能是“进行中”。重试拿到 360 元以后，Evidence 才完整，Status 随之变成“无解”：

苏州票价未知 → Status=进行中
苏州票价 360 → Status=无解

这时 Agent 不必硬挑一个城市，而是按照 Goal 正常结束：

三个城市都无法同时满足天气和预算条件，建议延期。

“无解”不是执行失败，而是 Goal 允许的一种结果。系统如果只认识“成功”和“继续”，就容易把无解当成还没努力够，继续搜索，或者偷偷放宽条件。

四项数据组成任务的控制状态

现在可以把这次运行压成一条线：

按照 Plan 执行下一步
        ↓
把天气和票价写入 Evidence
        ↓
用 Goal 检查结果是否合格
        ↓
更新 Status：继续、成功或无解

Plan 管下一步，Goal 管验收，Evidence 保存事实，Status 表示当前能不能结束。这四项共同构成任务的控制状态，也就是 Control State。它是应用自己的设计，不是 LangGraph 内置的类型。

LangGraph 可以用 State 和 checkpoint 保存这些数据，却不会替业务定义什么才算成功。LangGraph 管任务接下来可以怎么走，Control State 则让系统知道现在是否已经走完。

如果任务只是选最低票价，Todo 已经够用。等任务出现硬约束、中途重新规划，或者允许“无解”正常结束时，系统才需要把验收条件和执行步骤分开。

以后看到一个 Agent 宣布“任务完成”，可以先问三个问题：

  1. 完成的是当前 Plan，还是用户的 Goal？
  2. Evidence 已经完整，还是只有眼下能拿到的部分？
  3. 系统是否允许用“无解”正常结束？

能回答这三件事，才能判断 Agent 是真的完成了任务，还是只把清单走到了最后。

这三问也适用于研究、代码修复和商品筛选。只要任务允许重新规划，就要防止系统把“当前步骤做完了”误当成“用户的要求满足了”。
