一个任务，什么时候只需要 Workflow，什么时候才值得交给 Agent？

很多 AI 项目从一句话开始：

这个需求，我们做个 Agent 吧。

听起来是在选技术。其实更早该问的是：这个任务的下一步，能不能提前确定？

我们从一次支付 SDK 升级说起。

它看起来很像一个 Agent 任务

支付团队准备把 SDK 从 v2 升到 v3。你把代码仓库、迁移文档和终端工具交给模型，希望它完成升级。

模型要读文档、改代码、运行测试，还要根据结果继续处理。步骤不少，也调用了工具，很像一个 Agent。

但把任务写出来，会发现路线几乎是现成的：

读取迁移文档
→ 修改依赖版本
→ 替换废弃接口
→ 运行测试
→ 创建 PR

每一步可以调用 LLM。读文档需要理解，改代码需要生成，PR 描述也可以由模型撰写。

可下一步始终由程序决定。文档读完就修改依赖，修改完成就运行测试，测试通过才创建 PR。

这仍然是 Workflow。

用了模型，不等于用了 Agent。区别不在有没有 LLM，而在谁决定流程往哪里走。

有分支和循环，也未必是 Agent

第一次运行测试，失败了：

ImportError: create_charge has been removed

迁移文档已经写明，create_charge 要替换成 payments.create。程序找到旧调用，完成替换，再跑一次测试。

流程现在有了判断和循环：

运行测试
├─ 通过 → 创建 PR
└─ 已知错误 → 按迁移规则修复 → 再次测试

它依然不需要 Agent。

分支可以写成 if，重试可以写成 while。只要错误与处理方式能够提前对应，系统走哪条路仍由预先写好的规则决定。

流程复杂，不代表它需要自主探索。一份几十个步骤的财务报表可能很复杂，但每一步都清楚；调查一个偶发故障也许只走几步，却可能完全不知道下一步该查哪里。

直到错误没有写在文档里

第二次测试又失败了。这次没有明确报错，只在 CI 环境里偶尔超时，本地始终正常。

现在该做什么？

查 SDK 的网络配置，还是 CI 的代理？先看日志，还是构造一个最小复现？如果没有发现，再查依赖版本，还是去搜索同类问题？

这些步骤无法提前排好，因为下一步取决于刚刚发现的证据：

观察现象
→ 提出假设
→ 选择检查对象
→ 获得新证据
→ 保留、修改或放弃假设

任务走到这里，才真正需要 Agent。

Agent 获得的并不是“多调用几次工具”的能力，而是决定下一步的权力。它可以根据日志选择搜索文档，也可以先检查配置；一个假设不成立，再换一条路线。

判断边界的问题也因此变得很简单：

在看到这一步的结果以前，能不能确定下一步做什么？

能，交给 Workflow。不能，才需要 Agent 临场选择。

同一个任务，不必整体选边

真实系统通常不会纯粹属于某一边。

SDK 升级的大部分流程都很确定，只有“诊断未知错误”需要探索。更合理的结构是：

读取文档 → 修改代码 → 运行测试
                         ├─ 通过 → 人工确认 → 创建 PR
                         ├─ 已知错误 → 固定规则修复 ─┐
                         └─ 未知错误 → Agent 探索 ──┴→ 再次测试

外层 Workflow 保存状态、控制顺序，也守住测试和人工确认这些边界。Agent 只在未知错误里获得自由，找到候选修复后，再回到确定流程接受验证。

这比“整个任务交给 Agent”更容易调试，也更容易回答一个朴素的问题：这次失败，到底是固定流程写错了，还是 Agent 的判断错了？

Agent 不是 Workflow 的高级版本。它更像 Workflow 中一块无法提前画出路线的区域。

LangGraph 为什么会出现在这里

LangChain 和 LangGraph 不是“Agent 与 Workflow”两个对立选项。

LangChain 可以快速创建一个带工具的 Agent。LangGraph 则把状态、节点和路径显式组织起来，既能运行固定 Workflow，也能把 Agent 放进某个节点。

在这个例子里，读取文档、执行测试和人工确认可以是确定节点；诊断未知错误则是一个 Agent 节点。图的价值不在于看起来高级，而在于它把“哪里按规则走，哪里允许模型临场决定”留在了结构里。

这也解释了为什么不该一开始就问“要不要上 LangGraph”。先把任务画出来。如果所有路径都能提前写清，一个普通函数或队列可能已经够了；当确定步骤、循环、局部探索和人工确认开始交错，显式的 Graph 才真正有用。

别先问要不要 Agent

回到最开始的 SDK 升级。

它没有在某个时刻从 Workflow 整体变成 Agent。只是走到未知错误时，有一小段路线无法预先确定。

设计系统时，可以先画出那些已经知道的步骤。能确定的路径交给代码，必须看完现场才能决定的部分再交给模型；即使 Agent 找到了答案，执行高风险操作和确认结果仍然可以回到固定流程。

所以，真正值得问的不是“这个任务够不够复杂”。

而是：

走到哪一步时，我们第一次无法提前写出下一步？

那里，才是 Agent 应该开始的地方。
