DeepSeek 为什么也开始造 Harness？因为模型已经解释不了 Agent 为什么好用

看到一个 Agent 很好用，我们通常会先问：

它背后是什么模型？

这个问题正变得不够用了。

同一个模型，放进不同产品里，一个只能告诉你“代码应该怎么改”，另一个却能自己读文件、运行测试、发现失败、继续修改，最后交出可以验证的结果。

模型没有变。后者多出来的，是一套把判断变成行动、再把结果送回模型的闭环。

差别发生在哪里？

一家模型公司，造了一个可以换模型的系统

最近 DeepSeek 开源了 DeepSeek Harness。

第一眼看，它很像又一个 Agent Framework：有工具、Session、沙箱、权限和 Agent Loop，底下还有一套叫 Cordis 的插件系统。

单看这些名词，没有几个是新的。

反常的是：DeepSeek 是一家模型公司，造出的系统却没有把模型放在中心。

在它的架构里，模型适配器是插件，工具注册表是插件，Session Log 是插件，连负责决定 Agent 下一步怎么运行的 Agent Loop 也是插件。官方文档直接写道，这些部分都可以通过配置替换，系统里不存在一个需要不断打补丁的特权内核。

一个模型公司，为什么要把自己的模型也变成可替换部件？

模型越来越强，产品差距却开始发生在模型外

聊天产品的运行链路很短：

用户提问
   ↓
模型生成
   ↓
返回答案

模型能力几乎直接出现在用户面前。模型换代，回答质量通常也会跟着变化。

Agent 多了一个很厚的中间层：

目标
 ↓
选择上下文
 ↓
调用模型
 ↓
执行工具
 ↓
观察结果
 ↓
继续、重试或停止

模型仍然负责理解和决策，但它已经不能独自决定结果。

上下文选错了，再强的模型也会稳定跑偏；工具只能读取，模型就无法完成修改；权限过大，一次错误判断可能变成真实事故；任务中断后没有 Session 和恢复机制，模型再聪明也只能从头再来。

《从 Prompt 到 Loop：一个例子看懂 AI 工程的四次升级》曾把 Harness 称为 Agent 的工作台。现在再看，工作台已经不只是给模型摆几件工具。

它开始决定：

模型能看见什么
模型可以影响哪个世界
一次行动怎样留下状态
失败之后系统还做什么

DeepSeek 的 Session Log 是个很具体的例子。它先记录 Agent 做过什么，再从这份历史里生成模型看到的消息。任务恢复、分叉和回放，都建立在同一份运行记录上。

这里的 Session Log 不是 OpenTelemetry 日志。它是 Agent 运行时的事实来源：少了它，系统可能无法恢复和重放。Trace 则是从运行事实中生成的一种观测视图，即使上报失败，Agent 本身仍应能够继续运行。

当上下文可以从历史中重建，Agent 就不再只是一次模型调用，而是一段能够继续的运行过程。

模型决定了能力上限，Harness 决定这些能力能有多少变成稳定结果。

这就是为什么只问“用了什么模型”，已经解释不了一个 Agent 为什么好用。

Agent 的各部分，本来就不该一起升级

模型、工具和运行环境的变化节奏完全不同。

模型可能暂时保持不变，业务工具却要跟着接口每天调整；沙箱发现漏洞，需要立刻收紧；Session 存储要从本地文件迁到数据库；一次任务的 Agent Loop，也可能从简单 ReAct 换成带计划、审核和人工确认的流程。

如果这些东西都焊在同一个大循环里，每替换一部分，整个 Agent 都要跟着修改。

DeepSeek Harness 用插件和稳定接口拆开这些变化。它带来的价值可以压缩成一句话：

它让 Agent 的各部分能够以不同速度演化。

这句话也解释了为什么 Runtime 开始变得重要。

Runtime 是模型外面的组织层。它不替模型思考，而是让模型、工具、状态、权限和执行环境在各自变化时，仍然能够组成同一个 Agent。

过去我们把 LLM 当成一个 API。到了 Agent 产品里，它依然重要，却只是运行系统中的一个组件。

模型公司的竞争，正在向模型外移动

OpenAI 的 Agents SDK 已经负责工具、Handoff、Guardrail、Session 和 Trace。2026 年 4 月，OpenAI 又把 Agent Loop 的 Harness 与执行环境进一步分开，理由包括安全、持久运行和扩展性。

Anthropic 的 Claude Agent SDK 同样不只是一个模型客户端。它提供 Agent Loop、工具、Session、权限控制、Hook 和上下文管理，让开发者直接使用 Claude Code 背后的运行方式。

它们的做法并不相同，但都在把原本藏在产品内部的 Agent Loop、工具、Session 和权限，变成开发者可以使用和编排的基础设施。

模型公司开始设计“模型怎样持续做事”，而不再满足于提供一次推理。

这背后有一个很现实的变化：Agent 的用户体验、运行数据和开发者入口，越来越多地掌握在 Harness 手里。

如果模型公司只提供推理 API，那么下游产品将决定模型看到哪些数据、能调用哪些工具、怎样处理失败，也决定用户最终把功劳或责任归给谁。

模型仍然可能是最昂贵、最难替代的部分，却不再天然拥有整个产品的控制权。

如果这个方向继续发展，一个自然的战略结果是：谁掌握 Runtime，谁就掌握了模型、工具和用户任务之间的编排层。

DeepSeek 把模型也做成插件，至少说明它没有把模型当成整个系统唯一不变的中心。模型会换，Runtime 仍然可能留下。

以后判断 Agent，要同时看两层

模型依然重要。

模型能力不足，Harness 不能凭空补出推理能力；模型足够强，也不代表 Agent 就能可靠地完成任务。

以后看一个 Agent 产品，可以把问题拆成两层：

模型层
它能不能理解问题、提出有效行动？

运行层
它看到了什么、能做什么、失败后怎样继续？

前者决定它有没有可能做成，后者决定这种可能性能否反复兑现。

插件、事件和依赖注入都不是新技术。DeepSeek Harness 值得关注，是因为一家模型公司开始认真建设模型外面的系统。

这释放了一个比产品功能更有意思的信号：

Agent 时代，模型仍然是能力的来源，但光靠模型，已经解释不了能力怎样变成结果。

下一次再遇到一个表现惊人的 Agent，除了问它用了什么模型，也许还应该问一句：

是什么 Harness，让这个模型能够这样工作？
