MCP 升级后，AI 产品如何走出聊天框？

MCP 在 2026 年 7 月 28 日发布了新版规范。核心变化是：协议从双向、有状态的交互，转为无状态的请求/响应。

这次升级更像一次架构纠偏：MCP 把原本可选的无状态实践变成协议默认，并补齐了无状态情况下向客户端索取输入的标准流程。

特别关注点：

删除 Session：请求之间不再依赖协议层的隐藏上下文
引入 MRTR：执行中需要等待用户输入时，不再保留原请求的运行现场

Session 消失：每个请求都要把话说清楚

假设你对 AI 助手说：

点一杯冰美式，无糖，付款前让我确认。

旧版的 Streamable HTTP 模式里，服务器会在初始化时签发 Mcp-Session-Id：

客户端 ── initialize ───────────→ 服务器
       ←─ Mcp-Session-Id: s_123 ─
       ── initialized ──────────→

后续请求自动携带 Mcp-Session-Id: s_123

服务端通过这个 ID 知道请求来自同一段 MCP 协议会话，也能找回先前协商的能力和上下文。

新版取消了初始化握手和 Mcp-Session-Id。协议版本、客户端信息与能力改为由每个请求通过 _meta 提供。

但订单并不会因此消失。跨多个工具处理同一笔业务时，仍然需要业务 ID：

create_order({ drink: "冰美式", sugar: false })
                    ↓
             返回 order_id: 1024
                    ↓
update_order({ order_id: 1024, ... })
                    ↓
confirm_order({ order_id: 1024 })
                    ↓
pay_order({ order_id: 1024 })

order_id 并不是新版才有的设计。区别在于：旧版可以借助协议 Session 找回部分隐含上下文；新版要求请求自己带足信息，或者通过明确的业务查询方式找到状态。

旧版：后续请求可通过 Session 找回协议上下文
新版：每次请求自行携带信息，或显式查询业务状态

这只解决了“多次请求如何关联同一笔业务”。如果工具执行到一半需要用户确认，还需要另一套机制。

MRTR：先结束请求，再带着回答继续

旧版支持用户确认，通常使用 elicitation/create：

客户端 ── place_order（请求 10）──→ 服务器
                                     │
       ←─ elicitation/create ────────┤
           “确认支付 28 元吗？”      │
                                     │ 服务端保留执行现场并等待
客户端 ── accept ───────────────────→│
       ←─ 下单成功（响应 10）────────┘

这里的关键是：place_order 还没有结束。服务端内存里保留着这次调用执行到哪里、在等什么，以及收到答案后该如何继续。

新版仍用 elicitation/create 描述“需要向用户收集什么”，但它不再以服务端主动发起的 JSON-RPC 请求出现，而是放进 input_required 结果里：

客户端 ── place_order（请求 10）──→ 服务器 A
       ←─ input_required ────────── 请求 10 结束

用户点击「确认」

客户端 ── place_order（请求 11）──→ 服务器 B
       携带原请求参数、inputResponses、requestState
       ←─ 下单成功 ────────────────

第一次返回的内容大致如下：

{
  "resultType": "input_required",
  "inputRequests": {
    "confirm": {
      "method": "elicitation/create",
      "params": {
        "message": "确认支付 28 元吗？",
        "requestedSchema": {
          "type": "object",
          "properties": { "confirmed": { "type": "boolean" } },
          "required": ["confirmed"]
        }
      }
    }
  },
  "requestState": "..."
}

客户端根据 inputRequests 展示确认界面。用户作答后，客户端用新的 JSON-RPC 请求 ID 再次调用 place_order，并带回：

原请求参数     → 用户最初要做什么
inputResponses → 用户这次给出的答案
requestState   → 上一次调用留下的续跑信息

它真正改变的是：继续执行所需的条件，不再只能放在服务器内存里那段未结束的调用中。它们可以随下一次请求传回，也可以由外部业务存储保存。

旧版：用户回答回到仍在等待的原调用

新版：原调用结束；用户回答进入新请求；新请求恢复处理

两者的职责也更清楚：

elicitation/create → 描述要向用户收集什么
MRTR                → 定义如何结束当前请求、收集输入并继续处理

为什么只删除 Session 还不够？

如果只删除 Session，却保留旧式 elicitation/create，服务端还是得挂着一次调用等用户。请求依旧绑定在某个正在运行的实例上。

新版分别处理了两类状态：

跨请求的协议上下文
        ↓
取消 Session

等待中的执行现场
        ↓
MRTR 将它变成可恢复的信息

这样，服务端不再需要共享 MCP Session 或依赖粘性路由。用户想几分钟、几小时，原实例都可以释放资源；后续请求落到另一台实例，也能继续。

无状态的收益与代价

最直接的收益是扩容与故障恢复更简单。第一次请求结束后，服务器不必保留连接和执行栈；只要恢复信息完整，后续请求可以交给另一台实例。

产品层也更灵活：

聊天窗口 ── 发起订单 ─────┐
手机通知 ── 用户确认 ─────┼─→ 同一个 order_id
审批中心 ── 风控授权 ─────┘

服务端只需说明“还缺一次确认”。至于由聊天卡片、推送通知还是审批页面来收集答案，交给客户端和产品流程决定。

代价也是有的：

客户端   → 识别 input_required、收集输入并重新发起请求
服务端   → 保存业务状态，或生成安全的 requestState
业务操作 → 面对重试，确保付款、删除等动作具备幂等性

requestState 还应绑定用户和原始请求，设置过期时间，并防止被篡改。MCP 不会自动完成跨入口接力：产品仍要解决身份统一与业务状态的安全传递。

新版并没有消除状态，只是把它们放回各自该负责的位置：

_meta           → 协议版本、客户端信息与能力
业务 ID         → 正在处理的业务对象
MRTR            → 缺什么输入，以及如何继续处理

对产品而言，更有价值的变化是：AI 任务可以先结束当前请求，等用户在合适的入口做决定，再继续完成任务，而不必始终占着一段没有挂断的会话窗口。
